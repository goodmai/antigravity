API-стили и контракты

Канон: REST (Fielding, гл. 5), OpenAPI Specification, gRPC docs, GraphQL spec.

Контракт — это обещание между командами, которое переживёт обе. Стиль API выбирается по характеру взаимодействия, а не по моде: ресурсный CRUD, гибкая агрегация для клиента и низколатентный вызов сервис↔сервис — три разные задачи.

1. Три стиля и их компромиссы

СтильКогдаСильная сторонаСлабое место
RESTресурсный CRUD, публичный APIHTTP-кэш, простота, evolvabilityover/under-fetching
GraphQLгибкие клиенты, агрегацияклиент берёт ровно нужноесложность кэша, N+1
gRPCсервис↔сервис, низкая латентностьбинарный protobuf, стримыбраузер только через прокси

Филдинг описывает REST как набор ограничений (stateless, uniform interface, cacheable), а не как «JSON по HTTP». Ключевое свойство REST — эволюционируемость: уровень абстракции ресурса позволяет менять сервер, не ломая клиента, если соблюдён контракт.

2. Контракт-first и OpenAPI

Контракт пишется до кода и является источником истины: из него генерируются серверные стабы, клиенты и моки, по нему гоняются contract-тесты в CI. Это переносит обнаружение ломающего изменения с прода в pull request.

openapi: 3.1.0
info: { title: Marketplace Core API, version: 1.0.0 }
paths:
  /works/{id}:
    get:
      operationId: getWork
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Work' }
        '404': { description: not found }
  /orders:
    post:
      operationId: placeOrder
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/PlaceOrder' }
      responses:
        '201': { content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '409': { description: цена изменилась }
components:
  schemas:
    Work:
      type: object
      required: [id, title, priceCents, authorId]
      properties:
        id:        { type: string }
        title:     { type: string }
        priceCents:{ type: integer, format: int64 }
        authorId:  { type: string }
    PlaceOrder:
      type: object
      required: [workId]
      properties:
        workId: { type: string }

Заметьте: тело PlaceOrder содержит только workId — цену сервер берёт из каталога (урок 1.2), не из запроса. Контракт кодирует это правило явно.

3. Версионирование и обратная совместимость

  • Совместимо: добавить опциональное поле, новый эндпоинт, новый enum-вариант, который клиент игнорирует.
  • Ломающе: удалить/переименовать поле, сделать опциональное обязательным, сменить тип или семантику.
  • Версионируйте контракт явно (/v1 или media-type), не «меняйте смысл по-тихому».
  • Contract-тест в CI ловит нарушение раньше прода.
Правило Постела наоборот. Будьте строги к тому, что гарантируете, и снисходительны к тому, что принимаете. Удаление поля ломает молчаливых потребителей, о которых вы не знаете.

Пример использования элементов

Маркетплейс добавляет скидки. Наивно — переименовать priceCents в basePriceCents и добавить finalPriceCents. Это ломающее изменение: старые клиенты читают priceCents. Правильно — expand/contract на уровне контракта:

# v1.1.0 — НЕ ломает: priceCents остаётся, добавлены опциональные поля
Work:
  properties:
    priceCents:      { type: integer, format: int64 }   # = финальная цена, как раньше
    listPriceCents:  { type: integer, format: int64 }    # новое, опциональное
    discountPercent: { type: integer, minimum: 0, maximum: 100 }  # новое, опциональное

Старый клиент продолжает читать priceCents и видит уже дисконтированную цену — поведение не изменилось. Новый клиент использует listPriceCents + discountPercent для отрисовки «было/стало». Поле priceCents удаляется только в /v2, после миграции всех потребителей. Contract-тест проверяет, что v1-ответ всё ещё валиден против старой схемы.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему REST по Филдингу — это набор ограничений, а не «JSON по HTTP», и что даёт эволюционируемость?
  2. вопросКогда GraphQL предпочтительнее REST и какую новую проблему он привносит?
  3. вопросПочему gRPC хорош для сервис↔сервис, но неудобен для браузера напрямую?
  4. вопросКакие изменения контракта обратно совместимы, а какие ломающие? Дайте по два примера.
  5. задачаНапишите фрагмент OpenAPI 3.1 для GET /works/{id} и POST /orders со схемами Work и PlaceOrder.
  6. задачаВведите скидки в схему Work без ломающего изменения; объясните, что увидит старый клиент.
  7. задачаОпишите contract-тест в CI, который поймал бы удаление поля priceCents до прода.
Разбор ответов
  1. REST — ограничения (stateless, uniform interface, cacheable, client-server). Они дают эволюционируемость: сервер можно менять, не ломая клиента, пока соблюдён единообразный контракт ресурса; «JSON по HTTP» этого не гарантирует.
  2. GraphQL уместен при разнородных клиентах и агрегации из многих источников: клиент запрашивает ровно нужные поля, нет over/under-fetch. Цена — сложность HTTP-кэширования и риск N+1 на резолверах.
  3. gRPC использует HTTP/2 + бинарный protobuf и стримы — это быстро и типизировано для внутренних вызовов. Браузер не управляет HTTP/2-кадрами напрямую, поэтому нужен gRPC-Web прокси.
  4. Совместимо: добавить опциональное поле, добавить эндпоинт. Ломающе: удалить/переименовать поле, сделать опциональное обязательным или сменить семантику существующего поля.
  5. Критерий: валидный OpenAPI 3.1 с paths для обоих эндпоинтов, components.schemas Work и PlaceOrder, корректные коды ответов (200/404, 201/409).
  6. Сохранить priceCents как финальную цену, добавить опциональные listPriceCents и discountPercent. Старый клиент читает priceCents и видит уже дисконтированную цену — поведение не изменилось.
  7. В CI хранится «золотая» схема v1; тест валидирует реальный ответ сервиса против неё (или diff двух OpenAPI). Удаление required-поля делает ответ невалидным → сборка падает в PR, не в проде.
