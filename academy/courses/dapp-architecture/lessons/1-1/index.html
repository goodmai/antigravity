Приложение как система

Канон: C4 model (Simon Brown), DDD Reference (Eric Evans), Bounded Context (Fowler), Fundamentals of Software Architecture (Richards/Ford).

Архитектура начинается не со стека, а с домена. Прежде чем выбирать базу или язык, мы описываем, что система делает и где проходят её границы. Сквозной продукт курса — «маркетплейс цифровых работ + лента + платежи» — мы трижды спроектируем по одной и той же сетке из девяти кирпичей. Этот урок задаёт словарь, на котором мы будем сравнивать классику, Google Cloud и децентрализацию.

1. Зачем сначала домен, а не технология

Эрик Эванс в DDD формулирует это так: сложность приложения живёт в предметной области, а не в фреймворке. Если границы домена проведены неверно, никакой стек это не исправит — ошибка просто «размажется» по микросервисам, облаку или контрактам. Поэтому первый артефакт архитектора — не диаграмма развёртывания, а карта контекстов и единый язык (Ubiquitous Language), на котором бизнес и инженеры называют вещи одинаково.

Ubiquitous Language на практике

Если продакт говорит «работа», бекенд — Item, а база — products, вы платите «налог на перевод» в каждом обсуждении и багрепорте. Договоритесь о терминах один раз и проведите их сквозь код, API и схему БД: сущность называется Work везде — в Solidity-контракте модуля 3 тоже.

2. Девять кирпичей (сетка циркуля)

Любое приложение, независимо от парадигмы, отвечает на одни и те же девять вопросов. Это и есть «циркуль», которым мы трижды обведём один центр. Каждый последующий урок углубляет один кирпич.

3. C4: четыре уровня масштаба

Модель C4 (Simon Brown) — это «карта с разным зумом». Один уровень — один масштаб, одна аудитория. Не смешивайте их на одной диаграмме.

  1. Context — система как чёрный ящик и её акторы/внешние системы. Аудитория: все, включая бизнес.
  2. Container — развёртываемые единицы (SPA, API, БД, очередь) и потоки между ними. Аудитория: инженеры, devops.
  3. Component — внутренние блоки одного контейнера.
  4. Code — по необходимости (UML/классы); обычно генерируется из кода, а не рисуется руками.
Правило аудитории. Если на Context-диаграмме появилось слово «Redis» — вы спустились на уровень Container и запутаете бизнес. Каждый уровень отвечает только на свой вопрос.

4. Bounded Context: где резать систему

Bounded Context — это явная граница, внутри которой термин имеет ровно одно значение. «Пользователь» в Identity (профиль, пароль) и «Пользователь» в Payments (плательщик, payout-аккаунт) — это разные модели, связанные только идентификатором. Объединять их в одну таблицу — классическая ошибка, которая позже заставляет распиливать монолит по живому.

Пример использования элементов

Применим словарь к сквозному продукту. Сначала — Bounded Contexts маркетплейса:

Catalog        — карточки работ, поиск, теги
Identity        — профили, аутентификация
Order/Payments  — корзина, оплата, выплаты автору
Feed            — лента активности и подписки
Media           — загрузка и доставка файлов работ

Теперь — Context-диаграмма в нотации, которую мы держим как артефакт (C4-PlantUML / Structurizr DSL):

workspace {
  model {
    buyer  = person "Покупатель"
    author = person "Автор работ"
    market = softwareSystem "Маркетплейс цифровых работ" {
      description "Каталог + лента + платежи"
    }
    psp = softwareSystem "Платёжный провайдер" "Внешняя система"

    buyer  -> market "Ищет и покупает работы"
    author -> market "Публикует работы, получает выплаты"
    market -> psp    "Проводит платёж / payout"
  }
  views { systemContext market { include * autolayout lr } }
}

Заметьте: ни одного упоминания PostgreSQL, Kafka или контракта. Это уровень Context — он переживёт смену всех трёх парадигм курса. Каждый Bounded Context имеет собственную модель и контракт; пересечения идут через явные интеграции, а не общую БД.

Связь контекстов: Context Map

Эванс описывает паттерны связей между контекстами. Для нас важны три:

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему DDD утверждает, что начинать проектирование нужно с домена, а не с выбора БД или фреймворка?
  2. вопросЧем уровень Context в C4 отличается от Container и какая аудитория у каждого?
  3. вопросЧто такое Ubiquitous Language и какой конкретный «налог» вы платите, если его нет?
  4. вопросПочему «Пользователь» в Identity и «Пользователь» в Payments — это разные модели? Что их связывает?
  5. задачаВыпишите 9 кирпичей и для каждого сформулируйте вопрос применительно к маркетплейсу (одно предложение на кирпич).
  6. задачаНарисуйте Context-диаграмму продукта в Structurizr DSL или PlantUML с акторами «покупатель», «автор» и внешним PSP. Проверьте: нет ни одной технологии.
  7. задачаПостройте Context Map: для каждой пары контекстов (Catalog, Identity, Payments, Feed, Media) укажите тип связи (Customer–Supplier / ACL / Published Language) и направление зависимости.
Разбор ответов
  1. Сложность продукта живёт в предметной области, а не в технологии. Неверно проведённые границы домена нельзя «починить» стеком — ошибка размажется по сервисам/облаку/контрактам. Технология — это как, домен — что; выбор «как» без ответа «что» преждевременен.
  2. Context — система как чёрный ящик + акторы и внешние системы, аудитория — все, включая бизнес. Container — развёртываемые единицы (SPA, API, БД, очередь) и протоколы между ними, аудитория — инженеры/devops. Технологии (Redis, Postgres) допустимы только с уровня Container.
  3. Единый язык, на котором бизнес и инженеры называют сущности одинаково и который проходит сквозь код, API и схему БД. Без него платится «налог на перевод»: каждое обсуждение, багрепорт и ревью требует мысленного маппинга «работа ↔ Item ↔ products», где и рождаются ошибки.
  4. Это разные Bounded Contexts: в Identity модель — профиль, аутентификация; в Payments — плательщик, payout-аккаунт, KYC. У них разные инварианты и жизненный цикл. Связывает их только стабильный идентификатор (user id), а не общая таблица.
  5. Образец: Compute — «где исполняется код карточек и оплаты?»; State — «где истина о владельце работы?»; Storage — «где лежат файлы работ?»; Messaging — «как лента узнаёт о новой работе?»; Identity — «как доказать, что это автор?»; Networking — «как запрос доходит до API?»; Secrets — «где ключ к PSP?»; Observability — «как понять, что оплаты проходят?»; Delivery — «как выкатить новую цену без даунтайма?».
  6. Критерий приёмки: на диаграмме есть person покупатель/автор, softwareSystem маркетплейс и внешний PSP, связи подписаны бизнес-действиями. Ошибка, если появились БД, очередь или язык — это уже Container.
  7. Образец: Catalog → Feed — Customer–Supplier (Feed зависит от событий Catalog); Payments ↔ PSP — Anticorruption Layer; ядро ↔ внешние потребители — Published Language (OpenAPI); Identity — Supplier для всех (выдаёт user id), но без общей БД.
