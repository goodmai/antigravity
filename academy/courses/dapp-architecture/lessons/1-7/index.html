Файлы и медиа

Канон: AWS S3 presigned URLs, MDN: HTTP caching, Amazon S3 docs.

Файлы не хранят в БД и не гоняют через бэкенд. Индустриальный паттерн: объектное хранилище (S3) как стор + presigned URL для прямой загрузки/скачивания + CDN для доставки. БД хранит только метаданные и ссылку, бэкенд — только авторизует.

1. Почему объектное хранилище, а не БД и не диск

BLOB в реляционной БД раздувает её, ломает резервное копирование и кэш страниц. Локальный диск пода не переживёт рестарт и не масштабируется горизонтально. Объектное хранилище решает обе проблемы: бесконечно масштабируемое, дешёвое, с собственной durability. БД хранит media(id, s3_key, content_type, size, checksum, owner_id) — указатель и факты, не байты.

2. Прямая загрузка через presigned URL

Гонять гигабайты через бэкенд — это утроенный трафик и упёртый в память процесс. Presigned URL — это временно подписанная ссылка: бэкенд с правами IAM генерирует её, клиент кладёт файл напрямую в S3, бэкенд в потоке не участвует.

client → POST /uploads        (бэкенд выдаёт presigned PUT URL)
client → PUT  s3://bucket/... (грузит напрямую, минуя бэкенд)
client → POST /uploads/confirm (бэкенд валидирует, пишет метаданные)
// бэкенд: выдать presigned PUT с жёсткими ограничениями
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

const key = `works/${ownerId}/${crypto.randomUUID()}`;
const url = await getSignedUrl(s3,
  new PutObjectCommand({
    Bucket: 'mkt-private',
    Key: key,
    ContentType: 'application/zip',
    ContentLength: size,            // ограничиваем размер
  }),
  { expiresIn: 300 });              // ссылка живёт 5 минут
// клиент делает PUT по url; затем POST /uploads/confirm с key
Доверять только confirm. Факт выдачи presigned URL не значит, что файл загружен. Метаданные пишутся только в /confirm после HeadObject (размер, content-type, checksum совпали) — иначе в каталоге появятся «пустые» работы.

3. Доставка через CDN и приватность

  • Иммутабельные ассеты — Cache-Control: max-age=31536000, immutable.
  • Версионирование через хэш в имени файла, а не query-параметр (query ломает кэш некоторых CDN).
  • Публичные превью — кэшируемы на CDN; приватный контент (купленная работа) — короткоживущие подписанные ссылки на каждую выдачу.
  • Bucket приватный по умолчанию; публичность даёт только CDN-origin.

Пример использования элементов

Автор загружает архив работы; покупатель после оплаты скачивает его. Поток для маркетплейса:

1. POST /works/{id}/upload-url
   бэкенд: проверяет, что вызывающий = автор работы;
   выдаёт presigned PUT (key=works/{authorId}/{uuid}, TTL 5 мин, лимит размера)
2. client PUT → S3 (напрямую, бэкенд не в потоке)
3. POST /works/{id}/upload/confirm { key }
   бэкенд: HeadObject → проверяет size/content-type/etag,
   пишет media(...) и связывает с работой; до этого работа = draft
4. покупатель оплатил (урок 1.6) → GET /works/{id}/download
   бэкенд: проверяет наличие оплаченного order(buyer, work);
   выдаёт presigned GET с TTL 60 сек
5. CDN раздаёт публичные превью (immutable, хэш в имени);
   приватный архив — только по свежей подписанной ссылке, не кэшируется

Разбор: бэкенд нигде не пропускает файл через себя — только авторизует и фиксирует метаданные. Авторизация на каждом шаге серверная (автор для upload, оплативший buyer для download — клиенту не верим, урок 1.2). Приватный архив не кэшируется CDN и доступен только по ссылке, живущей 60 секунд, поэтому утёкшая ссылка быстро мертва.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему файлы не хранят в реляционной БД и не на локальном диске пода?
  2. вопросЧто такое presigned URL и зачем ограничивать его TTL, размер и content-type?
  3. вопросПочему метаданные пишут только в шаге /confirm, а не при выдаче URL?
  4. вопросЧем доставка публичного превью через CDN отличается от выдачи приватного купленного файла?
  5. задачаНапишите серверную функцию, выдающую presigned PUT с лимитом размера и TTL 5 минут.
  6. задачаОпишите полный поток upload→confirm→download для купленной работы с серверной авторизацией на каждом шаге.
  7. задачаПредложите кэш-политику: какие ассеты делать immutable на CDN, а какие — некэшируемыми, и почему.
Разбор ответов
  1. BLOB раздувает БД, ломает бэкап и кэш; локальный диск не переживает рестарт пода и не масштабируется. Объектное хранилище дёшево, durable и горизонтально масштабируемо; в БД — только метаданные и ключ.
  2. Это временно подписанная ссылка, дающая клиенту право на одну операцию с объектом без раздачи ключей. TTL ограничивает окно злоупотребления, лимит размера/типа — защита от загрузки мусора и DoS.
  3. Выдача URL не доказывает успешную загрузку. Только /confirm + HeadObject подтверждает, что объект есть и его size/type/checksum валидны; иначе появятся «пустые» работы.
  4. Публичное превью — иммутабельно, кэшируется CDN надолго (хэш в имени). Приватный файл — индивидуальная короткоживущая подписанная ссылка на каждую выдачу, без кэширования, после проверки оплаты.
  5. Критерий: getSignedUrl(PutObjectCommand{Bucket,Key, ContentType,ContentLength}) с expiresIn: 300; key включает owner; размер передан в команду.
  6. Критерий: (1) upload-url с проверкой «вызывающий=автор»; (2) прямой PUT в S3; (3) confirm с HeadObject-валидацией и записью media; (4) download с проверкой оплаченного заказа и presigned GET TTL ~60с.
  7. Образец: статика/превью с хэшем в имени — max-age=31536000, immutable; приватный купленный архив — без кэша CDN, только свежая подписанная ссылка; HTML/метаданные — короткий TTL или no-cache.
