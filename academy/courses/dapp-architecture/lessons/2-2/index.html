Compute на Google Cloud

Канон: Cloud Run docs, GKE Autopilot, Architecture Framework.

Кирпич Compute отвечает на вопрос «где исполняется код?». В классике это был наш кластер; на Google Cloud есть лестница абстракций от App Engine до Compute Engine. Выбор runtime для маркетплейса — не вкус, а функция от модели нагрузки, требований к latency и допустимого lock-in.

1. Четыре managed-runtime и их модель

Cloud Run — контейнер по запросу: вы даёте образ, Google скейлит от нуля до тысяч инстансов по конкурентности. Платите за CPU/RAM во время обработки запроса. GKE Autopilot — Kubernetes, где Google управляет нодами и биллит по запрошенным pod-ресурсам; нужен, когда требуется полный k8s-API (DaemonSet, операторы, сложный networking). App Engine Standard — старейший PaaS, привязан к рантаймам и сильнее лочит. Cloud Functions (2nd gen) — функция на событие, под капотом тот же Cloud Run.

2. Холодный старт, конкурентность и стоимость

Cloud Run обрабатывает несколько запросов на инстанс (concurrency, по умолчанию 80) — это резко снижает счёт против «инстанс на запрос». Холодный старт лечится min-instances (тёплый пул, платится постоянно) или CPU boost. Для платёжного пути с SLO 99.95% холодный старт в хвосте латентности недопустим — держим минимум 1–2 тёплых инстанса.

gcloud run deploy market-api \
  --image=REGION-docker.pkg.dev/PROJECT/repo/market-api:1.4.2 \
  --concurrency=80 --cpu=1 --memory=512Mi \
  --min-instances=2 --max-instances=50 \
  --no-allow-unauthenticated --region=europe-west1

Trade-off строкой: стоимость низкая при скейле-до-нуля, растёт с min-instances; lock-in низкий — это обычный OCI-контейнер; контроль низкий — нет доступа к ядру и sidecar-ам уровня k8s.

Пример использования элементов

Catalog и Payments — оба Cloud Run, но с разной политикой масштабирования. Манифест сервиса оплаты фиксирует SLO-обоснованные параметры:

apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: payments-api
  annotations:
    run.googleapis.com/ingress: internal-and-cloud-load-balancing
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "2"
        autoscaling.knative.dev/maxScale: "30"
    spec:
      containerConcurrency: 40
      containers:
        - image: REGION-docker.pkg.dev/PROJECT/repo/payments:2.1.0
          resources:
            limits: { cpu: "1", memory: 512Mi }

Решение: каталог — minScale: 0 (экономия ночью), оплата — minScale: 2 (нет холодного старта в денежном пути), конкурентность ниже у оплаты (40 vs 80) ради изоляции тяжёлых запросов к PSP. Транскодинг медиа выносим в Cloud Run jobs / GKE Autopilot, чтобы длинные задачи не держали HTTP-инстансы.

Артефакт урока. ADR-03 «runtime» — Cloud Run для Catalog/Payments/Feed и GKE Autopilot для медиа, с секциями «Контекст / Решение / Альтернативы / Последствия» и строкой trade-off (стоимость·lock-in·контроль) на каждый компонент.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем модель биллинга Cloud Run отличается от GKE Autopilot и как это влияет на ночной нулевой трафик?
  2. вопросКогда GKE Autopilot оправдан, несмотря на то что Cloud Run проще?
  3. вопросЧто такое concurrency в Cloud Run и почему она радикально снижает стоимость?
  4. вопросПочему App Engine Standard лочит сильнее, чем Cloud Run?
  5. задачаОбоснуйте, почему платёжному API нужен min-instances ≥ 1, а каталогу — нет.
  6. задачаНапишите команду gcloud run deploy для Feed-worker, принимающего push из Pub/Sub, с приватным ingress и max 20 инстансов.
  7. задачаЗаполните ADR-03: контекст, решение, отвергнутые альтернативы и последствия выбора runtime для маркетплейса.
Разбор ответов
  1. Cloud Run биллит за CPU/RAM во время обработки запроса и скейлит до нуля — ночью счёт ~0. GKE Autopilot биллит за запрошенные ресурсы pod-ов и держит минимум нод, поэтому платится даже без трафика.
  2. Когда нужен полноценный k8s-API: DaemonSet, операторы, service mesh, StatefulSet, тонкий контроль networking/affinity или долгоживущие процессы, которые модель «запрос → ответ» Cloud Run не покрывает.
  3. Concurrency — число одновременных запросов на инстанс. При 80 один инстанс обслуживает 80 запросов вместо одного, во столько же раз меньше инстансов и счёт; цена — конкуренция за CPU внутри инстанса.
  4. App Engine Standard привязывает к поддерживаемым рантаймам и проприетарному окружению/API; миграция требует переписывания. Cloud Run запускает любой OCI-образ, переносимый в любой контейнерный рантайм.
  5. Платёжный путь latency-критичен, SLO 99.95%: холодный старт добавляет секунды в хвост и тратит error budget. Каталог терпит редкий холодный старт ночью ради экономии на нулевом трафике.
  6. gcloud run deploy feed-worker --image=REGION-docker.pkg.dev/PROJECT/repo/feed:1.0 --no-allow-unauthenticated --ingress=internal --max-instances=20 --region=europe-west1; Pub/Sub push с OIDC service account, имеющим roles/run.invoker.
  7. Контекст: разные профили нагрузки компонентов. Решение: Cloud Run для Catalog/Payments/Feed, GKE Autopilot для транскодинга. Альтернативы: всё на GKE (дорого ночью), App Engine (lock-in). Последствия: низкий lock-in, экономия на скейле-до-нуля, ограниченный контроль рантайма.
