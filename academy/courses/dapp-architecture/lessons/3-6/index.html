Децентрализованная доставка

Канон: IPFS docs, IPFS gateway docs.

Это децентрализованный аналог кирпича Networking/доставки (Cloud CDN). p2p-доставка «холодная» медленнее облака; шлюзы и DePIN-CDN сглаживают латентность, но вводят новую точку доверия.

1. Шлюз как мост и как точка централизации

Браузер не говорит по протоколу IPFS напрямую — он ходит на HTTP-шлюз (https://gw/ipfs/<CID>), который достаёт контент из сети и отдаёт по HTTP. Шлюз самопроверяем (можно сверить хеш с CID), но публичный шлюз — это централизованная точка: он может быть недоступен, медленным или цензурировать. Поэтому в проде используют несколько шлюзов с фоллбэком или свой.

2. Кэш и латентность p2p

Первый запрос CID может потребовать DHT-поиска провайдера — это секунды. После — контент кэшируется на шлюзе/в браузере и отдаётся быстро. DePIN-сети (AIOZ, Fleek edge) добавляют географически распределённый кэширующий слой поверх content addressing — функциональный аналог edge-PoP облачного CDN.

  • Шлюз — мост HTTP↔IPFS; узкое место и точка доверия.
  • Fleek — деплой+кэш статики поверх IPFS (аналог хостинга+CDN).
  • AIOZ — DePIN-CDN: ноды раздают контент за вознаграждение.

Пример использования элементов

Превью и купленные файлы работ маркетплейса доставляем через пул шлюзов с фоллбэком и кэшем; интерактивный API остаётся на облаке.

const GATEWAYS = ["https://gw-a/ipfs/", "https://gw-b/ipfs/", "https://gw-self/ipfs/"];
async function fetchAsset(cid) {
  for (const gw of GATEWAYS) {
    try {
      const r = await fetch(gw + cid, { signal: AbortSignal.timeout(3000) });
      if (r.ok) return r;          // CID самопроверяем — подмена исключена
    } catch (_) { /* следующий шлюз */ }
  }
  throw new Error("all gateways failed");
}

Иммутабельный ассет идеально ложится на p2p-доставку; динамический интерактив (корзина, поиск) оставляем за облачным путём.

Граница применимости. Для иммутабельных ассетов (превью, файлы работ) p2p отлично. Для интерактивного динамического контента латентность «холодного» доступа всё ещё проигрывает облачному CDN — это осознанная граница гибрида.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему публичный IPFS-шлюз — точка централизации, несмотря на децентрализованный контент?
  2. вопросПочему первый запрос CID может быть медленным, а повторный — быстрым?
  3. вопросПочему подмена контента шлюзом не страшна при доставке по CID?
  4. вопросКакой класс контента маркетплейса плохо подходит для p2p-доставки и почему?
  5. задачаСпроектируйте стратегию фоллбэка по нескольким шлюзам с таймаутом и проверкой CID.
  6. задачаРазделите ассеты маркетплейса на «через p2p» и «через облачный CDN» с критерием.
  7. задачаОпишите, как снизить «холодную» латентность первого доступа к новому превью.
Разбор ответов
  1. Браузер ходит на конкретный HTTP-шлюз. Этот шлюз может быть недоступен, медленным или блокировать запрос — единая точка отказа и цензуры, хотя сам контент распределён.
  2. Первый запрос требует поиска провайдера в DHT (секунды). Дальше контент закэширован на шлюзе/в браузере и отдаётся из кэша быстро.
  3. Адрес — это хеш содержимого. Клиент пересчитывает хеш полученных байтов и сверяет с CID; любая подмена даёт другой хеш и отбрасывается.
  4. Интерактивный/динамический контент (поиск, корзина): он меняется и чувствителен к латентности; content addressing и «холодный» p2p здесь проигрывают облачному CDN.
  5. Образец: список шлюзов, по очереди fetch с таймаутом ~3 с, переход к следующему при ошибке/таймауте; результат принимается, так как CID гарантирует целостность.
  6. Через p2p: превью, файлы купленных работ (иммутабельны). Через облачный CDN: динамические страницы, API. Критерий — иммутабельность и терпимость к латентности первого доступа.
  7. Прогревать: пиннить новый CID на нескольких шлюзах/DePIN-нодах сразу после загрузки и делать прогревочный запрос, чтобы он попал в кэш до первого пользователя.
