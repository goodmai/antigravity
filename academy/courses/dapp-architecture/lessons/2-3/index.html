Данные на Google Cloud

Канон: Spanner docs, Firestore docs, Spanner paper, DDIA.

Кирпич State/Data отвечает на вопрос «где живёт истина о данных?». На Google Cloud это спектр от Cloud SQL (знакомый Postgres) до Spanner (глобальная strong-consistency) и Firestore (документная, realtime). Для маркетплейса разные Bounded Contexts требуют разных гарантий, и выбор определяется согласованностью, масштабом и операционной ценой.

2. Согласованность и TrueTime

DDIA различает уровни согласованности; Spanner добавляет external consistency — транзакции упорядочены так, будто выполнялись по глобальным часам. Это возможно благодаря TrueTime: API, возвращающий не точку, а интервал [earliest, latest] с гарантированной границей погрешности (атомные часы + GPS). Spanner делает commit-wait — ждёт, пока неопределённость интервала пройдёт, — и получает линеаризуемость на глобальном масштабе. Цена: латентность записи выше и стоимость существенно больше Cloud SQL.

Правило выбора. Не нужен глобальный масштаб со strong-консистентностью — не платите за Spanner. Для одного региона Cloud SQL/AlloyDB дают те же транзакционные гарантии дешевле и с меньшим lock-in.

3. Критерии выбора для маркетплейса

Деньги требуют сериализуемых транзакций → реляционка. Профили и лента требуют realtime и гибкой схемы → Firestore. Аналитические события (урок 2.4) не место в OLTP-базе.

Пример использования элементов

Схема Catalog/Payments в Cloud SQL (Postgres) с идемпотентностью платежа:

CREATE TABLE works (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  author_id     UUID NOT NULL,
  title         TEXT NOT NULL,
  price_cents   INTEGER NOT NULL CHECK (price_cents >= 0),
  status        TEXT NOT NULL DEFAULT 'draft',
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  buyer_id        UUID NOT NULL,
  work_id         UUID NOT NULL REFERENCES works(id),
  amount_cents    INTEGER NOT NULL,
  state           TEXT NOT NULL DEFAULT 'pending',
  idempotency_key TEXT NOT NULL UNIQUE,   -- защита от двойной оплаты
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

Профиль и лента — в Firestore, где документ обновляется атомарно и клиенты получают live-снимки:

// коллекция users/{uid}
{ "displayName": "ann", "rating": 4.8, "followers": 312 }

// feed/{uid}/items/{itemId} — realtime подписка клиента
db.collection(`feed/${uid}/items`).orderBy('ts','desc').limit(50)
  .onSnapshot(s => render(s.docs));

Решение: связь по идентификатору пользователя соединяет Cloud SQL и Firestore без общей таблицы (граница Bounded Context из урока 1.1 сохранена). Spanner не берём — продукт регионален, глобальная external consistency не нужна, а её цена не оправдана.

Артефакт урока. Схема данных на GCP: DDL Cloud SQL для Catalog/Payments + структура коллекций Firestore для Identity/Feed, с пометкой выбранного уровня согласованности и строкой trade-off на каждое хранилище.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧто такое external consistency в Spanner и чем она сильнее обычной strong-consistency?
  2. вопросКак TrueTime и commit-wait обеспечивают глобальную упорядоченность транзакций?
  3. вопросПочему для регионального маркетплейса Spanner — обычно переплата?
  4. вопросПочему профиль и лента ложатся на Firestore, а оплата — нет?
  5. задачаСпроектируйте таблицу orders с защитой от двойного списания и объясните роль idempotency_key.
  6. задачаОпишите, как связать запись в Cloud SQL и документ Firestore, не нарушая границу Bounded Context.
  7. задачаПостройте таблицу «контекст → хранилище → согласованность → trade-off» для всех данных маркетплейса.
Разбор ответов
  1. External consistency: если транзакция T1 закоммитилась до старта T2 в реальном времени, то и в глобальном порядке T1 раньше T2. Это сильнее линеаризуемости одного узла — гарантия держится между регионами.
  2. TrueTime возвращает интервал времени с ограниченной погрешностью (атомные часы + GPS). Spanner делает commit-wait — ждёт прохождения неопределённости интервала перед публикацией коммита, поэтому метки транзакций монотонны и сопоставимы глобально.
  3. Spanner оплачивается за глобальную распределённость и strong-scale, которые региональному продукту не нужны. Cloud SQL/AlloyDB дают те же ACID-гарантии в одном регионе значительно дешевле и проще.
  4. Профиль/лента — гибкая схема, realtime-подписки, обновление по документу: сильные стороны Firestore. Оплата требует многострочных сериализуемых транзакций и аудита — это реляционная Cloud SQL.
  5. Поля buyer_id, work_id, amount_cents, state и idempotency_key TEXT UNIQUE. Клиент передаёт ключ; повтор запроса с тем же ключом нарушает UNIQUE и возвращает прежний результат вместо второго списания.
  6. Хранить в обоих только общий идентификатор пользователя; никакой общей таблицы или внешнего ключа между системами. Синхронизация — через событие/контракт, а не shared DB; модели остаются независимыми.
  7. Catalog→Cloud SQL (strong, $ средний/lock-in низкий); Payments→Cloud SQL (strong ACID); Identity profile→Firestore (strong на документ, lock-in высокий); Feed→Firestore (realtime, lock-in высокий); аналитика — не в OLTP (см. урок 2.4).
