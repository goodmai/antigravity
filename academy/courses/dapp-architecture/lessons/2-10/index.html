Доставка и IaC

Канон: Cloud Build, Cloud Deploy, Terraform docs.

Кирпич Delivery/Governance отвечает на вопрос «как изменения попадают в прод?». Принцип модуля: build once, promote many — один неизменный образ продвигается по средам, а вся инфраструктура описана декларативным кодом. Для маркетплейса это убирает класс багов «works on staging» и делает откат предсказуемым.

1. Build once: Cloud Build и Artifact Registry

Cloud Build собирает образ один раз из коммита, фиксирует provenance (SLSA-аттестация: из какого коммита и пайплайна) и кладёт в Artifact Registry с неизменяемым digest. Дальше во все среды едет тот же digest, не пересобираемый под прод — пересборка вносит дрейф зависимостей.

# cloudbuild.yaml
steps:
  - name: gcr.io/cloud-builders/docker
    args: ['build','-t','$_REPO/market-api:$SHORT_SHA','.']
  - name: gcr.io/cloud-builders/docker
    args: ['push','$_REPO/market-api:$SHORT_SHA']
options: { requestedVerifyOption: VERIFIED }   # provenance
images: ['$_REPO/market-api:$SHORT_SHA']

2. Promote many: Cloud Deploy и progressive delivery

Cloud Deploy описывает delivery pipeline: dev → staging → prod с ручным одобрением между средами и автоматическим verify. Catalog может ехать canary (10% → 50% → 100%) на ревизиях Cloud Run; Payments — после ручного approve и прогона SLO-проверки (связь с error budget урока 2.9).

apiVersion: deploy.cloud.google.com/v1
kind: DeliveryPipeline
metadata: { name: market-api }
serialPipeline:
  stages:
    - targetId: dev
    - targetId: staging
    - targetId: prod
      strategy:
        canary:
          runtimeConfig: { cloudRun: {} }
          canaryDeployment: { percentages: [10, 50] }

3. Инфраструктура как код: Terraform vs Config Connector

Ресурсы (Cloud Run, Cloud SQL, IAM, Cloud Armor) описываются кодом и проходят ревью в PR; plan показывает дрейф до применения. Terraform — мультиоблачный, своё состояние. Config Connector — GCP-ресурсы как k8s-объекты, непрерывная реконсиляция, но привязка к GKE.

Пример использования элементов

Pipeline маркетплейса: коммит → один образ с provenance → промоут по средам, инфраструктура из git:

git push ──▶ Cloud Build ──▶ Artifact Registry
                 (build once, SLSA provenance, digest)
                       │ тот же digest
                       ▼
Cloud Deploy: dev ──auto verify──▶ staging ──approve──▶ prod (canary 10→50→100)
                                                          │ SLO gate (урок 2.9)
Terraform plan/apply (PR-ревью): Cloud Run, Cloud SQL, IAM, Cloud Armor
# Terraform: ревизия привязана к неизменному digest, не к :latest
resource "google_cloud_run_v2_service" "market_api" {
  name     = "market-api"
  location = "europe-west1"
  template { containers { image = "REPO/market-api@sha256:DIGEST" } }
}

Решение: образ собирается один раз с provenance; в prod Catalog едет canary, Payments — после approve и SLO-gate; вся инфраструктура (включая правила Cloud Armor урока 2.7 и SA урока 2.6) — Terraform с ревью в PR. CI аутентифицируется через WIF (урок 2.6), без ключей. Откат = промоут предыдущей ревизии, мгновенно. Lock-in: образ и Terraform переносимы, Cloud Deploy — средняя привязка.

Артефакт урока. Pipeline-диаграмма маркетплейса: Cloud Build (build once + provenance) → Artifact Registry → Cloud Deploy (dev→staging→prod, canary + SLO-gate) + слой Terraform/Config Connector с ревью инфраструктуры в PR.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему принцип «build once, promote many» устраняет класс багов «works on staging»?
  2. вопросЧто такое provenance и зачем фиксировать digest вместо тега :latest?
  3. вопросЧем canary deployment отличается от прямого переключения 100%?
  4. вопросВ чём разница между Terraform и Config Connector по обработке дрейфа и lock-in?
  5. задачаСпроектируйте delivery pipeline для Payments с ручным approve и SLO-gate перед prod.
  6. задачаОпишите, как откатить плохой релиз Catalog за секунды, не пересобирая образ.
  7. задачаОбъясните, почему правила Cloud Armor и service accounts тоже должны жить в Terraform, а не в консоли.
Разбор ответов
  1. В прод едет тот же артефакт, что прошёл staging; пересборки под прод нет, значит нет дрейфа зависимостей/окружения. Расхождение «на staging работало» исчезает, потому что среды получают идентичный образ.
  2. Provenance — аттестация, из какого коммита и пайплайна собран образ (SLSA). Digest неизменяем и однозначен, :latest может указывать на разные образы в разное время — источник невоспроизводимых деплоев.
  3. Canary выкатывает новую ревизию части трафика (10→50→100), наблюдая SLI; проблема ловится на малой доле пользователей. Прямые 100% переключают всех сразу — отказ затрагивает всю аудиторию.
  4. Terraform: plan/apply со state, дрейф виден в plan/PR, низкий lock-in, мультиоблако. Config Connector: k8s reconcile-loop автоисправляет дрейф, но требует GKE — средний lock-in, только GCP.
  5. Pipeline dev→staging→prod; между staging и prod — ручной approve; перед prod-стадией verify-проверка SLO (burn rate в норме, бюджет есть); прод-стратегия — осторожный canary или после approve полное.
  6. Cloud Run/Cloud Deploy промоутят предыдущую ревизию (старый digest) — переключение трафика на уже существующий образ за секунды, без пересборки и без билд-пайплайна.
  7. Иначе конфигурация периметра и доступы не воспроизводимы, не ревьюятся и расходятся между средами (drift). В Terraform они версионируются, проходят ревью в PR и применяются одинаково везде, как код приложения.
