Observability на Google Cloud

Канон: Cloud Monitoring, SRE Workbook: Implementing SLOs.

Кирпич Observability отвечает на вопрос «как мы узнаём, что система жива?». На Google Cloud это управляемая Operations Suite (Logging, Monitoring, Trace, Profiler), а сверху — SLO как объект с error budget и burn-rate алертами по SRE Workbook. Для маркетплейса цель — алертить на симптом, важный пользователю, а не на каждый дёрг метрики.

1. Четыре столпа Operations Suite

СервисОтвечает на вопросВ маркетплейсе
Cloud LoggingЧто именно произошло?Структурные логи с trace-id
Cloud MonitoringКаков тренд показателя?SLI, дашборды, алерты
Cloud TraceГде время в распределённом запросе?Покупка через N сервисов
Cloud ProfilerГде CPU/память внутри сервиса?Профиль Catalog API

Логи коррелируются с трейсами по trace-полю — из лога оплаты переходим в полный путь запроса через Payments → Pub/Sub → Payout.

2. SLI, SLO и error budget на практике

SRE Workbook предписывает: SLI измеряет опыт пользователя в долях (good/valid), SLO — целевой порог за окно, error budget — допустимый остаток «плохого». Для маркетплейса критичный SLI checkout — availability+latency: запрос «хороший», если status < 500 И latency < 300ms.

slo:
  service: checkout
  sli:
    good:  request.status < 500 AND request.latency < 300ms
    valid: все запросы POST /checkout
  objective: 99.9%          # rolling 28-дневное окно
  error_budget: 0.1%        # ~40 мин «плохого» за окно
  alerting: multi-window, multi-burn-rate

3. Burn-rate alerts: multi-window multi-burn-rate

Алерт на «error budget исчерпан» приходит слишком поздно. SRE Workbook предлагает алертить на скорость сжигания (burn rate): во сколько раз быстрее нормы тратится бюджет. Multi-window отсекает шум: быстрый burn подтверждается коротким и длинным окном, иначе ложная тревога.

Burn rateОкнаСмыслДействие
14.4x1ч и 5мин2% бюджета за часPage дежурному
6x6ч и 30мин5% бюджета за 6чPage дежурному
1x3д и 6чМедленная деградацияTicket, без пейджа

Пример использования элементов

SLO-спецификация checkout-пути маркетплейса с двумя burn-rate политиками, привязанная к Cloud Monitoring service-level objective:

displayName: "checkout availability+latency"
serviceLevelIndicator:
  requestBased:
    distributionCut:
      distributionFilter: 'metric.type="run.googleapis.com/request_latencies" resource.service_name="payments-api"'
      range: { max: 300 }            # latency < 300ms = good
goal: 0.999
rollingPeriod: 2419200s              # 28 дней
---
alertPolicy:
  - condition: burn_rate > 14.4 over [5m, 1h]   # быстрый ожог → page
  - condition: burn_rate > 6   over [30m, 6h]   # средний ожог → page
  - condition: budget_remaining < 10%           # фриз релизов

Решение: пейджим только на быстрый ожог бюджета checkout (симптом, который чувствует покупатель), не на каждый всплеск CPU. При остатке бюджета <10% — автоматический сигнал на freeze релизов (связь с error budget из урока 2.1). Trace показывает, какой из сервисов (Payments/Pub/Sub/Payout) даёт латентность. Lock-in: SLI-определения переносимы, привязка к метрикам Cloud Monitoring — средняя.

Артефакт урока. SLO-спецификация checkout: определение SLI (status<500 AND latency<300ms), цель 99.9% за 28 дней, расчёт error budget и две multi-window multi-burn-rate политики (14.4x и 6x) + правило фриза при остатке <10%.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем SLI отличается от обычной метрики вроде CPU и почему алертить надо на SLI?
  2. вопросЧто такое burn rate и почему он лучше алерта «бюджет исчерпан»?
  3. вопросЗачем burn-rate алерту два окна (multi-window)?
  4. вопросКак Cloud Trace и Cloud Logging связаны и зачем коррелировать их по trace-id?
  5. задачаСформулируйте SLI для checkout маркетплейса (good/valid) и обоснуйте порог 300ms.
  6. задачаПосчитайте error budget для SLO 99.9% за 28 дней и опишите политику фриза релизов.
  7. задачаСпроектируйте две burn-rate политики (быстрый и средний ожог) с окнами и действиями.
Разбор ответов
  1. SLI измеряет опыт пользователя (доля успешных/быстрых запросов), а CPU — внутренний показатель, который может скакать без вреда для пользователя. Алерт на SLI бьёт по симптому, важному клиенту, а не по шуму ресурсов.
  2. Burn rate — во сколько раз быстрее нормы тратится error budget. Он предупреждает заранее, пока бюджет ещё есть; алерт «исчерпан» приходит, когда инцидент уже состоялся.
  3. Короткое окно реагирует быстро, но шумит; длинное подтверждает, что ожог устойчивый. Срабатывание только при совпадении обоих окон убирает ложные тревоги от кратких всплесков.
  4. Логи содержат trace-id того же запроса; по нему из конкретной ошибки переходим в полный распределённый путь (Payments→Pub/Sub→Payout) и видим, где именно деградация — без этого корреляция ручная и медленная.
  5. good = ответ POST /checkout с status < 500 и latency < 300ms; valid = все POST /checkout. 300ms — порог ощутимости задержки оплаты пользователем; выше — UX страдает и теряются конверсии.
  6. 0.1% от валидных запросов за 28 дней (~40 мин эквивалента недоступности). Политика: при остатке <10% бюджета — freeze продуктовых релизов, приоритет на надёжность, пока бюджет не восстановится.
  7. Быстрый ожог: burn_rate > 14.4 на окнах [5м, 1ч] → page дежурному. Средний: burn_rate > 6 на [30м, 6ч] → page. Медленная деградация: 1x на [6ч, 3д] → тикет без пейджа.
