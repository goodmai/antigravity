Кэш, очереди, событийность

Канон: Transactional Outbox, Kafka design, DDIA (Kleppmann), гл. 11.

Асинхронность развязывает компоненты по времени: отправитель не ждёт получателя. Цена — eventual consistency и дубли сообщений. Этот урок: почему «exactly-once» — миф, как делать потребителей идемпотентными и зачем нужен outbox.

1. Гарантии доставки и миф exactly-once

ГарантияСмыслЦена
at-most-once0 или 1 доставкатеряет сообщения
at-least-once≥1 доставкадубли — норма
exactly-onceровно 1 эффекттолько end-to-end, через идемпотентность

На уровне сети exactly-once недостижим (проблема двух генералов): после отправки нельзя отличить «потерян ответ» от «потеряно сообщение», поэтому отправитель ретраит → дубль. Практический «exactly-once» — это at-least-once доставка + идемпотентный приём, где повтор не меняет итоговый эффект. Kafka transactions дают это только внутри Kafka, не до внешнего PSP.

2. Идемпотентность потребителя

Раз дубли неизбежны, потребитель обязан быть идемпотентным: повторная обработка того же события не должна повторять побочный эффект. Механизм — ключ дедупликации, зафиксированный в той же транзакции, что и эффект.

-- обработка события «оплата прошла» — идемпотентно
BEGIN;
  -- вставка-страж: повтор словит конфликт и НЕ продолжит
  INSERT INTO processed_events(event_id) VALUES ($1)
    ON CONFLICT (event_id) DO NOTHING;
  -- если строка не вставилась — дубль, выходим без эффекта
  -- иначе: применяем эффект в той же транзакции
  UPDATE author_balance SET amount_cents = amount_cents + $2
    WHERE author_id = $3;
COMMIT;

3. Outbox: проблема двойной записи

Нельзя атомарно записать в БД и опубликовать в брокер: между коммитом и публикацией процесс может упасть → событие потеряно или, при обратном порядке, опубликовано без коммита. Outbox решает это: событие пишется в ту же транзакцию, что и бизнес-данные, а доставляется отдельным relay.

[tx] INSERT order ; INSERT outbox(event)   ← один коммит, атомарно
 relay → читает outbox → публикует в Kafka → помечает отправленным
Кэш. Redis — это ускоритель, не источник истины. Стратегия инвалидации (TTL / write-through) должна быть явной, иначе вы кэшируете баги. Cache-aside: промах → читаем БД → кладём в кэш с TTL; запись → инвалидируем ключ.

Пример использования элементов

Сценарий «оплата → выплата автору». Платёж проходит в Payments, баланс автора должен пополниться, лента — узнать о продаже. Связываем это через outbox + идемпотентный consumer.

@startuml
actor Buyer
participant API
database OrdersDB
participant Relay
queue Kafka
participant PayoutSvc
participant FeedSvc

Buyer -> API : POST /orders/{id}/pay
API -> OrdersDB : BEGIN\nUPDATE orders SET status=paid\nINSERT outbox(OrderPaid)\nCOMMIT
API --> Buyer : 200 OK (eventual: payout позже)
Relay -> OrdersDB : SELECT unsent FROM outbox
Relay -> Kafka : publish OrderPaid (key=order_id)
Relay -> OrdersDB : mark sent
Kafka -> PayoutSvc : OrderPaid (возможен дубль)
PayoutSvc -> PayoutSvc : INSERT processed_events ON CONFLICT DO NOTHING
PayoutSvc -> PayoutSvc : credit author_balance (если не дубль)
Kafka -> FeedSvc : OrderPaid
FeedSvc -> FeedSvc : append «продажа работы» в ленту
@enduml

Разбор: ответ покупателю — синхронный («оплата принята»), а выплата и лента — eventual. Outbox гарантирует, что событие OrderPaid не потеряется (одна транзакция с заказом). Kafka даёт at-least-once, поэтому PayoutSvc дедуплицирует по order_id через processed_events — повтор не начислит баланс дважды. FeedSvc терпит дубль естественно (append идемпотентен по event_id). Никакого «exactly-once» в сети — только at-least-once + идемпотентность.

Артефакт урока. Sequence-диаграмма event-flow «оплата → выплата автору».

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему «exactly-once» на уровне сети — миф и что под этим понимают на практике?
  2. вопросЧто такое проблема двойной записи и как outbox её решает?
  3. вопросПочему ключ дедупликации нужно фиксировать в той же транзакции, что и эффект?
  4. вопросПочему Redis нельзя считать источником истины и что значит явная инвалидация?
  5. задачаНапишите идемпотентный обработчик события «оплата прошла» с защитой от дубля на уровне БД.
  6. задачаПостройте sequence-диаграмму event-flow «оплата → выплата автору» с outbox, relay и дедупликацией.
  7. задачаОбъясните, какие части потока синхронны, а какие eventual, и почему такое разделение допустимо.
Разбор ответов
  1. После отправки нельзя отличить потерю сообщения от потери ответа (проблема двух генералов), отправитель ретраит → дубль. «Exactly-once» на практике = at-least-once доставка + идемпотентный приём, дающий ровно один эффект.
  2. Двойная запись — невозможность атомарно записать в БД и брокер: сбой между ними теряет или фантомит событие. Outbox пишет событие в ту же транзакцию, что и данные; отдельный relay доставляет его в брокер.
  3. Иначе возможна гонка: эффект применён, а ключ ещё не записан (или наоборот) — сбой между ними сломает идемпотентность. Один коммит на ключ + эффект делает повтор безопасным.
  4. Redis — ускоритель: данные с TTL, узел может потерять кэш. Истина в БД. Явная инвалидация — заранее определённая стратегия (TTL или write-through/удаление ключа при записи), иначе кэшируются устаревшие/ ошибочные данные.
  5. Критерий: транзакция с INSERT processed_events(event_id) ON CONFLICT DO NOTHING; эффект применяется только если строка вставилась; всё в одном COMMIT.
  6. Критерий: на диаграмме есть транзакция order+outbox одним коммитом, relay → Kafka, consumer с дедупликацией по order_id, отдельная ветка Feed; ответ покупателю — до выплаты.
  7. Синхронно: приём оплаты и ответ «принято». Eventual: начисление баланса автора и запись в ленту. Допустимо, потому что эти эффекты не обязаны быть видимы покупателю мгновенно и защищены идемпотентностью.
