Сеть и периметр

Канон: Cloud Load Balancing, Cloud Armor, VPC docs.

Кирпич Networking отвечает на вопрос «как трафик доходит до сервиса и что его фильтрует?». На Google Cloud периметр — это набор управляемых сервисов: глобальный L7-балансировщик, WAF, приватная связность и API-шлюз. Для маркетплейса задача — впустить покупателей, отфильтровать вредный трафик и держать БД недоступной из интернета.

1. VPC, Serverless VPC Access и Private Service Connect

VPC — программно-определяемая сеть с подсетями и firewall-правилами. Serverless-сервисы (Cloud Run) живут вне VPC; чтобы ходить в приватные ресурсы (Cloud SQL по приватному IP), нужен Serverless VPC Access connector или Direct VPC egress. Private Service Connect даёт приватную точку входа к управляемым/сторонним сервисам без выхода в интернет.

СервисНазначениеВ маркетплейсе
VPC + firewallИзоляция и сегментация сетиПодсеть БД закрыта
Serverless VPC AccessCloud Run → приватный ресурсAPI → Cloud SQL приватно
Private Service ConnectПриватный доступ к сервисамДоступ к API без public IP
Cloud NATИсходящий трафик без public IPВызов внешнего PSP

2. Cloud Load Balancing и Cloud Armor

Global external HTTP(S) LB — единый anycast-вход с автоматическим управляемым TLS, маршрутизацией по хостам/путям и backend-ами в Cloud Run. Cloud Armor — WAF/edge-защита на этом LB: пред-настроенные правила OWASP, гео/IP-листы, rate limiting и защита от DDoS на уровне периметра Google.

gcloud compute security-policies create market-waf
gcloud compute security-policies rules create 1000 \
  --security-policy=market-waf \
  --expression="evaluatePreconfiguredExpr('xss-stable')" --action=deny-403
gcloud compute security-policies rules create 1100 \
  --security-policy=market-waf \
  --action=rate-based-ban --rate-limit-threshold-count=100 \
  --rate-limit-threshold-interval-sec=60 --ban-duration-sec=600

3. Apigee / API Gateway

Когда нужны квоты, API-ключи партнёрам, версионирование контракта и монетизация — перед backend ставится API Gateway (лёгкий, на OpenAPI) или Apigee (полноценный API management). Это слой Published Language из урока 1.1, вынесенный в управляемый продукт.

Принцип периметра. Периметр — это политика, а не железка. Правила Cloud Armor и firewall версионируются как код (IaC, урок 2.10) и проходят ревью в PR, как обычный код.

Пример использования элементов

Трафик покупателя проходит управляемый периметр; БД недостижима из интернета:

Интернет
  │  HTTPS (managed TLS)
  ▼
Global HTTP(S) LB ──▶ Cloud Armor (OWASP + rate-limit + geo)
  │ ok
  ▼
Cloud Run: market-api  ──Serverless VPC Access──▶ Cloud SQL (private IP)
  │                                                 ▲ нет public IP
  └──Cloud NAT──▶ внешний PSP (стабильный egress IP)

Решение: единственная публичная точка входа — LB; Cloud Armor режет XSS/боты/всплески до backend; Cloud SQL имеет только приватный IP и доступен Cloud Run через VPC connector; вызовы к внешнему PSP идут через Cloud NAT со стабильным IP (PSP вайтлистит его). Trade-off: периметр managed — меньше контроля над L3/L4, но снимается операционная нагрузка DDoS-защиты и TLS.

Артефакт урока. Диаграмма периметра маркетплейса: LB → Cloud Armor (правила OWASP + rate-limit) → Cloud Run → Serverless VPC Access → приватная Cloud SQL, с egress на PSP через Cloud NAT и пометкой «правила как код».

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЗачем Cloud Run нужен Serverless VPC Access для доступа к Cloud SQL?
  2. вопросЧто делает Cloud Armor на уровне периметра и где он подключается?
  3. вопросЧем Private Service Connect отличается от выхода через публичный интернет?
  4. вопросКогда оправдан Apigee/API Gateway перед backend?
  5. задачаСпроектируйте путь трафика покупателя так, чтобы Cloud SQL не имела публичного IP.
  6. задачаНапишите правила Cloud Armor: блок XSS и rate-limit 100 req/min на IP с баном на 10 минут.
  7. задачаОбъясните, почему правила периметра должны жить в IaC, а не настраиваться вручную в консоли.
Разбор ответов
  1. Cloud Run работает вне VPC. Чтобы достучаться до Cloud SQL по приватному IP (БД без публичного адреса), нужен Serverless VPC Access connector или Direct VPC egress, маршрутизирующий трафик в VPC.
  2. Cloud Armor — WAF/edge-защита на внешнем HTTP(S) LB: пред-настроенные OWASP-правила, гео/IP-листы, rate limiting, DDoS-защита. Срабатывает на периметре Google до того, как трафик дойдёт до backend.
  3. PSC даёт приватную точку доступа к сервису внутри сети Google без маршрута через публичный интернет: трафик не покидает периметр, меньше поверхность атаки и нет зависимости от публичного egress.
  4. Когда нужны квоты, API-ключи внешним партнёрам, версионирование контракта, аналитика и монетизация API. API Gateway — лёгкий случай на OpenAPI; Apigee — полноценный API management.
  5. Единственный публичный вход — Global HTTP(S) LB с managed TLS → Cloud Armor → Cloud Run → Serverless VPC Access → Cloud SQL только с приватным IP. Egress к PSP через Cloud NAT. БД из интернета недостижима.
  6. Политика с правилом evaluatePreconfiguredExpr('xss-stable') → deny-403 и правилом rate-based-ban: threshold 100 за 60 сек, ban 600 сек, привязанная к backend LB.
  7. Ручная настройка не воспроизводима, не проходит ревью и расходится между средами (config drift). В IaC правила версионируются, ревьюятся в PR и применяются одинаково в dev/staging/prod.
