Модуль 2 — Облачный Google подход · Урок 2.1 · SRE

Философия Google Cloud

Канон: Google Cloud Architecture Framework, Google SRE Book.

В модуле 1 мы спроектировали «маркетплейс цифровых работ + лента + платежи» на классическом стеке, где архитектор контролирует каждый слой. Модуль 2 переносит тот же продукт на Google Cloud по той же сетке из девяти кирпичей, но в другой философии: managed-first. Вы платите за то, чтобы не управлять инфраструктурой, и обмениваете контроль на скорость поставки и встроенные SRE-практики. Этот урок задаёт рамку принятия решений на весь модуль.

1. Managed-first и Google Cloud Architecture Framework

Architecture Framework — это пять опор, по которым Google предлагает оценивать любое решение: Operational Excellence, Security/Privacy/Compliance, Reliability, Cost Optimization, Performance Optimization. Managed-first означает, что по умолчанию мы выбираем сервис с наибольшей долей ответственности на стороне провайдера, и спускаемся «ниже» (контейнеры, ВМ) только когда конкретное требование этого требует.

2. SRE: SLO, SLI и error budget как инженерный рычаг

SRE Book формализует надёжность через измеримые величины. SLI — показатель (доля успешных запросов, доля быстрых ответов). SLO — целевое значение SLI за окно. Error budget = 1 − SLO: это разрешённый объём «плохого» поведения, которым команда распоряжается как ресурсом.

SLO доступностиБюджет ошибок / 30 днейПрактический смысл
99%~7 ч 18 минВнутренние/некритичные сервисы
99.9%~43 минAPI маркетплейса (целевой)
99.95%~21 минПлатёжный путь
99.99%~4.3 минДорого; редко оправдано

Пока бюджет не исчерпан — команда катит фичи и рискует. Бюджет исчерпан — релизы замораживаются, приоритет уходит на надёжность. Это инженерный, а не политический механизм: спор «катить или чинить» решается числом, а не должностью.

SLI  = good_events / valid_events
SLO  = 99.9% за 28 дней (rolling)
Бюджет = 0.1% от valid_events
Burn-rate alert: тратим бюджет в 14.4x → страница дежурному

3. TCO: цена владения, а не цена прайс-листа

Прямое сравнение «ВМ за $X против Cloud Run за $Y» обманчиво. TCO включает стоимость людей (patching, дежурства, capacity-планирование), стоимость инцидентов и стоимость упущенного time-to-market. Managed обычно дороже по counterfactual-цене железа, но дешевле суммарно, если учесть FTE на эксплуатацию.

Цена владения. Managed дешевле людей, но дороже железа и привязывает (lock-in). Каждый выбор в этом модуле сопровождается строкой trade-off: стоимость · lock-in · контроль.

Пример использования элементов

Применим рамку к маркетплейсу. Определяем класс надёжности для каждого Bounded Context и фиксируем философию обработки до выбора конкретных сервисов в следующих уроках:

Catalog/API   SLO 99.9%   managed-first → Cloud Run        (трафик скачет)
Payments      SLO 99.95%  managed + строгий контроль доступа
Feed          SLO 99.5%   event-driven, при деградации — отложенно
Media         SLO 99.9%   объектное хранилище + CDN, durability важнее latency
Analytics     best effort error budget не блокирует продуктовые релизы

Решение: фронт каталога и оплата — на serverless с авто-масштабированием до нуля (нет трафика ночью — нет счёта), аналитика — на полностью управляемом хранилище. Контроль отдаём там, где регуляторика и деньги (Payments), скорость берём там, где её ценит продукт (Catalog, Feed).

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧто означает принцип managed-first и когда от него осознанно отступают?
  2. вопросНазовите пять опор Google Cloud Architecture Framework и объясните, зачем их рассматривать вместе.
  3. вопросЧем SLI отличается от SLO, и как из SLO вычисляется error budget?
  4. вопросПочему error budget называют инженерным, а не политическим рычагом?
  5. задачаПосчитайте бюджет ошибок в минутах за 30 дней для SLO 99.9% и 99.95% и объясните, какой назначить платёжному пути.
  6. задачаСравните TCO ВМ и Cloud Run для ночного нулевого трафика каталога: перечислите статьи затрат, которые прайс-лист скрывает.
  7. задачаСоставьте строку trade-off (стоимость·lock-in·контроль) для трёх кирпичей маркетплейса и обоснуйте выбор модели ответственности.
Разбор ответов
  1. По умолчанию выбирается сервис с максимальной долей ответственности на стороне Google (serverless/fully managed). Отступают, когда конкретное требование — латентность, регуляторика, специфичное ПО, предсказуемая цена при стабильной нагрузке — оправдывает дополнительный контроль и эксплуатационные затраты.
  2. Operational Excellence, Security/Privacy/Compliance, Reliability, Cost Optimization, Performance Optimization. Вместе — потому что улучшение одной опоры обычно ухудшает другую (надёжность ↔ стоимость), и решение должно быть осознанным компромиссом, а не локальной оптимизацией.
  3. SLI — измеряемый показатель качества (доля успешных/быстрых запросов). SLO — целевое значение SLI за окно. Error budget = 1 − SLO, выраженный в абсолюте: для 99.9% это 0.1% валидных событий за окно.
  4. Спор «катить фичи или чинить надёжность» решается числом: бюджет не исчерпан — катим, исчерпан — фриз. Решение не зависит от иерархии или убедительности, что снимает политику с инженерного выбора.
  5. 99.9% → ~43.2 мин; 99.95% → ~21.6 мин за 30 дней. Платёжному пути — 99.95% (или строже): отказ оплаты прямо теряет деньги и доверие, более жёсткий бюджет оправдан несмотря на стоимость.
  6. Прайс-лист показывает только vCPU/RAM. Скрыты: FTE на патчинг и дежурства, capacity-планирование, простой при инцидентах, оплата 24/7-инстансов при нулевом ночном трафике (ВМ платится всегда, Cloud Run масштабируется до нуля).
  7. Пример: Catalog API — стоимость низкая при скейле-до-нуля, lock-in средний (контейнер портируем), контроль низкий → serverless. Payments — стоимость средняя, lock-in средний, контроль высокий нужен → managed с жёстким IAM. Media — стоимость по объёму, lock-in низкий (S3-совместимо), контроль низкий → fully managed storage.
