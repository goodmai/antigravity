Блокчейн как backend

Канон: Ethereum dev docs, EIP-1559.

Это децентрализованный аналог кирпича Compute и части State из модулей 1–2. Блокчейн — не «база данных», а детерминированный реплицируемый application-слой с дорогим состоянием и публичным исполнением. Понимание его ограничений — главное в этом уроке.

1. EVM: детерминированная реплицированная машина

EVM исполняет один и тот же код на тысячах нод, и все обязаны прийти к идентичному состоянию. Отсюда жёсткие правила:

  • Детерминизм: запрещены random, реальное время, сетевые вызовы. Источник «случайности» и внешних данных — оракул (урок 3.9).
  • Аккаунты: EOA контролируется приватным ключом; контрактный аккаунт — кодом. У обоих есть баланс и nonce.
  • Газ: каждая операция стоит газа. Запись в storage (SSTORE) — на порядки дороже вычисления.

2. EIP-1559: модель комиссии

Цена транзакции = base fee (рассчитывается протоколом по загрузке блока и сжигается) + priority fee (tip валидатору). Итог: (base + tip) × gasUsed. base fee плавает, поэтому стоимость записи непредсказуема в моменте — это архитектурный фактор, а не деталь.

4. Контракт = публичная неизменяемая бизнес-логика

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Marketplace {
    mapping(uint256 => uint256) public price;   // workId => wei
    mapping(uint256 => address) public owner;   // workId => владелец

    event Purchased(uint256 indexed workId, address indexed buyer);

    function purchase(uint256 workId) external payable {
        require(msg.value == price[workId], "bad price");
        require(owner[workId] == address(0),  "sold");
        owner[workId] = msg.sender;          // состояние = дорогое (SSTORE)
        emit Purchased(workId, msg.sender);  // событие = дешёвый индекс
        // pull-payment автору — отдельной транзакцией (без reentrancy)
    }
}

Пример использования элементов

В маркетплейсе on-chain держим только истину о праве и деньгах: кто владеет работой и факт оплаты. Метаданные, превью, описание — off-chain (уроки 3.4–3.5), иначе каждая карточка стоила бы заметного газа. Покупка: фронт вызывает purchase с msg.value = цена; контракт атомарно меняет владельца и эмитит Purchased. Лента и поиск строятся не из storage, а из событий через индексатор — это дешёвый аналог «БД + индекс». «Оплата завершена» в UI показываем только после финальности блока, иначе реорг может откатить транзакцию.

Артефакт урока. ADR с границей on-chain/off-chain для маркетплейса: что хранится в контракте (право, деньги), что выносится наружу, и обоснование по газу/латентности.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему в смарт-контракте нельзя использовать случайность и текущее время напрямую?
  2. вопросИз чего складывается комиссия по EIP-1559 и что происходит с base fee?
  3. вопросЧем EOA отличается от контрактного аккаунта?
  4. вопросПочему «оплата завершена» в UI нельзя показывать сразу после включения транзакции в блок?
  5. задачаДопишите в контракт pull-payment функцию withdraw() для автора без риска reentrancy.
  6. задачаДля маркетплейса разделите данные на on-chain и off-chain и обоснуйте каждое решение газом.
  7. задачаОцените, во сколько SSTORE обходится хранение поля «описание работы» в storage и предложите альтернативу.
Разбор ответов
  1. EVM детерминирована: все ноды должны воспроизвести идентичное состояние. random/время дали бы расхождение между нодами. Внешние данные и энтропия поступают через оракул.
  2. Комиссия = (base fee + priority fee) × gasUsed. Base fee рассчитывается протоколом по заполненности блоков и сжигается; priority fee — tip валидатору за приоритет.
  3. EOA управляется приватным ключом, не имеет кода. Контрактный аккаунт управляется своим кодом, не имеет приватного ключа; вызывается транзакцией или другим контрактом.
  4. Включённый блок может быть вытеснен при реорге, и транзакция откатится. Финансовый статус показываем только после достаточного числа подтверждений / финализации.
  5. Образец: маппинг balances[author] пополняется при покупке; withdraw() сначала обнуляет баланс (checks-effects), затем делает call с переводом — состояние меняется до внешнего вызова.
  6. On-chain: владелец, цена, факт оплаты (неоспоримость). Off-chain: описание, теги, превью (IPFS), лента (индекс событий) — газ за их хранение не оправдан.
  7. Строка переменной длины — несколько слотов SSTORE по ~20k газа за новый слот; для абзаца это десятки тысяч газа на запись. Альтернатива — хранить CID контента в IPFS, в storage только 32-байтовый указатель.
