Эталонная гибридная архитектура · Capstone

Канон: ADR (Nygard), Google Cloud Architecture Framework, C4 model, OWASP Threat Modeling (STRIDE).

Финал курса сводит три проекции одного домена в одну осознанную гибридную архитектуру. Цель — не «всё на блокчейне» и не «всё в облаке», а защищаемый микс, где каждый из девяти кирпичей размещён там, где его trade-off оптимален для конкретного продукта — маркетплейса цифровых работ.

1. Метод принятия решения по кирпичу

Для каждого кирпича применяем один и тот же протокол вместо вкусовщины:

  1. Свойство, которое продукт реально требует (не «модно», а нужно): сильная согласованность? цензуроустойчивость? минимальная латентность? суверенитет данных?
  2. Шесть осей trade-off для каждого кандидата: стоимость, латентность, доверие (кому приходится доверять), суверенитет данных, операционная сложность, vendor lock-in.
  3. Граница применимости: при каком объёме/SLA/бюджете выбор перестаёт работать.
  4. ADR: решение фиксируется как Architecture Decision Record (контекст → варианты → решение → последствия).
Принцип. Децентрализуем то, где ценность — отсутствие посредника и доверия (право собственности, деньги, неизменяемость). Централизуем то, где ценность — латентность, цена и UX (поиск, лента, медиа hot-path).

3. Эталонная гибридная архитектура (C4 Container)

Сведение в одну Container-диаграмму (Structurizr DSL — артефакт capstone):

workspace {
  model {
    user   = person "Пользователь (кошелёк)"
    market = softwareSystem "Маркетплейс цифровых работ" {
      spa    = container "SPA"            "React"        "web"
      api    = container "API/BFF"        "Cloud Run"    "hot-path: каталог, лента"
      db     = container "PostgreSQL"     "Cloud SQL"    "истина каталога (off-chain)"
      graph  = container "Indexer"        "The Graph"    "проекция on-chain событий"
      chain  = container "Контракты"      "EVM L2"       "право собственности, оплата"
      ipfs   = container "Хранилище"      "IPFS/Arweave" "файлы работ (CID)"
    }
    user -> spa  "SIWE-вход, покупка"
    spa  -> api  "чтение каталога/ленты"
    api  -> db   "запросы (низкая латентность)"
    api  -> graph "история владения"
    spa  -> chain "purchase() — подпись кошельком"
    chain -> graph "events → индекс"
    spa  -> ipfs "получение файла по CID"
  }
  views { container market { include * autolayout lr } }
}

Ключевая идея: деньги и право собственности идут on-chain (нет посредника), а чтение каталога и ленты — через классический API + индексатор (низкая латентность, нулевой газ). Файлы — контент-адресуемы (CID в контракте), доставка — через CDN-кэш поверх IPFS-шлюза.

Пример использования элементов: защита capstone

Сценарий «покупатель приобретает работу» проходит сквозь гибрид так:

  1. Вход — SIWE (кирпич Identity, урок 3.7): подпись кошельком, без пароля и кастодиана.
  2. Просмотр каталога — классический API + PostgreSQL (уроки 1.4–1.5, 2.3): десятки мс, нулевой газ.
  3. Покупка — транзакция purchase() в EVM-контракте (уроки 3.3–3.4): право собственности фиксируется без посредника.
  4. Событие Purchased индексируется The Graph (урок 3.11) → лента обновляется через обычный GraphQL-запрос.
  5. Файл выдаётся по CID из IPFS через CDN-кэш (уроки 3.5–3.6): иммутабельно и дёшево.

Каждый шаг — это один кирпич, размещённый по матрице §2, с зафиксированным ADR и обоснованием через шесть осей trade-off.

Критерий защиты capstone

  1. Матрица 9×3 с trade-off по шести осям (цена · латентность · доверие · суверенитет · опер. сложность · lock-in) и колонкой «граница применимости».
  2. C4 Context + Container гибрида (Structurizr/PlantUML).
  3. Threat-model (STRIDE) гибрида и письменное обоснование «что централизовать / отдать Google / децентрализовать» — с цифрами по стоимости, латентности и суверенитету.
  4. Набор ADR-01…05 по спорным решениям (декомпозиция, consistency, runtime, compute, ключи).
Артефакт урока. Capstone: матрица 9×3 + C4 гибрида (Context+Container) + ADR-набор (01–05) + threat-model STRIDE.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросСформулируйте принцип, по которому кирпич идёт on-chain, а не в классику/облако. Приведите два примера из матрицы.
  2. вопросПочему каталог и лента в гибриде читаются через классический API + индексатор, а не напрямую с цепочки?
  3. вопросКакие шесть осей trade-off обязательны в матрице 9×3 и почему «граница применимости» — отдельная важная колонка?
  4. вопросВ threat-model: почему подмена файла работы невозможна, если в контракте хранится только CID?
  5. задачаЗаполните полную матрицу 9×3 для маркетплейса: по каждому кирпичу — оценка трёх парадигм, гибридное решение и ведущий trade-off.
  6. задачаНарисуйте C4 Container-диаграмму гибрида (Structurizr DSL) и отметьте, какой путь идёт on-chain, а какой — классикой; обоснуйте каждую стрелку одной осью trade-off.
  7. задачаСоставьте threat-model STRIDE гибрида (≥6 угроз) и оформите ADR на самое спорное решение (например, SIWE как корень идентичности vs OIDC) по шаблону Nygard.
Разбор ответов
  1. Децентрализуем, когда ценность — отсутствие посредника и доверия: право собственности на работу и оплата идут on-chain (никто не может переписать владельца или отменить платёж). Централизуем, когда ценность — латентность/цена/UX: каталог и лента в PostgreSQL + Cloud Run.
  2. Чтение напрямую с цепочки дорогое и медленное (RPC-латентность, отсутствие сложных запросов, нет полнотекстового поиска). Истина прав остаётся on-chain, а проекция для чтения строится индексатором (The Graph) и классической БД — нулевой газ, десятки мс, богатые запросы.
  3. Стоимость, латентность, доверие, суверенитет данных, операционная сложность, vendor lock-in. «Граница применимости» отвечает на вопрос «при каком объёме/SLA/бюджете выбор ломается» — без неё рекомендация выглядит абсолютной, хотя любая верна лишь в диапазоне.
  4. CID — это криптографический хэш содержимого: любое изменение файла меняет CID. Контракт хранит CID, поэтому подменить файл, не сломав ссылку, невозможно — клиент проверяет, что полученный контент хэшируется в записанный в контракте CID.
  5. Критерий приёмки: 9 строк × (классика/Google/децентр. оценка + гибрид + ведущий trade-off + граница применимости); решения совпадают с логикой §1–§2 и подкреплены цифрами.
  6. Критерий: диаграмма уровня Container, видно разделение on-chain (purchase, events) и off-chain (каталог, лента, медиа hot-path); каждая связь подписана и обоснована одной осью trade-off.
  7. Критерий: ≥6 угроз STRIDE с контрмерами, привязанными к конкретным кирпичам; ADR содержит контекст, рассмотренные варианты, решение и последствия (в т.ч. негативные) — а не только итог.
