Состояние: on-chain vs off-chain

Канон: The Graph docs, Ethereum dev docs.

Это децентрализованный аналог кирпича State/Data. Главный архитектурный вопрос: что положить в дорогое on-chain storage, а что вынести. Правило: on-chain — только истина прав и денег, всё остальное — off-chain, читается через индекс событий.

1. Цена storage в газе

Запись нового слота storage (SSTORE с нуля) стоит порядка 20 000 газа за 32 байта. Хранение строки описания работы — десятки тысяч газа на каждую запись. Для каталога из тысяч карточек это экономически невозможно. Поэтому on-chain держим минимум: owner, price, факт оплаты — то, чему нужна неоспоримость.

2. Events/logs как дешёвый индекс

Записать event на порядок дешевле, чем storage, и события не входят в state-trie (их нельзя прочитать из контракта, только индексировать снаружи). Это и есть децентрализованный аналог пары «write-ahead log + read-replica»: контракт эмитит событие, индексатор строит проекцию для чтения.

Пример использования элементов

Контракт при покупке эмитит Purchased(workId, buyer). Субграф индексирует это событие и отдаёт ленту по GraphQL за миллисекунды — фронт никогда не читает storage напрямую для списков.

# schema.graphql субграфа
type Purchase @entity {
  id: ID!            # txHash-logIndex
  workId: BigInt!
  buyer: Bytes!
  blockTime: BigInt!
}
type Work @entity {
  id: ID!            # workId
  owner: Bytes!
  cid: String!       # указатель на метаданные в IPFS
  sales: [Purchase!]! @derivedFrom(field: "workId")
}
query Лента {
  purchases(first: 20, orderBy: blockTime, orderDirection: desc) {
    workId  buyer  blockTime
  }
}

Истина о владении — в контракте; читаемая лента — в субграфе; контент — в IPFS по CID. Три слоя, каждый по своей цене.

Артефакт урока. Data-схема on-chain/off-chain маркетплейса + subgraph schema.graphql для ленты с обоснованием границы по газу и латентности.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему описание работы нельзя хранить в storage контракта?
  2. вопросЧем event отличается от storage по цене и по доступности из контракта?
  3. вопросЧто индексирует The Graph и почему фронт не читает списки прямо из цепи?
  4. вопросГде в схеме «on-chain + субграф» остаётся точка доверия помимо самой цепи?
  5. задачаРазнесите 6 полей карточки работы по on-chain / IPFS / субграф и обоснуйте.
  6. задачаНапишите schema.graphql для ленты подписок (кто на кого подписан + последние покупки).
  7. задачаОпишите, как обработать лаг индексатора, чтобы UI не показывал устаревшую ленту как актуальную.
Разбор ответов
  1. Строка переменной длины занимает несколько слотов SSTORE по ~20k газа; для каталога это экономически невозможно. Описание выносим в IPFS, в storage кладём только CID-указатель.
  2. Event на порядок дешевле SSTORE и не входит в state-trie — его нельзя прочитать из контракта, только индексировать снаружи. Storage дорог, но читаем on-chain.
  3. The Graph индексирует события контракта в проекцию и отдаёт её по GraphQL за миллисекунды. Чтение списков из цепи было бы медленным и не поддерживало бы фильтры/сортировки.
  4. Доверие к Indexer/субграфу: он может отстать или отдать неактуальные данные. Сама цепь неоспорима, но индекс — производная, требующая мониторинга свежести.
  5. Образец: owner и price — on-chain; title, description, tags, previewImage — IPFS (CID on-chain); агрегат «продаж за неделю» — субграф.
  6. Образец: сущности Follow{follower, followee} и Purchase, плюс производное поле ленты через @derivedFrom по адресу подписки.
  7. Хранить номер последнего индексированного блока субграфа, сравнивать с головой цепи; при отставании показывать индикатор «лента обновляется», а финансовые статусы подтверждать только из цепи.
