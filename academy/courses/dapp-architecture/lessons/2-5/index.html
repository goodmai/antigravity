Хранилище и доставка

Канон: Cloud Storage classes, Cloud CDN docs, Media CDN docs.

Кирпич Storage/Media отвечает на вопрос «где лежат файлы и как они доставляются?». Паттерн тот же, что в классике (объектное хранилище + подписанный доступ + CDN), но управляемый и интегрированный с IAM. Для маркетплейса это файлы работ: их нужно дёшево хранить, безопасно отдавать только покупателю и быстро раздавать через периметр.

1. Классы хранения и lifecycle

Cloud Storage — один API, четыре класса с разной ценой хранения/извлечения и минимальным сроком. Стоимость оптимизируется автоматически через lifecycle policy или Autoclass, который сам переводит редко используемые объекты в холодные классы.

КлассДоступМин. срокЦена храненияЦена извлечения
StandardЧастый, горячий—ВысокаяНет
Nearline~раз в месяц30 днейНижеЕсть
Coldline~раз в квартал90 днейЕщё нижеВыше
ArchiveРаз в год / комплаенс365 днейМинимальнаяВысокая

Trade-off: холодные классы дешевле в хранении, но дороже и медленнее в извлечении плюс штраф за раннее удаление. Ошибка — класть туда часто читаемые файлы.

2. Приватная доставка: signed URL и signed cookies

Бакет с файлами работ закрыт от публичного доступа. Доступ выдаётся точечно: signed URL — одна подписанная ссылка с TTL на один объект (скачивание купленной работы); signed cookies — подписанная кука, открывающая доступ к группе ресурсов на время (галерея превью, HLS-сегменты видео). Подпись делается ключом сервис-аккаунта или через ключи Cloud CDN.

Правило периметра. Объект никогда не публичный. Право на скачивание = бизнес-проверка «оплачено» → выдача краткоживущего signed URL, а не постоянная ссылка.

3. Cloud CDN и Media CDN

Cloud CDN кэширует ответы origin (бакет или backend) на периметре Google — статика, изображения, документы. Media CDN — отдельный продукт под крупномасштабный видео-стриминг (HLS/DASH) с большей пропускной способностью. Для маркетплейса: картинки/архивы работ — Cloud CDN; видеопревью и видеоработы — Media CDN с подписанными запросами.

Пример использования элементов

Покупатель оплатил работу. Backend проверяет факт оплаты в Cloud SQL и выдаёт signed URL c TTL 10 минут — ссылку нельзя переслать «навсегда»:

# bucket приватный, доступ только сервис-аккаунту
gsutil iam ch serviceAccount:api@PROJECT.iam.gserviceaccount.com:roles/storage.objectViewer \
  gs://market-works
# lifecycle: горячее → Nearline через 30д, Archive через 365д
gsutil lifecycle set lifecycle.json gs://market-works
// выдача ссылки только после проверки оплаты
if (!(await order.isPaid(userId, workId))) throw forbidden();
const [url] = await storage.bucket('market-works')
  .file(`works/${workId}.zip`)
  .getSignedUrl({ action: 'read', expires: Date.now() + 10*60*1000 });
return { downloadUrl: url };  // TTL 10 мин, одноразово по смыслу

Решение: оригиналы работ — Standard с lifecycle в Nearline/Archive (старые непопулярные работы дешевеют автоматически); превью раздаются через Cloud CDN; видеоработы — Media CDN с signed cookies на сессию просмотра. Lock-in низкий: API S3-совместимо концептуально, миграция данных стандартна.

Артефакт урока. Спецификация хранилища маркетплейса: бакеты и их классы, lifecycle-правила (Standard→Nearline→Archive), схема приватной доставки (signed URL для скачивания, signed cookies для видео) и выбор Cloud CDN vs Media CDN.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем отличаются классы Standard, Nearline, Coldline, Archive и какой главный риск неверного выбора?
  2. вопросВ чём разница между signed URL и signed cookies и когда применять каждый?
  3. вопросЗачем нужна lifecycle policy и что делает Autoclass?
  4. вопросКогда брать Media CDN вместо Cloud CDN?
  5. задачаСпроектируйте доставку купленной работы так, чтобы ссылка не работала «навсегда» и не утекала.
  6. задачаОпишите lifecycle-правила для файлов работ маркетплейса с обоснованием сроков переходов.
  7. задачаОбъясните строкой trade-off (стоимость·lock-in·контроль) выбор Cloud Storage + Cloud CDN для медиа маркетплейса.
Разбор ответов
  1. Чем холоднее класс, тем дешевле хранение, но дороже/медленнее извлечение и больше минимальный срок (штраф за раннее удаление). Главный риск — положить часто читаемые файлы в Coldline/Archive: суммарно дороже из-за платы за извлечение.
  2. Signed URL — подписанная ссылка с TTL на один объект (скачивание одной работы). Signed cookies — подписанная кука на доступ к набору ресурсов на время (галерея превью, сегменты видео). URL — точечно, cookies — для множества связанных запросов.
  3. Lifecycle автоматически переводит объекты между классами или удаляет их по возрасту/условиям, оптимизируя стоимость. Autoclass делает это адаптивно по фактическому паттерну доступа без ручных правил.
  4. При крупномасштабном видео-стриминге (HLS/DASH) с высокой пропускной способностью и требованиями к доставке медиа: Media CDN специализирован под это, Cloud CDN — под общую веб-статику и API-ответы.
  5. Бакет приватный; backend проверяет факт оплаты в Cloud SQL и только тогда выдаёт signed URL с коротким TTL (например, 10 мин). По истечении ссылка мертва; постоянных публичных URL нет.
  6. Standard для свежих/популярных работ; переход в Nearline после ~30 дней низкой активности; Archive после ~365 дней для комплаенс-хранения. Сроки кратны минимальным срокам классов, чтобы не платить штраф за раннее удаление.
  7. Стоимость: оплата по объёму + lifecycle снижает её автоматически. Lock-in: низкий — объектная модель и миграция данных стандартны. Контроль: низкий, но durability и периметр обеспечивает Google; для медиа этот размен выгоден.
