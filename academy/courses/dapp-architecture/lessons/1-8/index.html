Идентичность и доступ

Канон: OAuth 2.1 draft, OIDC Core, OWASP ASVS.

Аутентификация отвечает «кто ты» (OIDC), авторизация — «что тебе можно» (OAuth scopes + RBAC/ABAC). Их нельзя смешивать: валидный токен не равен «можно делать что угодно». Этот урок — про сессии vs JWT, Authorization Code + PKCE, ротацию refresh-токенов и модели доступа.

1. Сессия vs JWT

Серверная сессияJWT
Отзывмгновенный (удалить из стора)сложный (нужен denylist / короткий TTL)
Состояниев сторе (Redis/БД)stateless, проверяется подписью
Размерcookie-id (мало)токен растёт с claims
Масштаб проверкичтение стора на запрослокальная проверка подписи

Практичный гибрид: короткоживущий access-JWT (минуты, без обращения к стору) + серверная запись о refresh-токене (мгновенный отзыв сессии). Так берём масштаб JWT и управляемость сессии.

2. OAuth 2.1: Authorization Code + PKCE

OAuth 2.1 убирает небезопасные потоки (implicit, password grant). Единственный рекомендуемый для приложений — Authorization Code, и PKCE обязателен для всех клиентов, не только публичных. PKCE защищает от перехвата authorization code: атакующий без code_verifier не обменяет код на токен.

app → /authorize?code_challenge=S256(verifier)&... → IdP
IdP → (логин/согласие) → redirect ?code=... → app
app → POST /token (code + code_verifier) → access(JWT, мин) + refresh
refresh rotation: каждый /token по refresh выдаёт НОВЫЙ refresh,
                  старый немедленно аннулируется (reuse → отзыв всей цепочки)
Refresh-token rotation. Повторное предъявление уже использованного refresh — признак кражи. Реакция: аннулировать всю цепочку токенов пользователя. Без ротации утёкший refresh живёт месяцами незаметно.

3. RBAC и ABAC

RBAC — доступ по роли (просто, грубо, легко аудировать). ABAC — по атрибутам субъекта/ресурса/контекста (гибко, сложнее аудит). Распространённая ошибка — клиентская авторизация: скрыли кнопку в UI, но эндпоинт открыт. Авторизация всегда серверная, по идентичности из токена, а не из тела запроса.

RBAC vs ABAC. RBAC — роли (просто, грубо). ABAC — атрибуты (гибко, сложнее аудит). Для маркетплейса: RBAC на админку, ABAC на «автор видит только свои выплаты».

Пример использования элементов

Маркетплейс: SPA-клиент, IdP (OIDC), API ядра. Поток входа и авторизация выдачи payout-отчёта автора.

@startuml
actor User
participant SPA
participant IdP
participant API

== Аутентификация (Authorization Code + PKCE) ==
SPA -> SPA : verifier=rnd; challenge=S256(verifier)
SPA -> IdP : /authorize?code_challenge=challenge&response_type=code
IdP -> User : логин + согласие
IdP --> SPA : redirect ?code
SPA -> IdP : POST /token (code + verifier)
IdP --> SPA : access(JWT,5m, sub, roles) + refresh
== Авторизация запроса ==
SPA -> API : GET /authors/{id}/payouts  (Bearer access)
API -> API : verify JWT (подпись, exp, aud)
API -> API : ABAC: token.sub == {id} ? allow : 403
API --> SPA : payout-отчёт ТОЛЬКО своего автора
== Ротация ==
SPA -> IdP : POST /token (refresh)
IdP --> SPA : НОВЫЙ access + НОВЫЙ refresh (старый refresh аннулирован)
@enduml

Разбор: пароль вводится только на IdP, API его не видит (OIDC). API доверяет лишь подписанному JWT и проверяет exp/aud. Доступ к payout — ABAC-правило «сам себе»: даже валидный токен другого автора получит 403, потому что решение принимается по token.sub, а не по {id} из URL (клиенту не верим). Refresh-ротация обнуляет украденный токен при первом же reuse. Админка маркетплейса — отдельно, через RBAC-роль admin.

Артефакт урока. Диаграмма auth-потока (Authorization Code + PKCE + refresh rotation).

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем отличаются аутентификация и авторизация и почему валидный токен ≠ «можно всё»?
  2. вопросСравните серверную сессию и JWT по отзыву, состоянию и масштабу; что даёт гибрид?
  3. вопросЗачем нужен PKCE и от какой атаки он защищает в Authorization Code flow?
  4. вопросЧто такое refresh-token rotation и как система реагирует на reuse уже использованного refresh?
  5. задачаПостройте диаграмму auth-потока SPA↔IdP↔API: Authorization Code + PKCE + ротация refresh.
  6. задачаСпроектируйте правило доступа к GET /authors/{id}/payouts: RBAC или ABAC и почему.
  7. задачаНайдите ошибку: кнопка payout скрыта в UI, но эндпоинт открыт — как должно быть и где проверка.
Разбор ответов
  1. Аутентификация устанавливает личность (кто ты, OIDC), авторизация — права (что можно, scopes/RBAC/ABAC). Токен лишь доказывает личность; доступ к конкретному ресурсу — отдельное решение по политике.
  2. Сессия: мгновенный отзыв, состояние в сторе, чтение на запрос. JWT: stateless, локальная проверка подписи, отзыв труден. Гибрид — короткий access-JWT + серверная запись refresh — даёт и масштаб, и управляемый отзыв.
  3. PKCE связывает запрос /authorize с обменом /token через verifier/challenge. Защищает от перехвата authorization code: без code_verifier украденный код не обменять на токен. В OAuth 2.1 обязателен для всех клиентов.
  4. Каждый обмен по refresh выдаёт новый refresh, старый сразу аннулируется. Повторное использование старого = признак кражи → аннулировать всю цепочку токенов пользователя.
  5. Критерий: SPA генерирует verifier/challenge, /authorize → code, /token с verifier → access(JWT,короткий)+refresh, API проверяет подпись, ротация выдаёт новую пару и гасит старый refresh.
  6. ABAC: правило «token.sub == {id}», т.к. доступ зависит от атрибута связи субъект↔ресурс, а не от роли. RBAC здесь дал бы слишком грубо («любой автор»).
  7. Ошибка: авторизация на клиенте. Эндпоинт должен сам проверять token.sub против запрашиваемого автора и роль; скрытие кнопки — лишь UX. Проверка — на сервере, до выдачи данных, по идентичности из токена.
