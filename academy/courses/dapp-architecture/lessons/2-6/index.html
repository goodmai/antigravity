Identity на Google Cloud

Канон: Cloud IAM overview, Workload Identity Federation, Identity Platform.

Кирпич Identity отвечает на вопросы «кто пользователь?» и «что сервису можно?». На Google Cloud это два разных IAM, которые нельзя путать: аутентификация конечных пользователей продукта (Identity Platform / Firebase Auth) и авторизация ворклоадов между сервисами (Cloud IAM роли + service accounts).

1. Два разных IAM

АспектПользователи продуктаСервисы/ворклоады
СервисIdentity Platform / Firebase AuthCloud IAM
СубъектПокупатель, авторService account, ворклоад
ТокенFirebase ID token (JWT)Google OAuth/OIDC, IAM
ВопросКто залогинен и его роль в продуктеИмеет ли сервис право на ресурс

Покупатель аутентифицируется в Firebase Auth и получает ID token; backend верифицирует его и применяет продуктовые роли (buyer/author). Право Cloud Run читать Cloud SQL — это уже Cloud IAM, не Firebase.

2. Принцип наименьших привилегий в Cloud IAM

IAM-политика = (member → role → resource). Антипаттерн — roles/editor на проект «чтобы работало». Правильно: отдельный service account на сервис с предопределёнными узкими ролями только на нужные ресурсы.

# SA для payments-сервиса: только нужное
gcloud iam service-accounts create payments-sa
gcloud projects add-iam-policy-binding PROJECT \
  --member="serviceAccount:payments-sa@PROJECT.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"
gcloud secrets add-iam-policy-binding psp-api-key \
  --member="serviceAccount:payments-sa@PROJECT.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

Trade-off: больше SA и биндингов — больше операционной работы, но радиус поражения при компрометации одного сервиса минимален.

3. Workload Identity Federation

Главный принцип безопасности модуля: никаких долгоживущих JSON-ключей service account. WIF позволяет внешнему ворклоаду (GitHub Actions, другое облако) обменять свой OIDC-токен на краткоживущий GCP-токен через STS — без хранимого секрета. Скомпрометировать нечего: секрета не существует.

GitHub Actions (OIDC id-token) ─▶ STS token exchange
   ─▶ временный access token GCP (минуты) ─▶ deploy
   (нет JSON-ключа в репозитории/секретах)

Пример использования элементов

Auth-поток маркетплейса разделён на пользовательский и сервисный контуры:

// 1. Пользователь: Firebase Auth → ID token → backend верифицирует
const decoded = await admin.auth().verifyIdToken(idToken);
const uid = decoded.uid;                 // кто
const role = await profile.roleOf(uid);  // buyer | author (продуктовая роль)
if (action === 'publishWork' && role !== 'author') throw forbidden();
// 2. Сервис: Cloud Run → Cloud SQL через привязанный SA, без ключа
//    payments-sa имеет только roles/cloudsql.client + secretAccessor
// 3. CI: GitHub → WIF → деплой, без service-account JSON

Решение: конечные пользователи живут в Firebase Auth (Identity Bounded Context из урока 1.1 сохранён — связь по uid). Каждый сервис маркетплейса получает свой SA с минимальными ролями. CI деплоит через WIF. Lock-in Firebase Auth средний (стандартные OIDC-провайдеры, экспортируемые пользователи), но устраняет долгоживущие секреты.

Артефакт урока. Auth-поток на GCP: диаграмма «пользователь → Firebase Auth → backend (продуктовые роли)» + «сервис → SA с минимальными ролями» + «CI → WIF без ключа», с таблицей service account → роли → ресурсы.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем Identity Platform/Firebase Auth отличается от Cloud IAM по назначению?
  2. вопросЧто такое принцип наименьших привилегий и почему roles/editor на проект — антипаттерн?
  3. вопросКак Workload Identity Federation устраняет долгоживущие service-account ключи?
  4. вопросПочему продуктовая роль (author/buyer) не должна быть Cloud IAM-ролью?
  5. задачаОпишите политики IAM для payments-сервиса по принципу least privilege.
  6. задачаСпроектируйте auth-поток публикации работы автором: от Firebase ID token до проверки роли в backend.
  7. задачаНастройте CI деплой через WIF и объясните, почему в репозитории нет ни одного секрета GCP.
Разбор ответов
  1. Firebase Auth/Identity Platform аутентифицирует конечных пользователей продукта и выдаёт ID token. Cloud IAM авторизует ворклоады/принципалов на ресурсы Google Cloud. Разные субъекты, токены и вопросы.
  2. Least privilege — давать ровно те права, что нужны, и не больше. roles/editor на проект даёт почти всё: компрометация одного сервиса = компрометация всего проекта; радиус поражения максимален.
  3. Внешний ворклоад предъявляет свой OIDC-токен, STS обменивает его на краткоживущий GCP-токен. Постоянного JSON-ключа не существует, поэтому его нельзя украсть или забыть ротировать.
  4. Author/buyer — состояние предметной области (Bounded Context Identity), а не право на облачный ресурс. Смешивание привязало бы продуктовую логику к Cloud IAM и нарушило границу контекста.
  5. Отдельный SA payments-sa; роли только roles/cloudsql.client на нужный инстанс и roles/secretmanager.secretAccessor на конкретный секрет PSP. Ни проектного editor, ни лишних ресурсов.
  6. Клиент логинится в Firebase → ID token; backend verifyIdToken → uid; по uid читается продуктовая роль; если роль не author — 403; иначе публикация. Cloud IAM здесь не участвует.
  7. В GitHub настраивается OIDC-провайдер и WIF-пул; workflow получает id-token, STS меняет его на временный GCP-токен. JSON-ключа SA нет — красть/ротировать нечего, утечка секрета невозможна.
