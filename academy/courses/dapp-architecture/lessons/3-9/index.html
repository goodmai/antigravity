Оракулы и внешний мир

Канон: Chainlink docs, Ethereum dev docs.

Это децентрализованный аналог кирпича «интеграции и внешние функции». Блокчейн детерминирован и изолирован — он не может сам сходить в API или запустить задачу по расписанию. Оракул — мост к внешнему миру и одновременно главная точка доверия dApp.

1. Oracle problem

Смарт-контракт безопасен ровно настолько, насколько достоверны данные, которые он принимает. Если цену доллара подаёт один API — атакующий, скомпрометировав этот API, ломает контракт, не трогая блокчейн. Поэтому доверенный фид должен быть децентрализован: много независимых нод, агрегация, экономические штрафы за ложь.

2. Data feeds и keepers/automation

  • Data feed — агрегированный on-chain фид (например, курс фиата для цены работы в стейблкоине). Контракт читает значение, не делая сетевых вызовов.
  • Keepers / Automation — децентрализованный аналог cron: ноды следят за условием и шлют транзакцию-триггер (выплата автору, закрытие аукциона), так как контракт сам себя по времени не запустит.

3. Trade-off против бэкенд-интеграции из модулей 1–2

СвойствоБэкенд + cron + внешний API (М1–2)Оракул + automation (М3)
СтоимостьИнфра бэкендаПлата оракулу + газ триггера

Пример использования элементов

В маркетплейсе цена работы задана в USD, оплата — в волатильном токене. Контракт читает price feed для пересчёта, а не доверяет числу из фронта. Автовыплата автору после периода удержания запускается keeper'ом, а не нашим cron.

function priceInToken(uint256 usdCents) public view returns (uint256) {
    (, int256 answer,,,) = priceFeed.latestRoundData(); // децентрализ. фид
    require(answer > 0, "stale feed");
    return (usdCents * 1e8) / uint256(answer);
}
// keeper: checkUpkeep() == true когда holdPeriod истёк → performUpkeep() платит автору

Доверие вынесено из нашего бэкенда в отдельную экономическую систему — это и есть смысл децентрализованного оракула.

Граница применимости. Оракул не устраняет доверие — он его перераспределяет и делает аудируемым. Один API быстрее и дешевле; децентрализованный фид дороже и медленнее, но устойчив к компрометации одной стороны.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему смарт-контракт не может сам сходить во внешний API?
  2. вопросВ чём суть oracle problem и почему один API — плохой источник цены?
  3. вопросЗачем нужны keepers/automation, если есть событие покупки?
  4. вопросОракул «убирает» доверие или перераспределяет его? Обоснуйте.
  5. задачаСпроектируйте пересчёт цены работы из USD в токен через price feed с защитой от устаревшего значения.
  6. задачаОпишите автовыплату автору после периода удержания через keeper: условие checkUpkeep и действие.
  7. задачаСравните «один API» и «децентрализованный фид» по доверию, латентности и стоимости в таблице.
Разбор ответов
  1. EVM детерминирована: все ноды должны воспроизвести одинаковый результат. Сетевой вызов недетерминирован и сломал бы консенсус, поэтому внешние данные приходят только через оракул-транзакцию.
  2. Контракт безопасен лишь настолько, насколько достоверен его вход. Один API — единая точка компрометации: подделав его, атакующий ломает контракт. Нужна децентрализованная агрегация независимых нод.
  3. Контракт не исполняется «по времени» сам; событие покупки не запускает отложенную выплату. Keeper следит за условием (истёк период) и шлёт транзакцию-триггер.
  4. Перераспределяет: доверие переходит от нашего бэкенда к децентрализованной сети с агрегацией и экономическими штрафами, и становится публично аудируемым, но не исчезает.
  5. Читать latestRoundData(), проверять, что answer > 0 и updatedAt не старше порога (stale check), и только потом пересчитывать; иначе откатывать транзакцию.
  6. checkUpkeep возвращает true, когда block.timestamp ≥ purchaseTime + holdPeriod и выплата не сделана; performUpkeep переводит средства автору и помечает выплату завершённой.
  7. Один API: доверие к одной стороне, низкая латентность, дёшево. Децентрализованный фид: доверие к сети с агрегацией, выше латентность и стоимость, но устойчив к компрометации одного источника.
