Безопасность и поставка

Канон: OWASP ASVS, OWASP Top 10, SLSA, OWASP: Threat Modeling (STRIDE).

Безопасность — не финальный этап, а свойство архитектуры: её проектируют вместе с системой, а не «навешивают» перед релизом. Этот урок замыкает модуль: базовые требования ASVS, управление секретами, безопасный pipeline (CI/CD + IaC + SLSA) и threat-модель классической схемы по STRIDE. Артефакт — C4 Container-диаграмма «классики».

1. Базовые требования (ASVS-минимум)

  • Секреты — в секрет-менеджере (Vault/KMS/SM), не в env-файле в репозитории и не в образе. Ротация по расписанию.
  • Весь внешний трафик — TLS; внутренний — mTLS, где возможно.
  • Валидация ввода на границе; параметризованные запросы (нет SQLi); authz на сервере по идентичности из токена (урок 1.8).
  • Принцип наименьших привилегий: узкие IAM-роли на каждый сервис.
  • CI/CD: SAST + SCA (зависимости) + image-scan + secret-scan — как обязательный гейт мерджа, не «по желанию».

2. Управление секретами и цепочка поставки

Главная ошибка — секрет в git. Он остаётся в истории навсегда, даже после удаления файла. Правильно: приложение получает секрет в рантайме из менеджера по своей IAM-идентичности; в репозитории — только ссылка на имя секрета. Поставка защищается SLSA: воспроизводимая сборка, provenance (откуда артефакт), подпись образа, запрет деплоя неподписанного.

Этап pipelineКонтрольЧто ловит
commitsecret-scan, pre-commitключи/токены в коде
buildSAST, SCAуязвимый код и зависимости

# GitHub Actions: безопасность как гейт мерджа
jobs:
  security-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Secret scan
        uses: gitleaks/gitleaks-action@v2     # ключи в истории/диффе
      - name: SCA (dependencies)
        run: npm audit --audit-level=high      # уязвимые пакеты
      - name: SAST
        uses: github/codeql-action/analyze@v3  # инъекции, небезопасный код
      - name: Image scan
        run: trivy image --exit-code 1 --severity HIGH,CRITICAL app:${{ github.sha }}
    # ветка main защищена: merge запрещён без зелёного security-gate

3. Threat-model по STRIDE

STRIDE — систематический разбор угроз по шести категориям. Моделируют по потокам данных C4-диаграммы: каждая стрелка через границу доверия — кандидат на угрозу.

УгрозаПример в маркетплейсеКонтрмера
Spoofingподделка автора работыOIDC + подпись сессии (урок 1.8)
Tamperingправка суммы платежа в запросесерверная цена из каталога (урок 1.2)
Repudiation«я не покупал»аудит-лог с trace_id (урок 1.9)

Elevation of privilegeпокупатель → adminRBAC на сервере, least privilege

Пример использования элементов

Сводим весь модуль в одну C4 Container-диаграмму «классики» и накладываем границы доверия для STRIDE.

workspace {
  model {
    buyer  = person "Покупатель"
    author = person "Автор"
    market = softwareSystem "Маркетплейс" {
      spa     = container "SPA"            "React"     "недоверенная зона"
      api     = container "Core API"       "Node"      "граница доверия"
      db      = container "PostgreSQL"     "истина"
      cache   = container "Redis"          "ускоритель"
      bus     = container "Kafka"          "события + outbox"
      media   = container "Object Storage" "S3, presigned"
      cdn     = container "CDN"            "доставка медиа"
    }
    idp = softwareSystem "IdP (OIDC)" "Внешняя система"
    psp = softwareSystem "PSP"        "Внешняя система"

    buyer  -> spa "HTTPS"
    author -> spa "HTTPS"
    spa    -> api "HTTPS + Bearer JWT"      # граница доверия #1
    spa    -> idp "Auth Code + PKCE"
    api    -> db    "SQL (params, TLS)"
    api    -> cache "read-through, TLS"
    api    -> bus   "outbox → publish"
    api    -> media "presigned URL"          # граница доверия #2
    api    -> psp   "charge (mTLS, secret из SM)"  # граница доверия #3
    spa    -> cdn   "медиа"
  }
  views { container market { include * autolayout lr } }
}

Разбор: три помеченные границы доверия — это точки приложения STRIDE. Граница #1 (SPA→API): Spoofing/Tampering → JWT-проверка + серверная цена. #2 (API→Storage): Information disclosure → короткоживущие presigned URL и серверная authz. #3 (API→PSP): секрет PSP только из секрет-менеджера, mTLS, идемпотентный ключ против повторной charge. Диаграмма — это и есть карта, по которой строилась STRIDE-таблица: безопасность выведена из архитектуры, а не добавлена сверху.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему секрет в git опасен даже после удаления файла и как приложение должно получать секреты?
  2. вопросЧто даёт SLSA и зачем подписывать артефакт и запрещать деплой неподписанного образа?
  3. вопросЧто такое граница доверия и почему STRIDE применяют именно к потокам через неё?
  4. вопросПочему security-проверки делают обязательным гейтом мерджа, а не отдельным ночным прогоном?
  5. задачаПостройте C4 Container-диаграмму маркетплейса с явными границами доверия.
  6. задачаСоставьте STRIDE-таблицу: по одной угрозе каждой категории с контрмерой из изученных уроков.
  7. задачаОпишите CI-гейт: какие шаги (secret-scan/SAST/SCA/image-scan) на каком этапе и что каждый ловит.
Разбор ответов
  1. Git хранит историю: секрет остаётся в прошлых коммитах и форках навсегда, удаление файла не помогает (нужна ротация ключа). Приложение должно брать секрет в рантайме из секрет-менеджера по своей IAM-роли; в репозитории — только имя секрета.
  2. SLSA даёт воспроизводимую сборку и provenance — доказательство, откуда и из чего собран артефакт. Подпись + запрет неподписанного деплоя защищают цепочку поставки от подмены артефакта между сборкой и продом.
  3. Граница доверия — место, где данные переходят между зонами с разным уровнем доверия (клиент↔API, API↔внешний сервис). Угрозы возникают именно на пересечении, поэтому STRIDE разбирают каждый такой поток.
  4. Ночной прогон обнаруживает проблему уже в main, после мержа. Гейт мерджа не пускает уязвимый код/секрет в основную ветку вовсе — дешевле и раньше, по принципу «безопасность как свойство, а не этап».
  5. Критерий: containers SPA/API/DB/Redis/Kafka/Storage/CDN, внешние IdP и PSP, подписанные связи с протоколами и ≥3 помеченные границы доверия.
  6. Критерий: 6 строк (S/T/R/I/D/E), у каждой конкретный пример в маркетплейсе и контрмера, ссылающаяся на изученный механизм (OIDC, серверная цена, аудит-лог, presigned+authz, rate-limit, RBAC).
  7. Образец: commit — secret-scan (ключи в диффе/истории); build — SAST (инъекции) + SCA (уязвимые зависимости); artifact — image-scan (CVE) + подпись; deploy — policy-gate (неподписанный образ/дрейф IaC).
