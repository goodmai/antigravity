Эталонная архитектура на Google

Канон: Google Cloud Architecture Framework, Cost Optimization pillar.

Этот урок сводит девять кирпичей маркетплейса в одну Google-проекцию, честно считает её цену по пяти опорам Architecture Framework и анализирует vendor lock-in. Тот же продукт из урока 1.1, тот же циркуль — другая парадигма ответственности.

3. Vendor lock-in: где привязка и какова цена выхода

Lock-in — не «да/нет», а градиент: насколько дорог переход. Низкий — переносимый стандарт (контейнер, SQL, объектное хранилище). Высокий — проприетарная модель данных/API без аналога. Архитектор обязан знать exit-стоимость каждого кирпича до внедрения.

СервисПривязкаExit-стратегия
Cloud RunНизкая — OCI-образЛюбой контейнерный рантайм
Cloud SQL (PG)Низкая — стандартный PGpg_dump → любой Postgres
FirestoreВысокая — проприетарная модельAnticorruption Layer + экспорт
Pub/SubСредняя — клиентский APIАбстракция publisher/consumer
BigQueryСредняя — SQL-диалект/sinkЭкспорт в Parquet, рекаст SQL
Правило. Lock-in допустим осознанно, если выигрыш в TCO/скорости перевешивает exit-стоимость, и для высокой привязки заложен Anticorruption Layer (урок 1.1) и план выхода.

Пример использования элементов

C4 Container-диаграмма «Google» — тот же продукт урока 1.1, но контейнеры названы сервисами GCP:

workspace {
  model {
    buyer  = person "Покупатель"
    author = person "Автор работ"
    market = softwareSystem "Маркетплейс (Google Cloud)" {
      lb     = container "Global LB + Cloud Armor"   "периметр"
      api    = container "market-api"  "Cloud Run"   "Catalog/Payments"
      feed   = container "feed-worker" "Cloud Run"   "лента (Pub/Sub push)"
      bus    = container "Pub/Sub"     "topic payment-succeeded"
      sql    = container "Cloud SQL"   "Postgres"    "заказы, CMEK"
      fs     = container "Firestore"                 "профили, лента"
      obj    = container "Cloud Storage + CDN"       "файлы работ"
      bq     = container "BigQuery"                  "аналитика (sink)"
    }
    psp = softwareSystem "Платёжный провайдер" "Внешняя система"

    buyer  -> lb "HTTPS";  author -> lb "HTTPS"
    lb -> api "маршрут"
    api -> sql "заказы (private IP)"
    api -> fs  "профиль/лента"
    api -> obj "signed URL после оплаты"
    api -> bus "publish payment.succeeded"
    bus -> feed "push";  bus -> bq "BigQuery subscription"
    api -> psp "платёж через Cloud NAT"
  }
  views { container market { include * autolayout lr } }
}

Решение: managed-first снижает операционный TCO ценой среднего lock-in; самый дорогой выход — Firestore (закрыт Anticorruption Layer и экспортом), остальное переносимо. Все девять кирпичей закрыты, error budget и план выхода зафиксированы — архитектура завершена и готова к сравнению с децентрализацией в модуле 3.

Артефакт урока. C4 Container-диаграмма «Google» (Structurizr/PlantUML) + чек-лист по пяти опорам Architecture Framework + lock-in таблица с exit-стратегией на каждый кирпич в личном форке.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему lock-in — это градиент exit-стоимости, а не бинарный признак?
  2. вопросКакой кирпич Google-проекции маркетплейса самый «лип кий» и почему?
  3. вопросКак пять опор Architecture Framework помогают честно посчитать TCO?
  4. вопросПочему C4 Container-диаграмма «Google» имеет ту же топологию, что классическая из модуля 1?
  5. задачаЗаполните чек-лист по пяти опорам для маркетплейса с конкретным ответом на каждый вопрос.
  6. задачаПостройте lock-in таблицу с exit-стратегией для Cloud Run, Cloud SQL, Firestore, Pub/Sub, BigQuery.
  7. задачаНарисуйте C4 Container-диаграмму «Google» продукта и отметьте, где проходит Anticorruption Layer к самому привязывающему сервису.
Разбор ответов
  1. Уйти можно почти всегда — вопрос в цене: переписать код, мигрировать данные, изменить процессы. Контейнер/Postgres дёшевы в переносе; проприетарная модель данных — дорого. Решение принимается по exit-стоимости, а не по факту «привязаны/нет».
  2. Firestore: проприетарная документная модель и API без прямого аналога, миграция требует пересборки слоя доступа и экспорта. Cloud Run/Cloud SQL переносимы почти без затрат.
  3. Они заставляют оценить решение по Cost, Reliability, Security, Operational, Performance вместе; TCO = не только цена ресурсов, но и надёжность, безопасность, эксплуатация — опоры делают скрытые статьи явными.
  4. Топология — это Bounded Contexts и потоки уровня Container (урок 1.1), которые не зависят от провайдера. Меняются только реализации контейнеров (Cloud Run вместо своего сервиса), а не связи между ними.
  5. Cost: scale-to-zero для Catalog/Feed. Reliability: checkout SLO 99.9% + burn-rate. Security: WIF, Secret Manager, CMEK на заказах. Operational: build once + Terraform, откат секундами. Performance: CDN на медиа, Payments без холодного старта.
  6. Cloud Run — низкая, любой OCI-рантайм; Cloud SQL — низкая, pg_dump в любой Postgres; Firestore — высокая, ACL + экспорт; Pub/Sub — средняя, абстракция publisher/consumer; BigQuery — средняя, экспорт в Parquet и рекаст SQL.
  7. Диаграмма: акторы buyer/author → LB+Cloud Armor → market-api (Cloud Run) → Cloud SQL/Firestore/Storage, Pub/Sub → feed/BigQuery, внешний PSP. Anticorruption Layer — на границе доступа к Firestore (и к PSP), чтобы проприетарная модель не протекала в домен.
