Секреты и ключи

Канон: Secret Manager, Cloud KMS, Envelope encryption.

Кирпич Secrets/Keys отвечает на вопрос «где хранятся ключи и как они ротируются?». На Google Cloud разделяются секреты (строки-учётки → Secret Manager) и ключи шифрования (криптоматериал → Cloud KMS). Для маркетплейса это API-ключ PSP, пароль БД и шифрование чувствительных полей.

1. Secret Manager: версии, ротация, доступ

Секрет — это именованный ресурс с версиями. Приложение читает latest или фиксированную версию; ротация = добавить новую версию и переключить трафик, старую отключить (не удалять сразу — нужен откат). Доступ — только через IAM-роль ворклоада (secretmanager.secretAccessor), никогда не через файл в образе или переменную в репозитории. Каждое обращение логируется в Cloud Logging — это аудит.

echo -n "$PSP_KEY" | gcloud secrets create psp-api-key --data-file=-
# ротация: новая версия, приложение читает latest
echo -n "$PSP_KEY_NEW" | gcloud secrets versions add psp-api-key --data-file=-
gcloud secrets versions disable 1 --secret=psp-api-key   # откат возможен
gcloud secrets add-iam-policy-binding psp-api-key \
  --member="serviceAccount:payments-sa@PROJECT.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

2. Cloud KMS, CMEK и CSEK

KMS управляет ключами шифрования (key ring → key → version), на бэкенде HSM. CMEK (Customer-Managed Encryption Key) — данные сервиса (Cloud SQL, Storage, BigQuery) шифруются вашим ключом из KMS: отзыв ключа делает данные нечитаемыми. CSEK (Customer-Supplied) — ключ приносите вы и Google его не хранит: максимальный контроль, максимальная операционная ответственность.

МодельКто владеет ключомКонтрольОперационная цена
Google-managed (default)GoogleМинимальныйНулевая
CMEKВы (ключ в KMS)Средний — отзыв/ротацияУправление ротацией
CSEKВы (вне Google)МаксимальныйВысокая — потеря = потеря данных

3. Envelope encryption и ротация

Шифровать большой объём данных мастер-ключом дорого и не масштабируется. Envelope encryption: данные шифруются локальным DEK (data encryption key), а сам DEK шифруется мастер-ключом KEK в KMS. Хранится зашифрованный DEK рядом с данными. Ротация KEK тогда дешёвая — перешифровывается только маленький DEK, а не весь датасет. KMS поддерживает автоматическую ротацию версии ключа по расписанию.

gcloud kms keyrings create market --location=europe-west1
gcloud kms keys create data-kek --keyring=market \
  --location=europe-west1 --purpose=encryption \
  --rotation-period=90d --next-rotation-time=+P90D

Пример использования элементов

Маркетплейс: ключ PSP — секрет; БД заказов — под CMEK; чувствительное поле payout-реквизитов — envelope encryption:

// 1. PSP-ключ: читается из Secret Manager в рантайме (не в образе)
const pspKey = await sm.access('projects/PROJECT/secrets/psp-api-key/versions/latest');

// 2. Cloud SQL заказов создаётся с CMEK → отзыв ключа = данные нечитаемы
//    --disk-encryption-key=projects/.../cryptoKeys/data-kek

// 3. payout-реквизиты: envelope encryption
const dek = crypto.randomBytes(32);                 // DEK на запись
const ct  = aesGcm(dek, payoutDetails);
const wrappedDek = await kms.encrypt('data-kek', dek); // KEK оборачивает DEK
store({ ct, wrappedDek });                            // мастер-ключ не покидает KMS

Решение: ни одного секрета в репозитории/образе — всё в Secret Manager с IAM-доступом payments-sa и аудитом в Cloud Logging. БД под CMEK с ротацией KEK раз в 90 дней. Trade-off: KMS снимает заботу об HSM, но ключи остаются в периметре провайдера — сравните с самокастодиальной моделью урока 3.10. Lock-in средний: данные перешифруемы при выходе.

Артефакт урока. Реестр секретов и ключей маркетплейса: какие секреты в Secret Manager (PSP-ключ, пароль БД), что под CMEK (Cloud SQL заказов), где envelope encryption (payout-реквизиты), политика ротации и кто (SA) имеет доступ.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем секрет в Secret Manager концептуально отличается от ключа в Cloud KMS?
  2. вопросЧто такое CMEK и что происходит с данными при отзыве CMEK-ключа?
  3. вопросЗачем нужна envelope encryption и почему она удешевляет ротацию мастер-ключа?
  4. вопросЧем CSEK отличается от CMEK по контролю и операционному риску?
  5. задачаОпишите процедуру ротации API-ключа PSP в Secret Manager без даунтайма и с возможностью отката.
  6. задачаСпроектируйте шифрование payout-реквизитов через envelope encryption (DEK/KEK) с хранением только обёрнутого DEK.
  7. задачаСоставьте строку trade-off (контроль·операционная цена·lock-in) для Google-managed vs CMEK vs CSEK для БД заказов.
Разбор ответов
  1. Secret Manager хранит произвольные строки-учётки (пароли, API-ключи) с версиями и аудитом. Cloud KMS управляет криптографическим материалом (ключами шифрования) на HSM и сам не отдаёт ключ наружу — он шифрует/ дешифрует.
  2. CMEK — шифрование ресурсов вашим ключом из KMS. При отзыве/отключении ключа Google теряет возможность расшифровать данные — они становятся нечитаемыми; это рычаг экстренной блокировки доступа.
  3. Данные шифруются локальным DEK, DEK шифруется мастер-ключом KEK в KMS. При ротации KEK перешифровывается только маленький обёрнутый DEK, а не весь датасет, поэтому ротация дёшева и быстра.
  4. CSEK: ключ приносите вы, Google его не хранит — максимальный контроль, но потеря ключа = безвозвратная потеря данных и вся операционная ответственность на вас. CMEK: ключ живёт в KMS, баланс контроля и эксплуатации.
  5. Добавить новую версию секрета (versions add), приложение читает latest и подхватывает новый ключ; старую версию disable (не destroy) — при проблеме включить обратно; после стабилизации destroy.
  6. На запись генерировать случайный DEK, шифровать им данные (AES-GCM), затем KMS оборачивает DEK мастер-ключом; хранить рядом шифртекст и обёрнутый DEK. Мастер-ключ никогда не покидает KMS.
  7. Google-managed: контроль низкий, опер. цена нулевая, lock-in низкий. CMEK: контроль средний (отзыв/ротация), опер. цена — управление ротацией, lock-in средний. CSEK: контроль максимальный, опер. цена высокая (потеря ключа фатальна), lock-in низкий по ключу.
