Клиент–сервер и слоистая архитектура

Канон: Clean Architecture (Martin), Hexagonal Architecture (Cockburn), Fundamentals of Software Architecture, 12-Factor App.

Клиент–сервер — это базовое разделение ответственности: клиент инициирует запрос и отображает результат, сервер хранит истину и применяет правила. Но «сервер» внутри себя — не монолитный комок: его структурируют слоями. Слоистая (она же «чистая», гексагональная, ports&adapters) архитектура задаёт одно жёсткое правило — правило зависимостей: исходный код может зависеть только внутрь, к домену. Инфраструктура (БД, HTTP, брокеры) зависит от домена, никогда наоборот. Этот словарь мы пронесём через все три парадигмы курса.

1. Клиент–сервер: где проходит граница доверия

Клиент–сервер — это не «фронт и бэк», а распределение ответственности и доверия. Сервер — авторитетный держатель истины: он применяет инварианты, принимает финальное решение, не доверяет ни одному биту, пришедшему от клиента. Клиент — это ненадёжная зона: его код виден, его запросы подделываемы. Отсюда архитектурное правило: любая проверка, влияющая на деньги или права, дублируется на сервере, даже если она уже есть в UI.

2. Правило зависимостей и почему оно главное

Роберт Мартин формулирует его так: зависимости в исходном коде указывают только в сторону более стабильных и более абстрактных политик. Домен — самое стабильное ядро: он не должен знать, что данные лежат в PostgreSQL, а запрос пришёл по HTTP. Это даёт три практических свойства: домен тестируется без базы и сети; инфраструктуру можно заменить (Postgres → другой стор) без переписывания правил; срок жизни бизнес-логики не привязан к сроку жизни фреймворка.

3. Порты и адаптеры (Hexagonal)

Кокбёрн переворачивает картинку: вместо «верх–низ» — «внутри–снаружи». Домен и приложение в центре объявляют порты (интерфейсы: что им нужно от мира). Инфраструктура снаружи поставляет адаптеры (реализации). Driving-адаптеры (HTTP, CLI) вызывают приложение; driven-адаптеры (БД, PSP) вызываются приложением через порт. Замена БД или протокола — это замена адаптера, домен не трогается.

// domain объявляет ПОРТ (интерфейс)
interface OrderRepository { save(o: Order): Promise<void>; byId(id: string): Promise<Order> }

// infrastructure поставляет АДАПТЕР
class PgOrderRepository implements OrderRepository { /* SQL, pg-pool */ }

// application получает порт через DI — БД заменяема в тестах
class PlaceOrder {
  constructor(private orders: OrderRepository) {}
  async exec(cmd: PlaceOrderCmd) { /* доменные правила, без import 'pg' */ }
}

4. Где обычно ломается правило

Самые частые нарушения: ORM-аннотации прямо на доменной сущности (домен начинает зависеть от инфраструктуры); use-case возвращает наружу ORM-модель вместо DTO (Presentation увидел SQL-структуру); «утечка» HTTP-объекта req/res внутрь application. Каждое такое нарушение делает домен непригодным к юнит-тесту без поднятой базы и размывает границы при будущей декомпозиции (урок 1.3).

Правило стабильности. Чем стабильнее код, тем абстрактнее он должен быть. Конкретный класс PgOrderRepository нестабилен (БД меняется) — поэтому зависят от абстракции OrderRepository, а не от него.

Пример использования элементов

Сценарий маркетплейса: покупатель оформляет заказ на цифровую работу. Раскладываем по слоям use-case «оформить заказ».

presentation/  OrderController.ts   // парсит JSON, валидирует формат, маппит в PlaceOrderCmd
application/    PlaceOrder.ts        // транзакция: резерв, проверка цены, создание заказа
domain/         Order.ts, Money.ts   // инвариант: total = sum(items), статус-машина заказа
                ports/OrderRepository.ts, ports/PriceCatalog.ts, ports/PaymentGateway.ts
infrastructure/ PgOrderRepository.ts, HttpCatalogClient.ts, PspPaymentGateway.ts
// domain/ports/PriceCatalog.ts — порт
interface PriceCatalog { priceOf(workId: string): Promise<Money> }

// infrastructure: боевой адаптер
class HttpPriceCatalog implements PriceCatalog {
  async priceOf(id: string) { /* GET /catalog/works/:id */ }
}
// тестовый адаптер — без сети
class InMemoryPriceCatalog implements PriceCatalog {
  constructor(private map: Record<string, Money>) {}
  async priceOf(id: string) { return this.map[id]; }
}

// application получает порт через конструктор (DI)
new PlaceOrder(new PgOrderRepository(pool), new HttpPriceCatalog(cfg));
// в тесте:
new PlaceOrder(new InMemoryOrderRepo(), new InMemoryPriceCatalog({ w1: usd(900) }));

Поток: POST /orders → контроллер собирает команду → PlaceOrder.exec читает цену через порт PriceCatalog (а не делает HTTP сам), создаёт Order, домен проверяет инвариант суммы, репозиторий сохраняет в одной транзакции. Цена берётся сервером через каталог, не из тела запроса — клиенту доверять нельзя. Тест PlaceOrder подставляет in-memory-адаптеры портов: ни Postgres, ни HTTP не нужны.

Маркер ошибки. Если в доменной сущности появился import pg или ORM-аннотация — правило зависимостей нарушено, и домен больше не тестируется без базы.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросСформулируйте правило зависимостей и объясните, почему домен не должен знать про PostgreSQL.
  2. вопросЧем порт отличается от адаптера и кто из слоёв объявляет порт, а кто поставляет адаптер?
  3. вопросПочему ORM-аннотация на доменной сущности — нарушение, а не «удобная оптимизация»?
  4. вопросПочему цену заказа нельзя брать из тела запроса клиента, даже если UI её уже показал?
  5. задачаРаспишите use-case «оформить заказ» по 4 слоям: что лежит в каждом и какие порты объявляет домен.
  6. задачаНапишите интерфейс порта PriceCatalog и два адаптера: HTTP-клиент и in-memory для теста; покажите, как application получает их через DI.
  7. задачаНайдите в чужом коде 3 типичных нарушения правила зависимостей и опишите, как каждое мешает юнит-тесту домена.
Разбор ответов
  1. Зависимости в коде направлены только внутрь — к более стабильным и абстрактным политикам (домену). Домен — самое стабильное ядро; знание о PostgreSQL привязало бы бизнес-правила к сроку жизни и API конкретной БД и сделало бы их непроверяемыми без поднятого стора.
  2. Порт — интерфейс, объявленный доменом/приложением («что мне нужно от мира»). Адаптер — реализация порта в инфраструктуре. Порт объявляет внутренний слой, адаптер поставляет инфраструктура; связь — через DI.
  3. Аннотация делает доменный класс зависимым от библиотеки инфраструктуры: домен перестаёт быть «чистым», его нельзя инстанцировать и протестировать без ORM/драйвера, а смена ORM становится сменой домена.
  4. Клиент — недоверенная зона: тело запроса подделывается. Цена — инвариант, влияющий на деньги, поэтому её авторитетный источник — сервер (каталог). UI-значение допустимо только как косметика, финальное решение принимает сервер.
  5. Presentation: контроллер, DTO, валидация формата. Application: PlaceOrder — транзакция и оркестрация. Domain: Order, Money, инвариант суммы и статус-машина; порты OrderRepository, PriceCatalog, PaymentGateway. Infrastructure: SQL-репозиторий, HTTP-клиент каталога, адаптер PSP.
  6. Критерий: interface PriceCatalog { priceOf(workId): Promise<Money> }; HttpPriceCatalog и InMemoryPriceCatalog реализуют его; PlaceOrder принимает PriceCatalog в конструкторе, в тесте подставляется in-memory — без сети.
  7. Образец: (1) ORM-аннотация на сущности — нужен драйвер для теста; (2) use-case возвращает ORM-модель — Presentation видит SQL-структуру, тест проверяет схему БД, а не правила; (3) req/res внутри application — нужен HTTP-мок для проверки бизнес-логики.
