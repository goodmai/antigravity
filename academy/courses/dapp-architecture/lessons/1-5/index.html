Состояние и данные: реляционка

Канон: PostgreSQL docs, DDIA (Kleppmann), гл. 7, PostgreSQL: Transaction Isolation.

Реляционная БД — это истина системы: она даёт ACID и позволяет выражать инварианты как ограничения схемы, а не как код, который кто-нибудь забудет вызвать. По умолчанию начинайте с PostgreSQL. Этот урок — про нормализацию, изоляцию транзакций, индексы и эволюцию схемы без даунтайма.

1. ACID и нормализация

ACID — это контракт: транзакция атомарна (всё или ничего), переводит БД из одного консистентного состояния в другое, изолирована от конкурентов и durable после коммита. Нормализация (до 3NF) устраняет аномалии вставки/обновления/удаления: каждый факт хранится ровно один раз. Денормализация — осознанная оптимизация чтения, не стартовая точка.

2. Уровни изоляции и аномалии

Уровень изоляции определяет, какие аномалии конкурентного доступа возможны. В PostgreSQL READ COMMITTED — дефолт; для денежных инвариантов нужен как минимум REPEATABLE READ, а для критичных проверок — SERIALIZABLE.

*В PostgreSQL REPEATABLE READ использует snapshot и исключает фантомы для большинства случаев, но не write-skew — для него нужен SERIALIZABLE. Инвариант баланса лучше защищать ограничением БД, а не уровнем изоляции в одиночку.

-- инвариант «баланс не уходит в минус» — в схеме, не в коде
ALTER TABLE author_balance
  ADD CONSTRAINT balance_non_negative CHECK (amount_cents >= 0);

3. Индексы под реальные запросы

Индекс ускоряет чтение и замедляет запись (и занимает место). Индексируйте под фактические запросы, подтверждённые EXPLAIN ANALYZE, а не «на всякий случай».

-- лента: последние работы автора → составной индекс под ORDER BY
CREATE INDEX idx_works_author_created
  ON works (author_id, created_at DESC);

EXPLAIN ANALYZE
SELECT id, title FROM works
WHERE author_id = $1 ORDER BY created_at DESC LIMIT 20;
-- ожидаем Index Scan, не Seq Scan + Sort

4. Эволюция схемы: expand–contract

Прямой ALTER с переименованием/NOT NULL ломает старый код во время выкатки. Паттерн expand–contract разводит изменение схемы и изменение кода во времени так, что обе версии кода работают одновременно.

-- 1. EXPAND: добавить nullable-колонку, деплой кода, читающего обе формы
ALTER TABLE orders ADD COLUMN total_cents bigint;
-- 2. BACKFILL: перенести данные пачками
-- 3. CONTRACT: сделать NOT NULL, убрать старую колонку
ALTER TABLE orders ALTER COLUMN total_cents SET NOT NULL;

Так схема меняется без даунтайма и совместима со старым и новым кодом одновременно. Это тот же expand/contract, что и для API-контракта в уроке 1.4 — один принцип на разных уровнях.

Опасный ALTER. ALTER ... SET NOT NULL и добавление колонки с volatile-default берут блокировку и переписывают таблицу. На больших таблицах делайте это через NOT VALID constraint + отдельный VALIDATE вне пиковой нагрузки.

Пример использования элементов

ER-модель ядра маркетплейса (нормализованная до 3NF):

CREATE TABLE users (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email       citext UNIQUE NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE works (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  author_id   uuid NOT NULL REFERENCES users(id),
  title       text NOT NULL,
  price_cents bigint NOT NULL CHECK (price_cents > 0),
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE orders (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  buyer_id    uuid NOT NULL REFERENCES users(id),
  work_id     uuid NOT NULL REFERENCES works(id),
  total_cents bigint NOT NULL CHECK (total_cents > 0),
  status      text NOT NULL DEFAULT 'pending',
  created_at  timestamptz NOT NULL DEFAULT now(),
  -- покупатель не может купить одну работу дважды
  UNIQUE (buyer_id, work_id)
);
CREATE INDEX idx_orders_buyer ON orders (buyer_id, created_at DESC);

Разбор: цена и владелец живут в works ровно один раз (3NF); orders.total_cents — снимок цены на момент покупки (намеренная денормализация: цена работы потом меняется, а в заказе зафиксирована); инвариант «не дважды одну работу» — UNIQUE в схеме, а не проверка в коде, которую обойдёт гонка. Миграция переименования amount → total_cents делается expand–contract из раздела 4.

Артефакт урока. ER-модель маркетплейса + одна expand-contract миграция.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧто гарантирует каждая буква ACID и почему инвариант лучше выражать ограничением БД, а не кодом?
  2. вопросКакие аномалии возможны на READ COMMITTED и зачем для денег нужен хотя бы REPEATABLE READ?
  3. вопросПочему индекс не ставят «на всякий случай» и чем подтверждают его необходимость?
  4. вопросЗачем нужен expand–contract и почему прямой RENAME/SET NOT NULL опасен при выкатке?
  5. задачаСпроектируйте ER-модель users / works / orders в DDL с PK, FK, CHECK и нужными UNIQUE.
  6. задачаОбъясните, почему orders.total_cents — намеренная денормализация, а не ошибка нормализации.
  7. задачаНапишите expand–contract миграцию переименования колонки amount → total_cents в 3 шага без даунтайма.
Разбор ответов
  1. Atomicity — всё или ничего; Consistency — переход между валидными состояниями; Isolation — конкуренты не видят промежуточное; Durability — после коммита данные не теряются. Ограничение БД нельзя «забыть вызвать» и его не обойдёт гонка, в отличие от проверки в коде.
  2. На READ COMMITTED возможны non-repeatable read и phantom (между двумя SELECT в транзакции данные изменились). Для денег это значит расчёт по «уплывшим» данным, поэтому нужен снапшот REPEATABLE READ или SERIALIZABLE.
  3. Каждый индекс замедляет запись и занимает место; полезен лишь под реальные запросы. Подтверждают через EXPLAIN ANALYZE: должен появиться Index Scan вместо Seq Scan + Sort.
  4. Expand–contract разводит изменение схемы и кода во времени, чтобы старая и новая версии работали одновременно. Прямой RENAME/SET NOT NULL ломает ещё живой старый код и берёт тяжёлую блокировку с переписью таблицы.
  5. Критерий: users(id PK, email UNIQUE), works(id PK, author_id FK, price_cents CHECK>0), orders(id PK, buyer_id/work_id FK, total_cents CHECK, UNIQUE(buyer_id, work_id)).
  6. Цена работы со временем меняется; заказ должен хранить цену на момент покупки. Это снимок факта, а не дублирование изменяемого факта — нормализация запрещает второе, не первое.
  7. (1) EXPAND: ADD COLUMN total_cents bigint, деплой кода, пишущего/читающего обе колонки; (2) BACKFILL пачками UPDATE ... SET total_cents = amount; (3) CONTRACT: SET NOT NULL, деплой кода только на total_cents, DROP COLUMN amount.
