Наблюдаемость

Канон: Google SRE: Monitoring, OpenTelemetry, 12-Factor: Logs.

Наблюдаемость — способность ответить на вопрос о системе, который вы не предвидели заранее. Это свойство, а не дашборд. Три столпа: структурные логи (что случилось), метрики (сколько и как часто), трейсы (где именно в цепочке). Связывает их сквозной trace_id.

1. Метрики: golden signals, RED и USE

Google SRE определяет четыре «золотых сигнала», достаточных для мониторинга пользовательского сервиса. RED — их прикладная проекция на сервис, USE — на ресурс.

СигналЧтоRED / USEПример в маркетплейсе
Latencyвремя ответа (отдельно для ошибок)RED: Durationp99 POST /orders
Trafficзапросов в секундуRED: Raterps /works
Errorsдоля неуспехаRED: Errors% 5xx на оплате
Saturationнасколько ресурс «забит»USE: Utilizationpool БД, лаг Kafka

Считайте latency по перцентилям (p95/p99), не по среднему: среднее прячет хвост, на котором страдают реальные пользователи. Ошибочную latency меряйте отдельно — быстрый 500 не должен «улучшать» график.

2. Структурные логи и 12-factor

Лог — это событие с полями, а не строка для глаз. JSON делает логи фильтруемыми и связываемыми с трейсом. По 12-factor приложение пишет в stdout как в поток событий; ротацию, агрегацию и хранение делает платформа, не код.

{"ts":"2026-05-16T10:00:00Z","level":"error","trace_id":"abc123",
 "service":"payments","msg":"payment failed","order_id":42,
 "psp_code":"card_declined","user_id":"u-7"}

Уровни осмысленно: error — нужен человек; warn — деградация, пока терпит; info — бизнес- событие; debug — выключено в проде. Не логируйте PII и секреты.

3. Трейсы и контекст-propagation

Распределённый запрос проходит через API, БД, Kafka, PayoutSvc. Трейс сшивает это в одно дерево спанов по trace_id, который пробрасывается через HTTP-заголовки и заголовки сообщений Kafka. OpenTelemetry — вендоронезависимый стандарт инструментирования и W3C traceparent для propagation.

Один trace_id — три столпа. Если trace_id есть и в логе, и в спане, и в exemplar метрики, расследование инцидента идёт от «p99 вырос» к конкретной строке лога за секунды, а не часы.

Пример использования элементов

Инцидент: выросла доля ошибок оплаты. Наблюдаемость должна довести от сигнала до причины. Инструментируем поток оплаты (урок 1.6).

// OpenTelemetry: спан + структурный лог с тем же trace_id
const tracer = otel.trace.getTracer('payments');
await tracer.startActiveSpan('pay_order', async (span) => {
  span.setAttribute('order.id', orderId);
  try {
    await psp.charge(order);                       // вложенный спан HTTP к PSP
    log.info({ trace_id: span.spanContext().traceId, order_id: orderId,
               msg: 'payment ok' });
    metrics.payments_total.inc({ result: 'ok' });
  } catch (e) {
    span.recordException(e);
    span.setStatus({ code: SpanStatusCode.ERROR });
    log.error({ trace_id: span.spanContext().traceId, order_id: orderId,
                psp_code: e.code, msg: 'payment failed' });
    metrics.payments_total.inc({ result: 'error', psp_code: e.code });
    throw e;
  } finally { span.end(); }
});

Разбор расследования: (1) алерт по RED — rate(payments_total {result="error"}) превысил SLO; (2) разрез по метке psp_code показывает всплеск card_declined у одного провайдера; (3) по exemplar берём trace_id и в логах видим, что 500-е идут только из региона X; (4) трейс показывает, что вырос спан HTTP-вызова PSP — деградация на стороне провайдера, не у нас. Решение — circuit breaker на PSP (урок 1.10). Все три столпа сшиты одним trace_id.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем наблюдаемость отличается от мониторинга и почему «дашборд» — не ответ?
  2. вопросНазовите golden signals и объясните, как RED и USE с ними соотносятся.
  3. вопросПочему latency меряют по p95/p99, а не по среднему, и зачем отделять ошибочную latency?
  4. вопросЧто даёт сквозной trace_id и как он связывает три столпа?
  5. задачаСпроектируйте JSON-схему структурного лога для события оплаты (поля и уровни).
  6. задачаОпишите набор RED-метрик и алертов для эндпоинта POST /orders/{id}/pay.
  7. задачаРаспишите шаги расследования «выросли ошибки оплаты» от сигнала до корневой причины через 3 столпа.
Разбор ответов
  1. Мониторинг отвечает на заранее заданные вопросы (алерты по известным метрикам). Наблюдаемость позволяет задать новый вопрос постфактум по сырым данным (логи/трейсы/метрики). Дашборд показывает ожидаемое, но не объясняет неожиданное.
  2. Latency, Traffic, Errors, Saturation. RED (Rate, Errors, Duration) — проекция на сервис, USE (Utilization, Saturation, Errors) — на ресурс; вместе покрывают и пользовательскую, и ресурсную сторону.
  3. Среднее маскирует хвост: при p99=5с среднее может быть 200мс, а страдает 1% запросов. Ошибочную latency отделяют, чтобы быстрый 500 не «улучшал» график успешных ответов.
  4. trace_id один на весь распределённый запрос, пробрасывается через HTTP и Kafka. Он есть в спане, в логе и в exemplar метрики, поэтому от «p99 вырос» переходят к конкретной строке лога за секунды.
  5. Критерий: JSON с ts, level, trace_id, service, msg, order_id, psp_code; уровни error (нужен человек) / warn (деградация) / info (бизнес-событие); без PII и секретов.
  6. Образец: rate запросов, доля 5xx (Errors), histogram длительности → p95/p99 (Duration); алерт при доле ошибок > SLO за окно и при росте p99 выше порога.
  7. (1) алерт RED по error-rate; (2) разрез по psp_code ищет домен ошибки; (3) по exemplar trace_id в логах локализуем (регион/ пользователь); (4) трейс показывает медленный/падающий спан → корневая причина (например, деградация PSP).
