Децентрализованная идентичность

Канон: EIP-4361 (SIWE), W3C DID Core.

Это децентрализованный аналог кирпича Identity/Auth (OIDC / Identity Platform). Идентичность здесь — контроль приватного ключа; центрального IdP нет, что меняет и модель доверия, и модель восстановления доступа.

1. Self-sovereign identity: ключ вместо IdP

В классике личность подтверждает IdP (выдаёт JWT). В web3 личность — это адрес, контролируемый приватным ключом; никто не «выдаёт» аккаунт. Плюс: нет хранилища паролей, нет утечки учёток, пользователь суверенен. Минус: нет «восстановить пароль» — потеря ключа = потеря аккаунта (смягчается account abstraction, урок 3.10).

2. SIWE (EIP-4361): аутентификация подписью

Сервер не хранит секрет пользователя. Он выдаёт nonce, пользователь подписывает структурированное сообщение кошельком, сервер проверяет подпись и заводит сессию. Домен и nonce в сообщении защищают от phishing и replay.

market.example хочет, чтобы вы вошли с вашим Ethereum-аккаунтом:
0xAb58...91F4

URI: https://market.example
Version: 1
Chain ID: 1
Nonce: 8sf9Hq2k         <- одноразовый, выдан сервером
Issued At: 2026-05-16T10:00:00Z
POST /siwe/verify { message, signature }
  → recover(address) из подписи
  → сверить nonce, домен, время
  → выдать сессионный cookie/JWT (теперь как в классике)

3. DID/VC и ENS: атрибуты без раскрытия личности

Адрес сам по себе анонимен. DID (W3C) — это идентификатор с DID-документом (ключи, сервисы); Verifiable Credentials — подписанные утверждения («верифицированный автор», «KYC пройден») без раскрытия персональных данных. ENS даёт человекочитаемое имя (author.eth) поверх адреса.

Пример использования элементов

В маркетплейсе вход — SIWE: подключил кошелёк, подписал сообщение с nonce, получил сессию. Статус «верифицированный автор» выдаётся как VC и не требует хранить паспортные данные у нас. Имя автора в ленте — ENS-резолв адреса. Финансовые действия (вывод средств) дополнительно требуют свежей подписи, а не только сессии.

Цена модели. Нет «восстановления доступа»: потеря ключа = потеря аккаунта. Это архитектурный риск, который закрывают account abstraction и social recovery (урок 3.10), а не пароль.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧто в SIWE заменяет хранилище паролей и почему утечка учёток невозможна?
  2. вопросЗачем в SIWE-сообщении нужны nonce и домен?
  3. вопросЧем DID/VC решают задачу «верифицированный автор» без раскрытия личности?
  4. вопросКакой главный минус self-sovereign-идентичности по сравнению с OIDC?
  5. задачаОпишите полный SIWE-поток для маркетплейса от подключения кошелька до выдачи сессии.
  6. задачаСпроектируйте, какие действия требуют только сессии, а какие — свежей подписи, и обоснуйте.
  7. задачаСравните SIWE и OIDC из 1.8 по доверию, суверенитету и восстановлению доступа в таблице.
Разбор ответов
  1. Заменяет приватный ключ пользователя и проверка подписи. Сервер не хранит секрет — красть нечего; компрометация БД сервера не даёт доступа к аккаунтам.
  2. Nonce — одноразовый, защищает от replay подписанного сообщения. Домен привязывает подпись к конкретному сайту и предотвращает phishing (подпись не сработает на другом домене).
  3. VC — подписанное доверенным эмитентом утверждение о субъекте. Маркетплейс проверяет подпись эмитента и видит «автор верифицирован», не получая и не храня персональные данные.
  4. Нет централизованного восстановления доступа: потеря ключа = потеря аккаунта. В OIDC есть reset по email; здесь нужен AA/social recovery.
  5. Подключение кошелька → запрос nonce у сервера → формирование EIP-4361 сообщения (домен, nonce, время) → подпись в кошельке → POST /verify → recover адреса, проверка nonce/домена/времени → сессия.
  6. Только сессия: просмотр, добавление в избранное. Свежая подпись: покупка, вывод средств, смена настроек выплат — финансово значимые действия, где риск перехвата сессии недопустим.
  7. Доверие: OIDC — к IdP, SIWE — к ключу. Суверенитет: OIDC низкий, SIWE полный. Восстановление: OIDC — reset по email, SIWE — отсутствует без AA. Lock-in: OIDC высокий, SIWE низкий.
