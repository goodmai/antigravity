Аналитика и события

Канон: Pub/Sub docs, BigQuery docs, Eventarc docs.

Кирпич Messaging отвечает на вопрос «как части системы общаются асинхронно?». На Google Cloud это управляемый Pub/Sub для событий и BigQuery как аналитический сток. Для маркетплейса событийная развязка позволяет ленте, аналитике и выплатам реагировать на оплату, не блокируя синхронный путь покупки.

1. Pub/Sub: доставка, at-least-once и идемпотентность

Pub/Sub — это topic (издатель пишет) и subscription (подписчик читает: pull или push). Гарантия — at-least-once: сообщение может прийти повторно при ретрае или отсутствии ack в дедлайн. Следствие архитектурное, а не опциональное: обработчик обязан быть идемпотентным (дедупликация по бизнес-ключу). Exactly-once доступен на pull в одном регионе, но дороже и не отменяет необходимость идемпотентного дизайна.

2. Eventarc и event-driven serverless

Eventarc маршрутизирует события источников (объект появился в Cloud Storage, запись в Audit Log, сообщение Pub/Sub) в Cloud Run/Functions по CloudEvents-контракту. Это превращает инфраструктурные факты в триггеры без своего поллинга. Связка «Cloud Run публикует → Pub/Sub → Cloud Run обрабатывает» — стандартный event-driven serverless паттерн модуля.

Cloud Run (Payments) ──publish──▶ topic: payment.succeeded
                                    ├─ push subscription → Feed worker
                                    ├─ push subscription → Payout worker
                                    └─ BigQuery subscription → analytics.payments

3. BigQuery: аналитический сток, не OLTP

BigQuery — serverless колоночный склад: оплата за просканированные байты (или слоты). Это не операционная БД — никаких точечных update в горячем пути. Истина транзакций живёт в Cloud SQL (урок 2.3); в BigQuery течёт копия событий для продуктовой аналитики. Error budget аналитики — best effort, её сбои не блокируют покупку.

Пример использования элементов

Event-flow «оплата → выплата автору» развязан через Pub/Sub. Payments публикует факт, два независимых подписчика реагируют, аналитика течёт параллельно:

gcloud pubsub topics create payment-succeeded
gcloud pubsub subscriptions create feed-sub \
  --topic=payment-succeeded --push-endpoint=https://feed-xxx.run.app/ \
  --dead-letter-topic=payment-dlq --max-delivery-attempts=5
gcloud pubsub subscriptions create payout-sub \
  --topic=payment-succeeded --push-endpoint=https://payout-xxx.run.app/ \
  --ack-deadline=30
# BigQuery sink без ETL-кода
gcloud pubsub subscriptions create bq-payments \
  --topic=payment-succeeded \
  --bigquery-table=PROJECT:analytics.payments
// payout worker: at-least-once → дедуп по payment_id
async function handle(msg) {
  const e = JSON.parse(msg.data);
  if (await alreadyPaidOut(e.payment_id)) return ack(msg); // идемпотентность
  await transferToAuthor(e.author_id, e.author_amount_cents);
  await markPaidOut(e.payment_id);
  ack(msg);
}

Решение: покупка завершается, как только Payments записал транзакцию в Cloud SQL и опубликовал событие; лента и выплата догоняют асинхронно. Дубль выплаты невозможен благодаря проверке alreadyPaidOut; «ядовитое» сообщение уходит в DLQ после 5 попыток.

Артефакт урока. Event-flow «оплата → выплата» на Pub/Sub: topic, две push-подписки (Feed, Payout) с DLQ и BigQuery-subscription для аналитики, с пометкой точек идемпотентности.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧто означает гарантия at-least-once в Pub/Sub и какое требование она накладывает на обработчик?
  2. вопросЗачем нужен dead-letter topic и что определяет попадание сообщения в него?
  3. вопросЧем Eventarc отличается от прямой публикации в Pub/Sub?
  4. вопросПочему BigQuery нельзя использовать как операционную БД маркетплейса?
  5. задачаСпроектируйте event-flow «оплата → лента + выплата + аналитика» с одним topic и тремя подписчиками.
  6. задачаПокажите, как сделать payout-обработчик идемпотентным при at-least-once доставке.
  7. задачаОбъясните, как настроить ack deadline и max-delivery-attempts, и какие риски у слишком малых/больших значений.
Разбор ответов
  1. Сообщение доставляется минимум один раз и может прийти повторно (ретрай, пропущенный ack). Обработчик обязан быть идемпотентным: повторная обработка того же события не должна давать побочного эффекта дважды.
  2. DLQ принимает сообщения, которые подписчик не смог обработать после заданного числа попыток (max-delivery-attempts). Это изолирует «ядовитые» сообщения, не блокируя нормальный поток.
  3. Eventarc маршрутизирует события многих источников (Storage, Audit Logs, Pub/Sub) в Cloud Run/Functions по стандарту CloudEvents без своего поллинга; прямой Pub/Sub требует, чтобы издатель сам публиковал в topic.
  4. BigQuery оптимизирован под колоночное сканирование и аналитику с оплатой за байты; точечные update/чтения в горячем пути медленны и дороги. Истина транзакций — в Cloud SQL, в BigQuery течёт копия для аналитики.
  5. Topic payment-succeeded; push-подписки feed-sub и payout-sub на свои Cloud Run, BigQuery-subscription на analytics.payments. Подписчики независимы, отказ одного не влияет на других.
  6. Перед эффектом проверять по бизнес-ключу (payment_id), не выполнена ли выплата уже; если да — сразу ack без повторного перевода; пометку о выплате ставить атомарно с переводом.
  7. Ack deadline — время на обработку до redelivery: слишком мало → лишние дубли при медленной обработке; слишком много → долгая задержка ретрая при падении воркера. max-delivery-attempts балансирует упорство ретрая против быстрого вывода «ядовитых» сообщений в DLQ.
