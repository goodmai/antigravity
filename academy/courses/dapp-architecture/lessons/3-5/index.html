Децентрализованное хранилище

Канон: IPFS docs, Arweave yellow-paper.

Это децентрализованный аналог кирпича Storage/Media (S3 / Cloud Storage). Главная смена парадигмы — адресация по содержимому (CID), а не по пути, и тот факт, что «загрузил» не означает «хранится».

1. Content addressing: CID вместо пути

В S3 ссылка — это путь к месту (bucket/key). В IPFS ссылка — это хеш содержимого (CID). Следствия: контент самопроверяем (скачал — пересчитал хеш), дедуплицируется автоматически, и ссылка ломается при любом изменении байтов. Это идеально для иммутабельных файлов работ, но не для часто меняющихся данных.

2. Persistence economics: кто платит за хранение

IPFS-нода держит контент, пока он закреплён (pinned). Снял pin — через GC контент исчезнет. Долговечность обеспечивается экономикой:

  • IPFS + Filecoin: сделка хранения с провайдером, оплата за период, криптографические proof-of-storage.
  • Arweave: единоразовая оплата за «вечное» хранение (permaweb) из endowment-модели.
  • Storj: S3-совместимый, шардирование по узлам, SLA-подобная модель.

Пример использования элементов

Файл работы и метаданные кладём в IPFS, в контракт пишем только CID:

$ ipfs add work-1042.zip
added bafybeih... work-1042.zip      # CID = хеш содержимого

# метаданные (JSON) — отдельным объектом
{ "title": "...", "cid_file": "bafybeih...", "preview": "bafkrei..." }
→ ipfs add → bafyMeta...
→ контракт: setWorkCID(1042, "bafyMeta...")   # 32 байта в storage

Для проданных работ оформляем Filecoin-сделку (платный долгоживущий pin), для превью достаточно pinning-сервиса. «Загрузил в IPFS» само по себе ничего не гарантирует — persistence это явная статья эксплуатации, которой не было в облаке.

Pinning. Без pinning/Filecoin- сделки контент по CID исчезнет после GC. Это операционная стоимость и риск, который архитектор обязан заложить в ADR хранилища.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросЧем адресация по CID отличается от адресации по пути в S3 и какие следствия у этого?
  2. вопросПочему «загрузил в IPFS» не значит «хранится вечно»?
  3. вопросЧем модель долговечности Arweave отличается от IPFS+Filecoin?
  4. вопросПочему content addressing плохо подходит для часто меняющихся данных?
  5. задачаСпроектируйте, что для работы кладётся в IPFS, а что в контракт, и почему именно CID идёт on-chain.
  6. задачаОпишите политику persistence: что пиннить через Filecoin-сделку, что через pinning-сервис, и критерий.
  7. задачаОцените, что произойдёт со ссылками маркетплейса, если автор изменит файл работы, и как это обработать.
Разбор ответов
  1. CID — хеш содержимого, путь S3 — адрес места. CID даёт самопроверяемость и дедупликацию, но ссылка ломается при любом изменении байтов; путь S3 стабилен при изменении содержимого.
  2. Контент живёт, пока он закреплён (pinned) хотя бы одной нодой или покрыт Filecoin-сделкой. Без этого GC удалит данные — нет вечного хранения по умолчанию.
  3. Arweave — единоразовая оплата за «вечное» хранение из endowment. IPFS+Filecoin — повторяемые сделки на период с proof-of-storage; по истечении сделки нужно продлевать.
  4. Любое изменение байтов меняет CID, то есть ссылку. Для изменяемых данных нужен слой косвенности (мутабельный указатель: IPNS, контракт, урок 3.8), а не голый CID.
  5. В IPFS — файл и JSON-метаданные; в контракт — только CID метаданных (32 байта). On-chain идёт CID, потому что storage дорог, а CID и так фиксирует и проверяет весь контент.
  6. Проданные работы — Filecoin-сделка (юридически/экономически обязаны хранить долго). Превью и черновики — pinning-сервис. Критерий: ценность и обязательность долговечности против стоимости.
  7. Изменение файла даёт новый CID; старые ссылки и CID в контракте указывают на прежнюю версию. Обрабатываем версионированием: новый CID — новая запись, история сохраняется, ничего не перезаписывается.
