Масштаб и отказоустойчивость

Канон: CAP / PACELC (Abadi), Release It! (Nygard), DDIA (Kleppmann), гл. 5–6.

Масштаб — это не «добавить серверов», а осознанный выбор между согласованностью и доступностью на каждом участке системы. Отдельно живут две темы: горизонтальное масштабирование данных (реплики, шарды) и устойчивость к частичным отказам (паттерны Нюгарда).

1. Масштабирование без состояния и с состоянием

Stateless-сервисы (API ядра) масштабируются тривиально: больше реплик за балансировщиком, состояние — в БД/Redis. Сложность всегда в состоянии. Реплики читающие снимают нагрузку чтения ценой репликационного лага (читатель видит чуть старые данные). Шардирование делит данные по ключу ради записи и объёма, но кросс-шард запросы и ребалансировка дороги.

2. CAP → PACELC

CAP: при сетевом разделении (P) система выбирает между согласованностью (C) и доступностью (A) — третьего не дано. PACELC (Abadi) добавляет важное: даже Else (без разделения, нормальная работа) есть компромисс между латентностью (L) и согласованностью (C). То есть «синхронная репликация ради C» стоит латентности всегда, не только при сбое.

Решение принимается по фиче, не глобально. Для денег — C (лучше отказать, чем списать дважды). Для ленты — A/латентность (лучше показать слегка устаревшее, чем 500).

3. Паттерны устойчивости (Release It!)

  • Timeout + retry с jitter — но только для идемпотентных операций (урок 1.6), иначе ретрай удвоит платёж.
  • Circuit breaker — после серии ошибок размыкаем вызов: не добиваем упавшую зависимость и быстро отдаём fallback.
  • Bulkhead — изолируем пулы ресурсов, чтобы отказ одной зависимости не выел все потоки.
  • Backpressure — отвергаем избыточную нагрузку явно (429), а не падаем под ней.
  • Graceful degradation — лента без рекомендаций лучше, чем 500 на всю страницу.
Антипаттерн retry storm. Ретраи без jitter и без circuit breaker превращают деградацию в лавину: все клиенты ретраят синхронно и добивают восстанавливающийся сервис.

Пример использования элементов

Применим к маркетплейсу. Оплата зависит от внешнего PSP; лента — от сервиса рекомендаций. Разные требования → разные решения.

# ADR-02 — Consistency vs Availability
Статус: принято · Дата: 2026-05-16

Контекст
  Два потока с разными свойствами:
   - Оплата: деньги, инвариант «не списать дважды».
   - Лента: показ активности, терпит устаревание.

Решение
  Оплата = CP (PACELC: PC/EC).
   - запись заказа/баланса — primary, синхронно, SERIALIZABLE
   - при разделении: отказать (503), НЕ принимать платёж вслепую
   - вызов PSP: timeout 3s + circuit breaker; при open → 503,
     операция не считается выполненной (идемпотентный ключ)
  Лента = AP (PACELC: PA/EL).
   - чтение с read-реплики, допускается лаг
   - рекомендации недоступны → graceful degradation:
     хронологическая лента вместо персональной (200, не 500)
   - backpressure: при перегрузке отдаём 429, не копим очередь

Последствия
  + Деньги корректны даже ценой доступности; лента всегда отвечает
  − Оплата может временно отказывать; лента бывает неперсональной
  Триггер пересмотра: SLA PSP ухудшился ИЛИ лаг реплик > 5s

Разбор: одна система — два разных режима. Оплата выбирает C: при сомнении лучше честный 503, чем двойное списание (повтор защищён идемпотентным ключом из урока 1.6). Лента выбирает A: read-реплика + деградация до хронологии + backpressure 429 — пользователь всегда получает ответ. ADR фиксирует решение и триггер пересмотра, как ADR-01.

Артефакт урока. ADR-02 «consistency vs availability» для оплаты и для ленты.

Закрепление — 7 вопросов и задач

Ответьте сами, затем раскройте разбор.

  1. вопросПочему сложность масштабирования — в состоянии, а не в compute? Чем отличаются read-реплики и шарды?
  2. вопросЧто PACELC добавляет к CAP и почему это важно для «нормальной» работы, а не только при сбое?
  3. вопросЗачем circuit breaker и чем он отличается от простого retry?
  4. вопросПочему retry допустим только для идемпотентных операций и что такое retry storm?
  5. задачаДля оплаты и для ленты выберите точку на CAP/PACELC и обоснуйте каждый выбор.
  6. задачаНапишите ADR-02 «consistency vs availability» с решением по обоим потокам и триггером пересмотра.
  7. задачаСпроектируйте graceful degradation ленты при отказе сервиса рекомендаций (что отдаём и с каким кодом).
Разбор ответов
  1. Stateless-сервисы масштабируются добавлением реплик за LB; сложность — в согласовании состояния. Read-реплики масштабируют чтение ценой лага; шарды делят данные по ключу ради записи/объёма ценой кросс-шард запросов и ребалансировки.
  2. CAP описывает выбор только при разделении (P). PACELC добавляет: и без разделения (Else) есть компромисс латентность↔согласованность. Значит синхронная репликация ради C стоит латентности всегда, а не только в аварии.
  3. Retry повторяет вызов; при устойчивом отказе это добивает зависимость. Circuit breaker размыкает цепь после серии ошибок и быстро отдаёт fallback, давая зависимости восстановиться.
  4. Неидемпотентный retry удвоит эффект (двойной платёж). Retry storm — синхронные ретраи без jitter/breaker, лавиной добивающие восстанавливающийся сервис.
  5. Образец: Оплата — CP (PACELC PC/EC): лучше 503, чем двойное списание. Лента — AP (PACELC PA/EL): read-реплика и деградация, лучше устаревшее, чем 500.
  6. Критерий: ADR с контекстом (2 потока), решением CP для оплаты (синхронно, breaker на PSP, 503) и AP для ленты (реплика, деградация, 429), последствиями и триггером пересмотра.
  7. Образец: при недоступности рекомендаций отдаём хронологическую ленту с read-реплики, код 200 (не 500), флаг «персонализация недоступна»; при перегрузке — 429 с Retry-After, без накопления очереди.
