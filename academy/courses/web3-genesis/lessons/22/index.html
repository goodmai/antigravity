IPFS & Pinata: хранение Lit Action, NFT-метаданных и контента

В Web3 нельзя просто «положить файл на сервер» — сервер может исчезнуть, а ссылка протухнуть. IPFS (InterPlanetary File System) решает это через контентную адресацию: адрес файла — это хэш его содержимого (CID), а не путь на чьём-то диске. Pinata — managed-сервис, который надёжно пиннит (хранит и реплицирует) контент в IPFS и отдаёт его через быстрый шлюз.

Что вы получите. После урока вы поймёте, что такое CID и пиннинг, освоите ключевые ручки Pinata (v3 Files API, legacy, шлюз, приватный доступ), и научитесь применять IPFS для трёх главных кейсов: хранение Lit Action, NFT-метаданных (info) и NFT-контента.

1. Основы IPFS: контентная адресация

В обычном вебе адрес location-based: https://site.com/file.png указывает где лежит файл. В IPFS адрес content-based: ipfs://bafkrei… указывает что это за файл — его криптографический хэш. Отсюда свойства:

  • Неизменяемость. Изменил хоть один байт → изменился CID. Старый CID навсегда указывает на старое содержимое (tamper-evidence).
  • Дедупликация. Одинаковый контент = одинаковый CID, где бы его ни загрузили.
  • Пиннинг. IPFS сам по себе не гарантирует, что файл кто-то хранит. Чтобы контент не «уехал» из сети, его надо запиннить на ноде, которая его держит. Это и делает Pinata.
  • Шлюз (gateway). Мост IPFS→HTTP: https://<gateway>/ipfs/<cid> отдаёт контент обычным браузерам.
CIDv0 vs CIDv1. Qm… (base58, CIDv0) — старый формат; bafkrei… / bafybei… (base32, CIDv1) — современный. Pinata v3 возвращает CIDv1. Для совместимости со старыми привязками (например, Lit permitted-action) иногда нужен именно CIDv0.

2. Pinata: функционал и ручки (API)

Pinata экспонирует две разные поверхности. Для хранения файлов нужна Files / Pinning API; Agents API (agents.pinata.cloud) — отдельный продукт для AI-агентов и в этом уроке не используется.

2.1 Аутентификация

При создании ключа (API Keys → New Key) Pinata выдаёт сразу три значения: pinata_api_key, pinata_api_secret и JWT. JWT — рекомендуемый способ (заголовок Authorization: Bearer <JWT>). Шлюз-домен берётся во вкладке Gateways в формате fun-llama-300.mypinata.cloud.

2.2 Ключевые ручки (v3 Files API)

Метод · путьНазначение
POST https://uploads.pinata.cloud/v3/filesзагрузить/запиннить файл (form-data file + network=public/private); ответ { data: { cid, id, size, … } }
GET https://api.pinata.cloud/v3/files/{network}список файлов (фильтры по имени, cid, group, keyvalues; пагинация)
GET …/v3/files/{network}/{id}метаданные одного файла по id
PUT …/v3/files/{network}/{id}обновить имя / keyvalues
DELETE …/v3/files/{network}/{id}удалить (unpin)
POST https://api.pinata.cloud/v3/files/signвременная подписанная ссылка доступа к приватному файлу (signed/expiring URL)
POST/GET …/v3/groups/{network}группы — логическая организация файлов (создать/листинг/добавить)
GET https://<gateway>/ipfs/<cid>чтение через шлюз; для restricted/private — ?pinataGatewayToken=<GATEWAY_KEY>

Legacy-ручки (всё ещё работают): POST /pinning/pinFileToIPFS, POST /pinning/pinJSONToIPFS, GET /data/pinList, DELETE /pinning/unpin/{cid} на api.pinata.cloud; аутентификация заголовками pinata_api_key + pinata_secret_api_key; ответ содержит IpfsHash вместо data.cid.

2.3 SDK pinata (TypeScript)

import { PinataSDK } from 'pinata';

const pinata = new PinataSDK({
  pinataJwt: process.env.PINATA_JWT,
  pinataGateway: 'fun-llama-300.mypinata.cloud',
});

// публичная загрузка → CID
const { cid } = await pinata.upload.public.file(file);
// чтение через шлюз
const data = await pinata.gateways.public.get(cid);
// приватная: загрузка + временная ссылка
const priv = await pinata.upload.private.file(file);
const link = await pinata.gateways.private.createAccessLink({ cid: priv.cid, expires: 3600 });

2.4 curl-пример (v3 + JWT)

curl -X POST https://uploads.pinata.cloud/v3/files \
  -H "Authorization: Bearer $PINATA_JWT" \
  -F "network=public" \
  -F "file=@./metadata.json"
# → { "data": { "cid": "bafkrei…", "id": "…", "size": 512, "is_duplicate": false } }

3. Главные юзеркейсы

3.1 Хранение Lit Action (trustless-код)

Lit Action — это JS-код, который исполняется в сети Lit/Chipotle (TEE) и, например, подписывает минт NFT через PKP. Чтобы код нельзя было подменить незаметно, его пиннят в IPFS и привязывают PKP к CID: только этот байт-в-байт код имеет право подписывать. Изменил код → новый CID → старый PKP теряет право (это и есть гарантия целостности).

В этом проекте экшен claim-signer.action.js уже запинен — CID bafkreicg2b2ttr6p2tqp2rbf6p5dtoq3j4srieatm55ntt2cqh6adlb6ta (см. smartcontracts/lit-actions/cids.json, скилл skills/pinata/). Команда: node tools/pinata/pin.mjs --lit-actions.

3.2 NFT-метаданные (info)

По стандарту ERC-721/1155 tokenURI указывает на JSON-метаданные. Их кладут в IPFS и записывают в контракт как ipfs://<cid> — так информация о токене неизменяема и не зависит от чьего-то сервера. 

{
  "name": "Daskibo Client Pass #1",
  "description": "Soulbound доступ к курсу",
  "image": "ipfs://bafybei…imageCID",
  "attributes": [{ "trait_type": "course", "value": "Web3 Genesis" }]
}

Важно: image тоже должен быть ipfs://…, иначе «децентрализованный» NFT будет ссылаться на смертный HTTP-URL.

3.3 NFT-контент (сам ассет)

Картинка/видео/арт токена. Публичный ассет → network=public и ipfs://<cid>. Приватный/гейтед контент → загрузка как private + выдача временной signed-ссылки только тем, кто прошёл проверку прав (см. POST /v3/files/sign).

IPFS vs BNB Greenfield в нашем стеке. В Daskibo на IPFS/Pinata лежит код Lit Actions и публичные метаданные, а зашифрованный приватный контент курса — в BNB Greenfield (с гейтингом ключа через Lit/Chipotle). Разные носители под разные задачи: неизменяемый публичный код/метаданные vs объёмный приватный контент с платным доступом.

4. Задачи для самостоятельного изучения

  1. Ключи и проверка доступа. Создай в Pinata API-ключ (Admin), сохрани PINATA_JWT и шлюз в .env. Проверь авторизацию: GET https://api.pinata.cloud/v3/files/public с Bearer-токеном должен вернуть 200, а без него — 401.
  2. Первый пин и CID. Запинь любой текстовый файл через POST /v3/files (curl + JWT). Прочитай его обратно через шлюз https://<gateway>/ipfs/<cid>. Залей тот же файл ещё раз — объясни, почему CID не изменился и что значит is_duplicate.
  3. NFT-метаданные. Собери JSON по ERC-721 (name/description/ image/attributes), запинь сначала картинку, подставь её CID в поле image: ipfs://…, затем запинь JSON. Сформируй tokenURI = ipfs://<jsonCID>. Объясни, почему image обязан быть на IPFS.
  4. Приватный контент + signed-ссылка. Загрузи файл как network=private, попробуй открыть его публичным шлюзом (должно не отдаться), затем создай временную ссылку (POST /v3/files/sign или SDK createAccessLink) и открой контент по ней.
  5. Lit Action → CID → целостность. Запинь claim-signer.action.js (node tools/pinata/pin.mjs --lit-actions), зафиксируй CID. Измени в файле один байт (комментарий), перепинь и покажи, что CID сменился. Объясни, как это защищает привязку PKP↔CID.
  6. Группы. Создай группу (POST /v3/groups), загрузи в неё 2–3 файла с указанием group_id, получи листинг группы. Опиши, как группами организовать ассеты одной коллекции/курса.
  7. IPFS vs Greenfield (вывод по проекту). На одной странице обоснуй, что из Daskibo логично хранить на IPFS/Pinata (код экшенов, публичные метаданные), а что — в Greenfield (зашифрованный приватный контент курса), и почему. Сошлись на свойства: неизменяемость, приватность, объём, стоимость, гейтинг доступа.
