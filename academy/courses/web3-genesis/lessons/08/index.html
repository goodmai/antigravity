The Graph — индексация on-chain данных и GraphQL поверх блокчейна

→ продолжение Lesson 03 — JSON-RPC. Там мы выяснили, что блокчейн отдаёт сырые логи через eth_getLogs. Здесь — учимся превращать миллионы этих логов в нормальный GraphQL-API с пагинацией, агрегатами и связями между сущностями.

Реальный dApp редко работает с одним адресом и одним событием. Uniswap хранит ~30 000 пулов, Lens — миллионы постов, ENS — десятки миллионов доменов. Делать eth_getLogs по всему блокчейну на каждый рендер UI — это секунды задержки, бесконечный rate-limit и ноль агрегатов. The Graph решает эту проблему: вы описываете, какие события вас интересуют и в какую модель данных их превращать — а сеть индексеров поднимает GraphQL endpoint, отвечающий за миллисекунды.

Что вы получите. После урока вы умеете: написать subgraph.yaml + GraphQL-схему + AssemblyScript-маппинги для произвольного ERC-20 / ERC-721 / DEX-контракта; развернуть subgraph в Subgraph Studio; опубликовать в Decentralized Network под GRT-кураторов; читать его из фронтенда через graph-client / urql / Apollo; выбирать между The Graph и альтернативами (Subsquid, Goldsky, Ponder, Envio, Substreams).

1. Зачем нужен индексер: проблема «JSON-RPC недостаточно»

Допустим, мы хотим показать «топ-10 холдеров токена USDC». Через сырой RPC задача решается так: 

// Псевдокод — НЕ ДЕЛАЙТЕ ТАК на проде:
const logs = await client.getLogs({
  address: USDC,
  event:   parseAbiItem("event Transfer(address indexed,address indexed,uint256)"),
  fromBlock: 6_082_465n,   // блок деплоя USDC, 2018 год
  toBlock:   "latest",
});
// → 100+ миллионов записей, public RPC отдаст error
// → если даже отдаст, агрегировать sum(value) on the fly = больно

Чем плохо:

  • Публичные RPC ограничивают eth_getLogs: Alchemy — 10k логов за запрос, Infura — 10k, llamarpc — 10k. На 100 млн событий это 10 тысяч запросов.
  • JSON-RPC не умеет JOIN, GROUP BY, ORDER BY. Только «вернуть массив логов в диапазоне блоков».
  • Reorg-handling — на стороне клиента. Если фронт получил лог на блоке N, а блок N был реорганизован, клиент должен сам это заметить и откатить.
  • Пагинация — только по блокам. Курсорная пагинация по «id» транзакции / event-логу невозможна.

Индексер делает три вещи: (1) на этапе синка один раз читает все нужные логи; (2) хранит их в Postgres / ClickHouse, обновляя при реоргах; (3) экспортирует наружу как GraphQL (или SQL). Запросы к нему идут не в EVM, а в обычную реляционную БД — со всеми привычными возможностями.

2. Архитектура The Graph: 4 роли + GRT

┌─────────────────────────────────────────────────────────────────┐
│                     Decentralized Network                        │
│                                                                  │
│   ┌──────────────┐   stake GRT   ┌───────────────┐               │
│   │ Indexers     │◄─────────────►│ Delegators    │               │
│   │ (node ops)   │  share rewards│ (passive)     │               │
│   │ • PoI proofs │               └───────────────┘               │
│   │ • Postgres   │                                               │
│   │ • IPFS sync  │   curation signal  ┌───────────────┐          │
│   │ • graph-node │◄──────────────────►│ Curators      │          │
│   └──────────────┘   bonding curve    │ (signal GRT)  │          │
│         ▲                             └───────────────┘          │
│         │ GraphQL query + payment                                │
│         │ через Gateway (Edge & Node)                            │
│         ▼                                                        │
│   ┌──────────────┐                                               │
│   │ Consumers    │  dApp frontend / backend / analytics          │
│   │ (you)        │                                               │
│   └──────────────┘                                               │
└─────────────────────────────────────────────────────────────────┘
  • Indexers — операторы нод graph-node. Стейкают GRT (минимум 100k), синхронизируют subgraph, отдают запросы. За каждый запрос получают «query fee» в GRT.
  • Curators — указывают, какие subgraph'ы качественные. Сигналят GRT через bonding curve; получают долю query fees тех subgraph'ов, что они «прокурировали».
  • Delegators — стейкают GRT на индексеров без запуска ноды. Получают долю indexer rewards (10–20% APY на 2025).
  • Consumers — разработчики dApp'ов. Платят за запросы в GRT (или USD через Gateway).

На 2025 в сети ~190 активных индексеров, ~30 000 курируемых subgraph'ов, ~3 млрд запросов / день. Подробнее — thegraph.com/explorer.

3. Анатомия subgraph: три файла

Subgraph — это директория с тремя обязательными файлами: 

my-subgraph/
├─ subgraph.yaml          ← манифест: какие контракты, какие события, какие хендлеры
├─ schema.graphql         ← модель данных, которую увидит фронт
├─ src/
│   └─ mappings.ts        ← AssemblyScript: «как из event сделать entity»
├─ abis/
│   └─ ERC20.json         ← ABI контракта
└─ package.json           ← graph-cli + matchstick (тесты)

3.1 subgraph.yaml — манифест

specVersion: 1.0.0
description: USDC transfers + holders aggregation
repository: https://github.com/you/usdc-subgraph
schema:
  file: ./schema.graphql

dataSources:
  - kind: ethereum/contract
    name: USDC
    network: mainnet
    source:
      address: "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"
      abi: ERC20
      startBlock: 6082465        # блок деплоя — экономим часы синка
    mapping:
      kind: ethereum/events
      apiVersion: 0.0.9
      language: wasm/assemblyscript
      file: ./src/mappings.ts
      entities:
        - Account
        - Transfer
      abis:
        - name: ERC20
          file: ./abis/ERC20.json
      eventHandlers:
        - event: Transfer(indexed address,indexed address,uint256)
          handler: handleTransfer
      # blockHandlers:                     # опционально — обработка КАЖДОГО блока
      #   - handler: handleBlock
      #     filter:
      #       kind: call                   # только если был вызов контракта
      # callHandlers:                      # обработка вызовов функций
      #   - function: approve(address,uint256)
      #     handler: handleApprove

Ключевая идея — startBlock. Если поставить 0, индексер пройдёт всю историю блокчейна = часы / дни синка. Указывайте блок деплоя контракта (из Etherscan «Contract Creation») — индексер пропустит всё, что было до.

3.2 schema.graphql — модель данных

type Account @entity {
  id:           Bytes!         # = address
  balance:      BigInt!
  totalSent:    BigInt!
  totalReceived: BigInt!
  txCount:      Int!

  # Reverse lookup — без @derivedFrom Graph будет хранить дубликаты:
  sent:     [Transfer!]! @derivedFrom(field: "from")
  received: [Transfer!]! @derivedFrom(field: "to")
}

type Transfer @entity(immutable: true) {
  id:        Bytes!           # = tx.hash + logIndex
  from:      Account!
  to:        Account!
  value:     BigInt!
  block:     BigInt!
  timestamp: BigInt!
  txHash:    Bytes!
}

type DailyStat @entity {
  id:           String!       # = "YYYY-MM-DD"
  date:         Int!
  transferCount: Int!
  volume:       BigInt!
  uniqueSenders: Int!
}

Аннотации The Graph поверх GraphQL:

  • @entity — сущность хранится в БД. Без неё — это просто тип для query input.
  • @entity(immutable: true) — сущность никогда не обновляется (только создаётся). Индексер хранит её в append-only таблице — быстрее запись и in-place upserts не нужны.
  • @derivedFrom(field: "X") — обратная связь. Не хранится отдельно, а вычисляется при чтении.
  • id: Bytes! — на сети 2024+ предпочтительнее String! (меньше storage, быстрее равенство).

3.3 mappings.ts — AssemblyScript handler

import { BigInt, Bytes, Address } from "@graphprotocol/graph-ts";
import { Transfer as TransferEvent } from "../generated/USDC/ERC20";
import { Account, Transfer, DailyStat } from "../generated/schema";

const ZERO = BigInt.fromI32(0);
const ONE  = BigInt.fromI32(1);

function getOrCreateAccount(address: Bytes): Account {
  let acc = Account.load(address);
  if (acc == null) {
    acc = new Account(address);
    acc.balance = ZERO;
    acc.totalSent = ZERO;
    acc.totalReceived = ZERO;
    acc.txCount = 0;
  }
  return acc;
}

export function handleTransfer(event: TransferEvent): void {
  // 1. Transfer entity (immutable)
  let id = event.transaction.hash.concatI32(event.logIndex.toI32());
  let t  = new Transfer(id);
  t.from      = event.params.from;
  t.to        = event.params.to;
  t.value     = event.params.value;
  t.block     = event.block.number;
  t.timestamp = event.block.timestamp;
  t.txHash    = event.transaction.hash;
  t.save();

  // 2. Account aggregates
  let from = getOrCreateAccount(event.params.from);
  let to   = getOrCreateAccount(event.params.to);

  // mint (from = 0x0) и burn (to = 0x0) — не вычитаем у нулевого адреса
  if (event.params.from.notEqual(Address.zero())) {
    from.balance     = from.balance.minus(event.params.value);
    from.totalSent   = from.totalSent.plus(event.params.value);
  }
  to.balance         = to.balance.plus(event.params.value);
  to.totalReceived   = to.totalReceived.plus(event.params.value);

  from.txCount += 1;
  to.txCount   += 1;
  from.save();
  to.save();

  // 3. Daily stat
  let day = (event.block.timestamp.toI32() / 86400) * 86400;   // округление до суток
  let dayId = day.toString();
  let stat = DailyStat.load(dayId);
  if (stat == null) {
    stat = new DailyStat(dayId);
    stat.date = day;
    stat.transferCount = 0;
    stat.volume = ZERO;
    stat.uniqueSenders = 0;
  }
  stat.transferCount += 1;
  stat.volume = stat.volume.plus(event.params.value);
  stat.save();
}
AssemblyScript — это не TypeScript. Похож синтаксисом, но: нет null (только проверки == null на классах); нет BigInt литералов — BigInt.fromI32(0); нет Date — event.block.timestamp это BigInt секунд; нет async; i32 вместо number. Файл компилируется в WASM, который исполняется индексером в песочнице.

4. CLI workflow: от init до published subgraph

# 1. Установка
npm install -g @graphprotocol/graph-cli

# 2. Авторизация (получите ключ в Subgraph Studio)
graph auth --studio <DEPLOY_KEY>

# 3. Bootstrap нового subgraph из ABI существующего контракта
graph init \
  --product subgraph-studio \
  --from-contract 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48 \
  --network mainnet \
  --abi ./abis/ERC20.json \
  usdc-transfers

# 4. Codegen — генерирует TS-типы из schema.graphql + ABI
cd usdc-transfers
graph codegen

# 5. Build — компилирует AS в WASM
graph build

# 6. Локальное тестирование (matchstick — фреймворк юнит-тестов)
graph test

# 7. Deploy в Subgraph Studio (приватный testnet деплой)
graph deploy --studio usdc-transfers --version-label v0.1.0

# 8. Publish в Decentralized Network (требует ETH + GRT кураторов)
graph publish

Stage 7 (deploy в Studio) бесплатен и нужен для разработки. Stage 8 (publish в DN) — это on-chain транзакция: вы платите газ и signal'ите свой subgraph своим GRT, чтобы привлечь кураторов и индексеров. После публикации у subgraph'а есть и Studio-URL (для dev) и DN-URL (для прод-трафика).

5. Юзеркейс №1 — UI «Top-10 holders» на 60 строк

Минимальный фронт на viem-стиле, никакого framework: 

// queries/topHolders.ts
import { GraphQLClient, gql } from "graphql-request";

const client = new GraphQLClient(
  "https://gateway.thegraph.com/api/<API_KEY>/subgraphs/id/<DEPLOY_ID>",
  // во время разработки — Studio URL:
  // "https://api.studio.thegraph.com/query/<userId>/usdc-transfers/v0.1.0",
);

const TOP_HOLDERS = gql`
  query TopHolders($first: Int!, $skip: Int!) {
    accounts(
      first:   $first
      skip:    $skip
      orderBy: balance
      orderDirection: desc
      where:   { balance_gt: "0" }
    ) {
      id
      balance
      totalReceived
      totalSent
      txCount
    }
  }
`;

export async function getTopHolders(limit = 10, offset = 0) {
  const data = await client.request(TOP_HOLDERS, { first: limit, skip: offset });
  return data.accounts.map((a) => ({
    address: a.id,                       // hex-строка
    balance: BigInt(a.balance) / 10n ** 6n,   // USDC = 6 decimals
    netFlow: BigInt(a.totalReceived) - BigInt(a.totalSent),
    txCount: a.txCount,
  }));
}
// HTML
<ul id="leaderboard"></ul>
<script type="module">
  import { getTopHolders } from "./queries/topHolders.js";
  const top = await getTopHolders(10);
  document.getElementById("leaderboard").innerHTML = top
    .map((h, i) => `<li>#${i + 1} ${h.address.slice(0, 10)}… — ${h.balance} USDC</li>`)
    .join("");
</script>

Тот же запрос можно гонять через fetch (один POST на application/json) или через любой Apollo / urql / SWR / TanStack Query клиент — это просто HTTP+JSON.

6. Юзеркейс №2 — Свечи (OHLC) для DEX-пула

Этот паттерн используют Uniswap Info, Dune, Aave Pulse. На стороне mapping держим «текущую свечу» в памяти БД и обновляем её на каждый swap. 

type Candle @entity {
  id:        String!        # poolId-interval-bucketTimestamp
  pool:      Pool!
  period:    String!        # "1m", "5m", "1h", "1d"
  timestamp: Int!
  open:      BigDecimal!
  high:      BigDecimal!
  low:       BigDecimal!
  close:     BigDecimal!
  volume:    BigDecimal!
  txCount:   Int!
}

# mapping:
export function handleSwap(event: SwapEvent): void {
  let price = computePrice(event.params.sqrtPriceX96);
  let intervals = ["1m", "5m", "1h", "1d"];
  let secs      = [60, 300, 3600, 86400];

  for (let i = 0; i < intervals.length; i++) {
    let bucket = (event.block.timestamp.toI32() / secs[i]) * secs[i];
    let id = event.address.toHex() + "-" + intervals[i] + "-" + bucket.toString();
    let c  = Candle.load(id);
    if (c == null) {
      c = new Candle(id);
      c.pool = event.address;
      c.period = intervals[i];
      c.timestamp = bucket;
      c.open = price; c.high = price; c.low = price; c.close = price;
      c.volume = BigDecimal.fromString("0");
      c.txCount = 0;
    }
    if (price.gt(c.high)) c.high = price;
    if (price.lt(c.low))  c.low  = price;
    c.close   = price;
    c.volume  = c.volume.plus(event.params.amount0.abs().toBigDecimal());
    c.txCount += 1;
    c.save();
  }
}

Фронт читает свечи одним запросом: 

query Candles($pool: Bytes!, $period: String!, $first: Int!) {
  candles(
    first:   $first
    where:   { pool: $pool, period: $period }
    orderBy: timestamp
    orderDirection: desc
  ) {
    timestamp
    open
    high
    low
    close
    volume
  }
}

8. Юзеркейс №4 — Cross-chain индексация без боли

Один subgraph = одна сеть. Чтобы индексировать одно приложение в нескольких сетях (mainnet + Arbitrum + Base + Optimism), есть три подхода: 

# Подход 1: один subgraph, network: matic в subgraph.yaml — копипастим папку
my-app-mainnet/   my-app-arbitrum/   my-app-base/   my-app-optimism/

# Подход 2: subgraph-radio (federation) — один GraphQL endpoint,
# который роутит на N подкорневых subgraph'ов:
import { stitchSchemas } from "@graphql-tools/stitch";

# Подход 3: graph-client — клиентский слой,
# который параллельно бьёт в N subgraph'ов и склеивает ответы:
npx graph-client init
# config.yaml:
sources:
  - name: mainnet
    handler: { graphql: { endpoint: https://api.studio.thegraph.com/.../mainnet/v0.1 } }
  - name: arbitrum
    handler: { graphql: { endpoint: https://api.studio.thegraph.com/.../arbitrum/v0.1 } }
# в коде:
const { mainnet, arbitrum } = sdk;
const both = await Promise.all([
  mainnet.TopHolders({ first: 10 }),
  arbitrum.TopHolders({ first: 10 }),
]);

9. Substreams + Firehose: когда subgraph'а недостаточно

Subgraph хорош для «нормальных» приложений с десятками миллионов событий. Если вы индексируете каждую транзакцию Ethereum («mempool-style» аналитика), классический subgraph упрётся в throughput одного индексера. Для таких задач The Graph выпустил Substreams:

ПараметрSubgraphSubstreams
Язык маппинговAssemblyScriptRust → WASM
ПараллелизмSequentialПараллельная обработка блоков
Sync 1B событийчасы–дниминуты
ИсточникJSON-RPC нодыFirehose (gRPC поток блоков)
ВыходGraphQL + PostgresgRPC stream, sink в любую БД
Сложностьнизкаясредняя — нужен Rust

Substreams удобно использовать как «sink» в свою БД (ClickHouse, BigQuery, Snowflake) — например, для построения дашбордов в Superset / Metabase прямо поверх блокчейн-данных.

10. Альтернативы The Graph

РешениеМодельКогда выбирать
Subsquid SQuid Network + TypeScript processors, ArrowSquid Чистый TS вместо AssemblyScript, нужен Postgres напрямую
Goldsky Managed subgraph + Mirror (real-time sink в свою БД) Не хотите DevOps, нужен webhook на каждое событие
Ponder OSS, Node.js + viem, локальный Postgres / SQLite Маленький subgraph, хотите всё писать в TS, self-host
Envio HyperIndex (TS / ReScript), HyperSync для скорости Multi-chain в одном проекте, нужен 100× sync
Alchemy Subgraphs The Graph-совместимый hosted Уже на Alchemy, не хочется отдельного провайдера
Dune SQL Готовые таблицы, чистый SQL Аналитика, не нужно real-time, дашборды

11. Четыре практические задачи

11.1 Задача №1 — Subgraph для своего ERC-20

Возьмите ERC-20 из Lesson 02 (или любой токен mainnet, например UNI). Напишите subgraph, который индексирует Transfer и поддерживает сущности Account, Transfer, DailyStat. Проверьте:

  • Сумма всех balance ненулевых аккаунтов = totalSupply (минус сожжённое на 0x0).
  • Для каждого аккаунта: balance + totalSent − totalReceived ≡ 0 (с учётом mint/burn).
  • Сумма DailyStat.volume = сумма Transfer.value.

Запуск тестов локально через matchstick: 

// tests/transfer.test.ts
import { assert, test, createMockedFunction } from "matchstick-as";
import { handleTransfer } from "../src/mappings";
import { createTransferEvent } from "./helpers";

test("Transfer mints into a new Account", () => {
  let ev = createTransferEvent(
    /* from */ "0x0000000000000000000000000000000000000000",
    /* to   */ "0x0000000000000000000000000000000000000abc",
    /* val  */ "1000000",
  );
  handleTransfer(ev);

  assert.fieldEquals("Account", "0x0000…abc", "balance", "1000000");
  assert.fieldEquals("Account", "0x0000…abc", "totalReceived", "1000000");
  assert.fieldEquals("DailyStat", "1672531200", "transferCount", "1");
});

11.2 Задача №2 — Курсорная пагинация на >5000 записей

The Graph отдаёт максимум first: 1000 за запрос, а skip работает медленно после >5000. Реализуйте курсорную пагинацию по id_gt: 

async function* allTransfers(client, pageSize = 1000) {
  let lastId = "";
  while (true) {
    const { transfers } = await client.request(gql`
      query ($lastId: Bytes!, $first: Int!) {
        transfers(
          first:   $first
          where:   { id_gt: $lastId }
          orderBy: id
          orderDirection: asc
        ) { id from { id } to { id } value }
      }
    `, { lastId, first: pageSize });

    if (transfers.length === 0) return;
    for (const t of transfers) yield t;
    lastId = transfers[transfers.length - 1].id;
  }
}

// Использование:
let total = 0n;
for await (const t of allTransfers(client)) {
  total += BigInt(t.value);
}
console.log("Total transferred:", total);

Сравните производительность id_gt vs skip:N на 100k записей. Разница — порядки величины.

11.3 Задача №3 — Real-time subscription без WebSocket

The Graph DN не поддерживает GraphQL Subscriptions из коробки. Реализуйте polling-стратегию, которая (a) не дёргает индексер каждую секунду, и (b) гарантирует не пропустить ни одного события: 

async function pollNewTransfers(onTransfer) {
  let lastSeen = await getLastSeenBlock();   // из localStorage / Redis
  while (true) {
    const { _meta, transfers } = await client.request(gql`
      query ($from: Int!) {
        _meta { block { number } hasIndexingErrors }
        transfers(
          first: 100
          where: { block_gt: $from }
          orderBy: block
          orderDirection: asc
        ) { id from { id } to { id } value block timestamp }
      }
    `, { from: lastSeen });

    if (_meta.hasIndexingErrors) console.warn("Subgraph has indexing errors!");

    for (const t of transfers) {
      onTransfer(t);
      lastSeen = Math.max(lastSeen, parseInt(t.block));
    }
    await new Promise((r) => setTimeout(r, 5000));   // 5s
  }
}

_meta — служебная сущность, доступная в любом subgraph; возвращает текущий индексированный блок и флаг ошибок.

11.4 Задача №4 — Сравните latency: RPC vs subgraph vs Substreams

Замерьте время получения «последних 10 swap'ов на Uniswap v3 USDC/ETH 0.05% pool» тремя способами:

  1. eth_getLogs на публичном RPC, диапазон ~10 последних блоков (~2 минуты). Декод Swap-event'а руками.
  2. GraphQL-запрос к Uniswap v3 subgraph (https://api.thegraph.com/subgraphs/name/uniswap/uniswap-v3).
  3. Substreams через substreams.dev на готовый Uniswap-пакет.

Постройте табличку: latency p50 / p95, cold start, стоимость месячного 1 RPS трафика. Эта таблица — основа выбора бэкенда для вашего dApp.

12. Чек-лист «production-ready subgraph»

  • startBlock = блок деплоя контракта. Без него синк займёт сутки.
  • Сущности с большой write-frequency (Transfer, Swap) — помечайте @entity(immutable: true). Это в 2–3 раза быстрее.
  • Все BigInt-арифметические операции — через методы (a.plus(b), a.minus(b)), не операторы.
  • Никогда не делайте contract.read.balanceOf() в маппинге без явной необходимости — это +1 RPC-вызов на каждое событие, синк замедлится в 100 раз.
  • Тестируйте matchstick'ом — это единственный способ поймать нулевые случаи (address(0), integer-overflow) до деплоя.
  • Перед публикацией в DN проверьте _meta.hasIndexingErrors на Studio-версии. Ошибки во время синка останавливают индексер.
  • На фронте — кешируйте на 5–15 секунд (TanStack Query, SWR). Не «вспышивайте» индексер сотнями параллельных запросов на каждый ререндер.
  • Используйте API key с allow-list доменов. Без него ключ может быть украден и использован чужим dApp.
