Sign-In with Ethereum (EIP-4361) и серверная авторизация

→ продолжение Lesson 14 — Transaction UX. Транзакции — это on-chain действия. Логин — это off-chain действие, и у него совсем другие правила.

Sign-In with Ethereum (SIWE), EIP-4361 — стандарт, как авторизовать пользователя по адресу Ethereum без password, email и OAuth. Идея: сервер посылает структурированное сообщение, пользователь подписывает его кошельком, сервер проверяет подпись и создаёт сессию. Один протокол — одинаковая авторизация на тысячах dApp.

Что вы получите. После урока вы умеете: писать корректное SIWE-сообщение со всеми обязательными полями; реализовать flow nonce → sign → verify → session на сервере; проверять подписи EOA и ERC-1271 контрактных кошельков; защищаться от replay-атак, phishing и domain-spoofing; интегрировать siwe или viem.verifyMessage в Next.js/Express.

1. Зачем не использовать password

Password — это shared secret. Утечка БД = катастрофа: hash + rainbow table + GPU = миллионы паролей раскрыты. OAuth решает часть проблем, но завязывает на Google/Apple/Meta (privacy concerns, Account Takeover через email-recovery).

Криптокошелёк — это асимметричный ключ. Сервер видит только публичный адрес и подпись; никаких секретов хранить не нужно. Утечка БД сессий не даёт ничего, кроме списка адресов. Это passwordless по дизайну.

2. Структура SIWE-сообщения

EIP-4361 определяет точный формат строки, которую видит пользователь в кошельке. Любое отклонение от него — и кошельки не покажут «красивое» сообщение, а dApp откроет уязвимость phishing'а. 

example.com wants you to sign in with your Ethereum account:
0x9D85ca56217D2bb651b00f15e694EB7E713637D4

Welcome to Example. By signing in you accept our Terms of Service:
https://example.com/tos

URI: https://example.com/login
Version: 1
Chain ID: 1
Nonce: 32891756
Issued At: 2026-05-14T12:34:56.789Z
Expiration Time: 2026-05-14T13:04:56.789Z
Not Before: 2026-05-14T12:34:56.789Z
Request ID: r_8b4d3f
Resources:
- ipfs://Qm...
- https://example.com/my/asset

Обязательные и опциональные поля:

Phishing-protection. Метамаск визуально подсвечивает domain в SIWE-сообщении. Если пользователь видит «evil.com wants you to sign in», он сразу заметит подмену. С произвольной строкой через personal_sign такой защиты нет.

3. Полный flow на клиенте

// src/useSiwe.ts
import { useAccount, useSignMessage, useChainId } from 'wagmi'
import { SiweMessage } from 'siwe'

export function useSiwe() {
  const { address } = useAccount()
  const chainId     = useChainId()
  const { signMessageAsync } = useSignMessage()

  const signIn = async () => {
    if (!address) throw new Error('connect wallet first')

    // 1. Запросить nonce у бэка (одноразовый, привязан к сессии)
    const { nonce } = await fetch('/api/siwe/nonce').then(r => r.json())

    // 2. Сконструировать SIWE-сообщение
    const message = new SiweMessage({
      domain:    window.location.host,
      address,
      statement: 'Welcome to MyApp. Sign in to continue.',
      uri:       window.location.origin,
      version:   '1',
      chainId,
      nonce,
      issuedAt:  new Date().toISOString(),
      expirationTime: new Date(Date.now() + 30 * 60 * 1000).toISOString(),  // +30 мин
    })

    const messageStr = message.prepareMessage()

    // 3. Попросить пользователя подписать (виден в MetaMask)
    const signature = await signMessageAsync({ message: messageStr })

    // 4. Отправить на бэк для verify
    const res = await fetch('/api/siwe/verify', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ message: messageStr, signature }),
    })

    if (!res.ok) throw new Error('SIWE verify failed: ' + (await res.text()))
    return res.json()  // { user: {...}, sessionId, ... }
  }

  return { signIn }
}

4. Серверная верификация (Node/Express)

// server/siwe.ts
import express from 'express'
import session from 'express-session'
import { SiweMessage, generateNonce } from 'siwe'

const app = express()
app.use(express.json())
app.use(session({
  secret: process.env.SESSION_SECRET!,
  resave: false,
  saveUninitialized: true,
  cookie: { sameSite: 'lax', httpOnly: true, secure: process.env.NODE_ENV === 'production' },
}))

// 1. nonce — сервер генерирует и привязывает к сессии
app.get('/api/siwe/nonce', (req, res) => {
  req.session.nonce = generateNonce()      // криптостойкий случайный 17-байтовый id
  res.json({ nonce: req.session.nonce })
})

// 2. verify
app.post('/api/siwe/verify', async (req, res) => {
  try {
    const { message, signature } = req.body
    const siwe = new SiweMessage(message)
    const result = await siwe.verify({
      signature,
      nonce: req.session.nonce,            // обязательно проверяем тот же nonce
      domain: req.hostname,                // защита от cross-domain атак
    })

    if (!result.success) {
      return res.status(401).json({ error: result.error?.type })
    }

    // 3. Подпись валидна — создаём сессию
    req.session.siwe = siwe                // сохраняем для будущих authenticated endpoint'ов
    req.session.nonce = undefined          // одноразовый — больше использовать нельзя
    res.json({ user: { address: siwe.address }, ok: true })
  } catch (err: any) {
    res.status(400).json({ error: err.message })
  }
})

// 4. authenticated endpoint
app.get('/api/me', (req, res) => {
  if (!req.session.siwe) return res.status(401).json({ error: 'not authenticated' })
  if (new Date(req.session.siwe.expirationTime ?? 0) < new Date()) {
    return res.status(401).json({ error: 'session expired' })
  }
  res.json({ address: req.session.siwe.address })
})

// 5. logout
app.post('/api/siwe/logout', (req, res) => {
  req.session.destroy(() => res.json({ ok: true }))
})

app.listen(3000)

5. Верификация через viem (без npm-пакета siwe)

Если у вас уже есть viem на бэке (например, Next.js API route с Node), можно проверить подпись и без отдельной библиотеки siwe — но придётся руками парсить сообщение и проверять nonce/expiration. 

// server/api/siwe/verify.ts (Next.js Edge / Node)
import { createPublicClient, http, verifyMessage } from 'viem'
import { mainnet } from 'viem/chains'

const client = createPublicClient({ chain: mainnet, transport: http() })

export async function POST(req: Request) {
  const { message, signature } = await req.json()

  // 1. Криптографическая проверка подписи (EOA + ERC-1271)
  const valid = await client.verifyMessage({
    address: extractAddressFromSiwe(message),
    message,
    signature,
  })
  if (!valid) return Response.json({ error: 'bad signature' }, { status: 401 })

  // 2. Парсинг полей SIWE-сообщения
  const fields = parseSiwe(message)

  // 3. Защита: nonce совпадает с серверным
  if (fields.nonce !== session.nonce) {
    return Response.json({ error: 'bad nonce' }, { status: 401 })
  }
  // 4. Защита: expiration не истёк
  if (new Date(fields.expirationTime) < new Date()) {
    return Response.json({ error: 'expired' }, { status: 401 })
  }
  // 5. Защита: domain корректный
  if (fields.domain !== req.headers.get('host')) {
    return Response.json({ error: 'bad domain' }, { status: 401 })
  }

  // 6. Создать сессию (JWT, cookie, etc.)
  return Response.json({ user: { address: fields.address }, ok: true })
}
verifyMessage и ERC-1271. viem.verifyMessage автоматически делает fallback на ERC-1271, если адрес — контракт. Это значит: Safe-мультисиги, Coinbase Smart Wallet, Argent — все пройдут проверку без специального кода. Без этого fallback'а ваш сервис «не пускает» 5-10% пользователей (растущая доля smart wallets).

6. Атаки и защита

6.1 Replay-атака

Атакующий перехватывает SIWE-сообщение + signature и отправляет на сервер повторно. Защита: nonce одноразовый. После успешного verify сервер обнуляет session.nonce; следующая попытка с тем же nonce упадёт. Дополнительно — expirationTime: даже если nonce сохранился, после expiration подпись недействительна.

6.2 Cross-domain атака

Атакующий заводит сайт evil.com, заставляет пользователя подписать SIWE с domain: example.com. Если пользователь невнимателен — он подписывает «логин на example.com», находясь на evil.com. Затем атакующий приносит подпись на example.com.

Защита: на сервере проверять, что domain в сообщении совпадает с req.hostname. И/или прикреплять nonce к session cookie, который выдаёт ТОТ ЖЕ домен — тогда атакующий не сможет запросить корректный nonce.

6.3 Phishing — фальшивый SIWE

Атакующий сайт показывает SIWE-сообщение с domain example.com, пользователь невнимательно подписывает. Тут защита — на стороне кошелька: MetaMask показывает реальный window.location.host и сопоставляет с domain в сообщении. Если не совпадает — warning.

6.4 Privilege escalation через resources

SIWE поддерживает поле Resources: список URI, которые пользователь авторизует. Это удобно для делегирования (Permissions capability URLs). Но сервер обязан проверять, что требуемый ресурс есть в списке — иначе подпись на «логин» даст доступ ко всему API.

7. Сессионная стратегия

После успешного verify сервер должен создать сессию. Три популярных подхода:

  • Cookie + server-side session store (express-session + Redis). Лучший вариант для классических server-rendered приложений. HttpOnly + Secure + SameSite=Lax — стандартный набор защит.
  • JWT в httpOnly cookie. Сервер не хранит state; JWT включает { address, exp }. Проще scaling, но logout-всех-устройств требует чёрного списка.
  • Refresh + access JWT. Production-grade: короткий access (15 мин), длинный refresh (7 дней). Refresh ротируется при каждом использовании — компрометация одного устройства не даёт долгий доступ.

Задача 4 — Защита от replay и cross-domain

# Расширьте verify-handler из задачи 1 четырьмя проверками:

app.post('/api/siwe/verify', async (req, res) => {
  const { message, signature } = req.body
  const siwe = new SiweMessage(message)
  const result = await siwe.verify({ signature, nonce: req.session.nonce })

  // 1. Криптография
  if (!result.success) return res.status(401).json({ error: 'bad signature' })

  // 2. Domain
  if (siwe.domain !== req.hostname) {
    return res.status(401).json({ error: 'domain mismatch' })
  }

  // 3. Chain ID — мы хотим только mainnet (или ваш список)
  if (siwe.chainId !== 1) {
    return res.status(401).json({ error: 'unsupported chain' })
  }

  // 4. Expiration
  if (siwe.expirationTime && new Date(siwe.expirationTime) < new Date()) {
    return res.status(401).json({ error: 'expired' })
  }

  // 5. Replay-защита: nonce одноразовый, после use обнуляем
  req.session.siwe = siwe
  req.session.nonce = undefined
  res.json({ ok: true, address: siwe.address })
})

10. ENS — суверенная идентичность поверх кошелька

SIWE доказывает «я владею адресом 0xa1b2…». Но адрес нечитаем. ENS (Ethereum Name Service) — базовый слой суверенной идентичности Web3: он заменяет шестнадцатеричный адрес на читаемое имя vitalik.eth. В отличие от классического DNS, арендуемого на серверах провайдера, ENS-имя — это NFT (ERC-721), собственность пользователя, устойчивая к цензуре. В SIWE-логине ENS-имя обычно показывают в UI вместо адреса (через publicClient.getEnsName({ address })), но доверять по-прежнему нужно подписи, а не имени.

10.1 Регистрация: commit → reveal (защита от frontrunning)

Регистрация двухфазная — чтобы боты-снайперы не перехватили имя, увидев его в mempool:

  • Commit — пользователь отправляет в сеть только криптографический хэш (имя + секрет). Намерение зафиксировано, имя не раскрыто.
  • Reveal — после короткой задержки безопасности отправляется финальная транзакция с открытым именем; контракт регистрирует домен и оплату.
// Псевдокод фазы commit/reveal через ETHRegistrarController
bytes32 commitment = controller.makeCommitment(
    "myapp", owner, duration, secret, resolver, data, reverseRecord, ownerControlledFuses
);
controller.commit(commitment);                 // фаза 1: только хэш
// ...ждём minCommitmentAge (защита от frontrunning)...
controller.register{value: price}(             // фаза 2: раскрытие + оплата
    "myapp", owner, duration, secret, resolver, data, reverseRecord, ownerControlledFuses
);

Экономика прогрессивна: 3-символьные имена ≈ $640/год, 4-символьные ≈ $160/год, от 5 символов ≈ $5/год (в эквиваленте ETH).

10.2 Архитектура: Registry · Registrar · Resolver

  • Registry — реестр прав: кто владеет именем и какой у него resolver.
  • Registrar — контракт выпуска имён в зоне .eth.
  • Resolver — трансляция имени в адреса множества блокчейнов (включая Bitcoin, Dogecoin) или в ссылку на децентрализованный контент в IPFS.

10.3 CCIP-Read (EIP-3668) — бесплатные L2-субдомены

CCIP-Read (EIP-3668) позволяет L1-контракту безопасно запрашивать данные вне сети (на сервере проекта или в L2 вроде Base) через криптографически проверяемый шлюз. Благодаря этому проекты массово и почти бесплатно раздают защищённые субдомены (name.base.eth), не платя газ за каждую запись в L1 и сохраняя безопасность основного блокчейна. Для приложения с SIWE это означает: каждому пользователю можно выдать читаемое имя alice.myapp.eth без затрат на ончейн-регистрацию.

Связь с авторизацией. ENS-имя — это удобство и идентичность, а не право. Reverse-record (addr → name) может быть не установлен или указывать на чужое имя; всегда выполняйте forward-resolution (name → addr) и сверяйте с адресом, подписавшим SIWE-сообщение.
