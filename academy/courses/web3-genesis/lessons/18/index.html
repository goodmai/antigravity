Multichain & Bridges: L1↔L2 и кросс-чейн протоколы

Блокчейны по своей природе изолированы: Ethereum не «знает» о Solana, а Arbitrum не может напрямую прочитать состояние Optimism. При этом ценность сосредоточена на разных цепочках — огромная ликвидность заперта в Ethereum L1, быстрые и дешёвые L2 пусты без мостов. Кросс-чейн мосты — это инфраструктура для передачи токенов и сообщений между изолированными блокчейнами, и одновременно — самая атакуемая точка всего экосистемы Web3.

В этом уроке мы разберём архитектуру мостов от фундамента: доверенные и trustless варианты, нативные мосты Optimism и Arbitrum, и расскажем, почему два крупнейших взлома в истории Web3 (Ronin $625M и Wormhole $320M) стали возможными.

Что вы получите. После этого урока вы сможете: объяснить разницу между lock-and-mint и burn-and-mint; сказать, почему вывод из Optimism занимает 7 дней; объяснить роль sequencer и fraud proof; сравнить нативные мосты с LayerZero и CCIP; назвать конкретную причину взлома Ronin Bridge.

1. Зачем нужны мосты

Ethereum L1 — самый безопасный и ликвидный блокчейн, но и самый дорогой: в периоды нагрузки gas fee за обычный swap превышает $50–100. Layer 2 решения (Optimism, Arbitrum, Base, Scroll, zkSync) предлагают в 10–100 раз более дешёвые транзакции, наследуя безопасность Ethereum через публикацию данных и proof'ов в L1.

Чтобы использовать DeFi-протоколы на L2, пользователи должны перевести туда свои активы. Здесь вступают мосты: они берут актив на одной цепочке и «создают» его эквивалент на другой.

1.1 Фундаментальная проблема

Блокчейн — детерминированная машина состояний. Она не может самостоятельно прочитать состояние другой цепочки (это нарушило бы детерминизм). Мост — это внешняя система, которая:

  1. Наблюдает события на цепочке A (например, депозит ETH)
  2. Формирует доказательство того, что событие произошло
  3. Предъявляет это доказательство контракту на цепочке B
  4. Контракт на B минтит эквивалентный актив

Всё различие между типами мостов сводится к вопросу: кто формирует доказательство, и как оно верифицируется?

2. Типы мостов

3. Optimism (OP Stack): депозиты и выводы

Optimism — это Optimistic Rollup. Батчи транзакций публикуются в Ethereum L1 как calldata (или blob после EIP-4844), а корректность батча по умолчанию принимается оптимистически — без немедленного доказательства.

3.1 L1 → L2: депозит

Депозит ETH из Ethereum в Optimism — быстрый, потому что данные идут «вниз» (от родительской цепочки к дочерней): 

// На Ethereum L1: пользователь вызывает OptimismPortal
interface IOptimismPortal {
    function depositTransaction(
        address _to,          // адрес получателя на L2
        uint256 _value,       // ETH в wei
        uint64  _gasLimit,    // газ для выполнения на L2
        bool    _isCreation,  // true если деплой контракта
        bytes   calldata _data
    ) external payable;
}

// Пример: перевести 0.1 ETH себе на Optimism
OptimismPortal(0xbEb5Fc579115071764c7423A4f12eDde41f106Ed).depositTransaction{
    value: 0.1 ether
}(
    msg.sender,   // тот же адрес на L2
    0.1 ether,
    100_000,      // газ на L2
    false,
    ""
);
// Средства появятся на L2 через ~1-3 минуты (1 подтверждение L1)

3.2 L2 → L1: вывод и 7-дневный challenge period

Вывод средств из Optimism обратно в Ethereum занимает 7 дней. Это не техническое ограничение, а параметр безопасности: 

// ── Шаг 1 (L2): инициировать вывод ──────────────────────────────────────────
// Вызывается на L2
L2ToL1MessagePasser.initiateWithdrawal(
    address _target,    // получатель на L1
    uint256 _gasLimit,
    bytes   calldata _data
);
// Транзакция включается в батч и публикуется в L1

// ── Шаг 2 (L1, ~7 дней спустя): доказать вывод ───────────────────────────────
// После 7-дневного окна challenge period истёк
OptimismPortal.proveWithdrawalTransaction(
    Types.WithdrawalTransaction memory _tx,
    uint256 _l2OutputIndex,
    Types.OutputRootProof calldata _outputRootProof,
    bytes[] calldata _withdrawalProof
);

// ── Шаг 3 (L1): финализировать вывод ─────────────────────────────────────────
OptimismPortal.finalizeWithdrawalTransaction(
    Types.WithdrawalTransaction memory _tx
);
// ETH/токены поступают на адрес получателя на L1

Зачем 7 дней? За это время любой наблюдатель (watcher) может заметить мошеннический батч и подать dispute (fault proof). Если fraud proof подтверждён — батч отклонён, sequencer слэшится, мошеннический вывод не проходит. Если за 7 дней никто не возразил — батч считается финальным.

Fault Proofs в Optimism (Bedrock+). До 2024 года Optimism работал без on-chain fault proofs — security council мог вручную вмешаться. В 2024 году запущены permissionless fault proofs: теперь любой может оспорить батч, отправив залог и играя в «bisection game» — пошаговое сужение спорного вычисления до одного шага EVM.

4. Arbitrum Nitro: ArbOS, fraud proofs, inbox/outbox

Arbitrum Nitro — технически более сложная система, чем OP Stack. Ключевые отличия:

КомпонентЧто делает
ArbOS «Операционная система» поверх Geth. Добавляет precompiles для кросс-чейн сообщений, обрабатывает L1→L2 сообщения, управляет fee market
Geth fork (go-ethereum) Arbtirum буквально форкнул geth и добавил ArbOS как слой. Это даёт полную EVM-совместимость без адаптации инструментов
Sequencer Принимает транзакции пользователей, упорядочивает их, публикует в L1 Inbox. Централизован у Offchain Labs, но не может цензурировать навсегда — есть forced inclusion через L1
Inbox (DelayedInbox) Смарт-контракт на L1. Принимает L1→L2 сообщения (депозиты). Если sequencer игнорирует сообщение 24ч — любой может его включить принудительно
Outbox Смарт-контракт на L1. Хранит merkle-root завершённых L2→L1 сообщений. После финализации RBlock пользователи могут исполнить свои выводы
Interactive Fraud Proof (Bisection) Если validator оспаривает RBlock, запускается on-chain игра: спорный диапазон вычислений делится пополам итеративно, пока не остаётся один шаг — его исполняет L1

5. Нативный мост vs сторонние мосты

Для каждого L2 существует нативный (официальный) мост — самый безопасный вариант, но с ограничениями. Сторонние мосты предлагают скорость и дополнительные функции за счёт другого профиля доверия.

Протокол Тип Скорость вывода Механизм Риск
Optimism Native Bridge Оптимистичный 7 дней Fault proofs, L1 finality Минимальный (=L1 security)
Arbitrum Native Bridge Оптимистичный ~7 дней Interactive fraud proofs Минимальный (=L1 security)
Hop Protocol Liquidity network Минуты AMM + hTokens + bonders Smart contract risk, bonder risk
Across Protocol Liquidity network Секунды–минуты LP pool + UMA oracle для settlement Oracle risk, LP risk
Stargate (LayerZero) Unified liquidity + оракульный Минуты LayerZero messaging + SGT/USDC pools Relayer/Oracle risk
LayerZero Messaging protocol Минуты Ultra-Light Node + Oracle + Relayer Оба oracle и relayer не должны быть скомпрометированы
CCIP (Chainlink) Messaging + token transfer Минуты Decentralized Oracle Network + Risk Management Network Oracle network risk (Chainlink DON)
Trilemma мостов. Хорошее резюме от Li Jin (Connext): мост не может одновременно быть trustless, extensible и generalizable. Нативные мосты выбирают trustless + generalizable, теряя скорость. Liquidity networks выбирают скорость, допуская дополнительное доверие.

6. Безопасность мостов: два крупнейших взлома

6.1 Ronin Bridge — $625 млн (Март 2022)

Ronin — это sidechain (не rollup) для игры Axie Infinity, разработан Sky Mavis. Мост Ronin управлялся multisig из 9 валидаторов: для подтверждения вывода требовалось 5 из 9 подписей.

Что произошло:

  1. Sky Mavis временно передала 4 голоса AxieDAO для снятия нагрузки с пользователей ещё в ноябре 2021
  2. В ноябре 2021 AxieDAO перестала использовать эти ключи, но Sky Mavis не отозвала разрешение
  3. В марте 2022 атакующий (предположительно Lazarus Group, КНДР) скомпрометировал 4 ключа Sky Mavis через spear-phishing PDF
  4. Вместе с 4 ключами AxieDAO (которые ещё имели разрешение) — получилось 5 из 9: кворум достигнут
  5. Атакующий вывел $625M в 2 транзакциях; атака оставалась незамеченной 6 дней
// Упрощённая схема уязвимости:
// Валидаторы: SkyMavis(4) + AxieDAO(4) + Independent(1)
//
// Требуется: 5 из 9
//
// AxieDAO сохранила разрешение → итого у атакующего: 4 + 1 (AxieDAO) = 5 ✓
//
// Атакующий подписал:
// withdrawETH(173,600 ETH, attacker_address)  ← $592M
// withdrawUSDC(25,500,000 USDC, attacker_address)  ← $25M
//
// Защита которой НЕ было:
// - Нет мониторинга крупных выводов
// - Нет time-lock на крупные транзакции
// - Не отозваны устаревшие разрешения
// - 6 дней до обнаружения

Урок: централизованный multisig — это одна точка отказа, если ключи управляются небрежно. Для мостов с миллиардами TVL необходим мониторинг аномалий в реальном времени, time-lock'и на крупные выводы, и регулярный аудит активных разрешений.

6.2 Wormhole — $320 млн (Февраль 2022)

Wormhole — это протокол кросс-чейн сообщений, поддерживающий Solana, Ethereum и другие цепочки. Мост Ethereum↔Solana позволял депонировать ETH на Ethereum, получать wETH на Solana, и обратно.

Уязвимость в коде Solana: 

// Уязвимая функция verify_signatures() на Solana (псевдокод):
//
// Solana аккаунты имеют поле owner — программа, которая "владеет" аккаунтом.
// Только owner-программа может изменять данные аккаунта.
//
// ❌ УЯЗВИМЫЙ КОД (упрощённо):
fn verify_signatures(signature_set: &AccountInfo) -> Result<()> {
    // Проверяем, что signature_set создан ЭТОЙ программой
    // НО: использовался устаревший системный вызов solana_program::sysvar
    // который НЕ проверял, что аккаунт принадлежит правильной программе
    if signature_set.owner != sysvar::id() { // ← НЕПРАВИЛЬНАЯ проверка!
        return Err(BridgeError::InvalidSignatureSet);
    }
    // Считаем подписи "верифицированными" на основе этого аккаунта
    // ...
}
//
// Атакующий:
// 1. Создал фейковый аккаунт, имитирующий SignatureSet с "верифицированными" подписями
// 2. Передал его в mint_wrapped_eth() вместо настоящего
// 3. Функция не проверила реальные guardian signatures
// 4. Контракт выпустил 120,000 wETH ($320M) "из воздуха"
// 5. Атакующий вывел wETH → ETH на Ethereum

Урок: проверка авторизации в Solana — не то же самое, что в EVM. В Solana критически важно проверять owner аккаунта (какая программа им управляет), а не только pubkey. Уязвимость типа «account confusion» — специфична для Solana-архитектуры.

7. ERC-20 canonical token на L2: lock-and-mint vs burn-and-mint

Когда токен «переезжает» на L2, существует две принципиально разные архитектуры:

7.1 Lock-and-Mint

Токены на L1 блокируются в контракте-мосте, на L2 минтится «обёрнутый» токен в соотношении 1:1. 

// L1: пользователь блокирует USDC
ERC20Bridge.deposit(USDC, amount, l2Recipient);
// USDC переходит в кастодию bridge contract
// → Bridge публикует событие в L1

// L2: BridgedUSDC контракт получает сообщение и минтит
BridgedUSDC.mint(l2Recipient, amount);
// Теперь у пользователя есть "wrapped USDC" на L2

// При выводе:
BridgedUSDC.burn(l2Recipient, amount);
// → сообщение идёт в L1 → ERC20Bridge разблокирует USDC

Риск: если мост взломан — все заблокированные токены на L1 под угрозой. Именно так работал Ronin Bridge, и Wormhole ETH Bridge.

7.2 Burn-and-Mint (Canonical Token)

Canonical-подход: эмитент токена сам деплоит контракт на L2 и даёт Bridge право минтить/сжигать. Нет кастодии — нет и риска «кражи запасов». 

// Circle's Cross-Chain Transfer Protocol (CCTP) для USDC:
// На L1:
TokenMessenger.depositForBurn(
    amount,           // количество USDC
    ARBITRUM_DOMAIN,  // domain ID целевой цепочки
    mintRecipient,    // адрес получателя на Arbitrum
    USDC_L1_ADDRESS
);
// Circle сжигает USDC на L1 (burnFrom)
// Публикует attestation в Circle's API

// На L2 (Arbitrum):
MessageTransmitter.receiveMessage(
    message,       // raw message bytes
    attestation    // Circle's signature
);
// USDC контракт на Arbitrum минтит нативный USDC
// Никакой кастодии на L1 — нет риска кражи запасов

7.3 OptimismPortal StandardBridge

OP Stack поставляет стандартизированный bridge для ERC-20. Принцип — lock-and-mint, но через безопасный нативный контракт: 

// На L1: StandardBridge
interface IL1StandardBridge {
    function bridgeERC20(
        address _localToken,   // адрес токена на L1
        address _remoteToken,  // адрес wrapped токена на L2
        uint256 _amount,
        uint32  _minGasLimit,
        bytes   calldata _extraData
    ) external;
}

// Сначала approve:
IERC20(localToken).approve(L1_STANDARD_BRIDGE, amount);
IL1StandardBridge(L1_STANDARD_BRIDGE).bridgeERC20(
    DAI_L1,      // DAI на Ethereum
    DAI_L2,      // Optimism DAI (L2StandardERC20)
    100e18,      // 100 DAI
    200_000,
    ""
);

// DAI заблокирован в L1StandardBridge
// На Optimism L2 автоматически минтится 100 OVM_DAI

8. Как работает LayerZero (детальнее)

LayerZero — это не мост, а messaging protocol: он передаёт произвольные сообщения между цепочками. Stargate и другие мосты строятся поверх него. 

// Упрощённая архитектура LayerZero V2:
//
// Отправитель (chain A)  →  Endpoint.send()
//                               │
//                               │  Пакет с payload
//                               ▼
//                          DVN (Decentralized Verifier Network)
//                          — независимые верификаторы
//                          — подтверждают хэш пакета on-chain
//                               │
//                          Executor
//                          — доставляет пакет на chain B
//                               │
//                               ▼
//                         Endpoint.lzReceive() → ваш контракт
//
// Безопасность: атакующий должен скомпрометировать
// majority DVN-верификаторов И executor одновременно

9. Практика: депозит ETH в Optimism через контракт

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface IOptimismPortal {
    function depositTransaction(
        address _to,
        uint256 _value,
        uint64  _gasLimit,
        bool    _isCreation,
        bytes   calldata _data
    ) external payable;
}

interface IOptimismPortalV2 {
    /// @notice Читает статус вывода
    function provenWithdrawals(bytes32 withdrawalHash)
        external view
        returns (
            bytes32 outputRoot,
            uint128 timestamp,
            uint128 l2OutputIndex
        );

    function finalizedWithdrawals(bytes32 withdrawalHash)
        external view returns (bool);
}

/// @title OptimismDepositor — утилита для L1→L2 депозитов
contract OptimismDepositor {
    // Ethereum Mainnet: OptimismPortal2
    IOptimismPortal constant PORTAL =
        IOptimismPortal(0xbEb5Fc579115071764c7423A4f12eDde41f106Ed);

    IOptimismPortalV2 constant PORTAL_V2 =
        IOptimismPortalV2(0xbEb5Fc579115071764c7423A4f12eDde41f106Ed);

    event DepositInitiated(address indexed to, uint256 value);

    /// @notice Депозит ETH в Optimism
    /// @param _l2Recipient  Получатель на L2 (может быть тем же адресом)
    /// @param _l2GasLimit   Газ для исполнения транзакции на L2
    function depositETH(address _l2Recipient, uint64 _l2GasLimit)
        external payable
    {
        require(msg.value > 0, "Send ETH");

        PORTAL.depositTransaction{value: msg.value}(
            _l2Recipient,
            msg.value,
            _l2GasLimit,
            false,
            ""
        );

        emit DepositInitiated(_l2Recipient, msg.value);
    }

    /// @notice Депозит с произвольным calldata (например, вызов контракта на L2)
    /// @param _l2Contract  Контракт на L2
    /// @param _calldata    Encoded function call
    function depositWithCall(
        address _l2Contract,
        bytes calldata _calldata,
        uint64 _l2GasLimit
    ) external payable {
        PORTAL.depositTransaction{value: msg.value}(
            _l2Contract,
            msg.value,
            _l2GasLimit,
            false,
            _calldata
        );
    }

    /// @notice Проверить статус вывода
    /// @param withdrawalHash  keccak256 хэш WithdrawalTransaction struct
    function isWithdrawalFinalized(bytes32 withdrawalHash)
        external view returns (bool)
    {
        return PORTAL_V2.finalizedWithdrawals(withdrawalHash);
    }
}
