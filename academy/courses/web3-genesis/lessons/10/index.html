Модуль II · Lesson 10 · gas · storage packing · via-ir

Gas optimisation — storage packing, calldata vs memory, --via-ir

→ продолжение Lesson 09 — Security: Reentrancy. Сначала пишем безопасно, потом оптимизируем. Никогда наоборот.

На Ethereum-mainnet один SSTORE из нуля в ненулевое значение стоит 22 100 gas (Cancun, 2024). При gas price 30 gwei и цене ETH $3 500 — это ≈ $2.30 за одну запись в storage. Сложный DeFi-протокол с десятками SSTORE в одной транзакции может стоить пользователю $20–50 в плохой день. Поэтому gas optimisation — не «преждевременная оптимизация», а UX-фича: дешёвый контракт = больше пользователей.

Что вы получите. После урока вы умеете: читать gas-отчёт от forge test --gas-report; паковать storage переменные так, чтобы каждый slot использовался полностью; знать, когда calldata экономит газ относительно memory; включить и понять --via-ir компилятор; оценить trade-offs unchecked, кастомных ошибок и immutable/constant.

1. Цена опкодов EVM — что дороже всего

EVM назначает цену каждому опкоду. Большинство стоят 3 газа; SLOAD — 2100 (cold) / 100 (warm); SSTORE — самый дорогой. Понимание этих цен позволяет писать оптимальный код без угадывания.

2. Storage packing — главная техника

EVM хранит каждый slot как 32 байта (256 бит). Если в structure объявлены несколько маленьких переменных подряд, Solidity пакует их в один slot. Это значит: запись/чтение нескольких полей могут стоить одного SSTORE/SLOAD вместо нескольких. 

// BAD: 3 slot'а
struct UserBad {
    uint256 amount;        // slot 0 — 32 байта
    address user;          // slot 1 — 20 байт + 12 пустых
    uint96 nonce;          // slot 2 — 12 байт + 20 пустых (!)
}

// GOOD: 2 slot'а (uint96 + address вместе = 32 байта)
struct UserGood {
    uint256 amount;        // slot 0 — 32 байта
    uint96 nonce;          // slot 1 — 12 байт ─┐
    address user;          // slot 1 — 20 байт ─┘ ИТОГО 32 байта
}

// LEGENDARY: 1 slot, если amount уместится в 128 бит
struct UserPacked {
    uint128 amount;        // slot 0 — 16 байт ─┐
    uint96 nonce;          // slot 0 — 12 байт ─┤ 32 байта
    uint32 reserved;       // slot 0 — 4 байта ─┘
    address user;          // slot 1 — 20 байт (не помещается с теми)
}

Размер типа значит цену. uint8, uint16, uint32, uint64, uint96, uint128, uint256, bool (1 байт), address (20 байт), bytes32 (32 байта), enum (1 байт обычно) — все могут паковаться.

Важно: цена чтения «маленького» типа. Когда вы читаете uint8, EVM всё равно делает SLOAD на 32 байта и потом маскирует нужный байт. Поэтому отдельно uint8 в slot'е ДОРОЖЕ, чем uint256. Маленькие типы выгодны только в parking-режиме: несколько переменных в одном slot'е.

2.1 Counter-pattern: лучше использовать uint256, если не пакуется

// BAD: uint8 в отдельном slot'е
contract A {
    uint8 public count;      // slot 0, но 31 байт пустует
}

// GOOD: uint256 в отдельном slot'е
contract B {
    uint256 public count;    // slot 0, используется полностью
    // Запись и чтение — без маскирования
}

2.2 Mapping vs array

Если порядок не важен — mapping дешевле массива. Массив хранит длину в отдельном slot'е и индексация требует keccak256+offset; mapping — просто keccak256. Если нужна итерация — массив (но осторожно с unbounded loop в pubic функциях: вектор для DoS).

3. calldata vs memory

calldata — read-only память входных параметров transaction. Чтение из неё дешевле (~3 газа за байт), и она не копируется. memory — read-write, копия в RAM EVM, стоит газа на запись и растёт квадратично после ~22 KB. 

// BAD: arr копируется в memory
function sumBad(uint256[] memory arr) external pure returns (uint256 s) {
    for (uint256 i = 0; i < arr.length; i++) s += arr[i];
}

// GOOD: arr читается напрямую из calldata
function sumGood(uint256[] calldata arr) external pure returns (uint256 s) {
    for (uint256 i = 0; i < arr.length; i++) s += arr[i];
}

// Разница на массиве из 100 элементов: ~3000 газа (3% от 100k).

Правило: для external функций по умолчанию используйте calldata для динамических типов (bytes, string, массивы, структуры). Для internal / public — память чаще необходима, потому что внутренние вызовы передают аргументы через стек/память.

4. Custom errors вместо require-строк

// BAD: строка занимает место в bytecode + memory во время revert
require(msg.sender == owner, "Ownable: caller is not the owner");

// GOOD: 4-байтовый selector, в 10× дешевле
error NotOwner(address caller);

if (msg.sender != owner) revert NotOwner(msg.sender);

// Экономия на bytecode-size: 30+ байт на каждую require-строку.
// Экономия на rev-pass: вместо memory-копии строки — 4-байтовый selector.

OpenZeppelin Contracts 5.x уже целиком перешли на custom errors. Если вы используете OZ ≥4.9 — они доступны в новых модулях. Это даёт читаемые ошибки (с параметрами) и значительную экономию.

5. Constant и immutable

constant — значение известно на compile-time, инлайнится в bytecode. Не занимает storage slot. immutable — значение устанавливается один раз в конструкторе, потом инлайнится в bytecode при деплое. Тоже не занимает storage slot, но допускает динамическое значение (chain id, deployer address). 

// constant — compile-time
uint256 public constant MAX_SUPPLY = 1_000_000 * 1e18;
address public constant WETH = 0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2;

// immutable — set in constructor
contract Token {
    uint256 public immutable maxSupply;
    address public immutable factory;

    constructor(uint256 _max) {
        maxSupply = _max;            // ОК
        factory = msg.sender;         // ОК
    }

    function read() external view returns (uint256) {
        return maxSupply;            // SLOAD НЕ выполняется — значение в bytecode
    }
}

В реальных контрактах перевод storage public переменных в immutable часто даёт 10–20% экономии на чтении в горячих функциях.

6. Loop-оптимизации

// BAD: повторное чтение storage в каждой итерации
function rewardAll() external {
    for (uint256 i = 0; i < users.length; i++) {  // SLOAD users.length каждую итерацию
        users[i].reward += 100;                     // SLOAD users[i] каждую итерацию
    }
}

// GOOD: кешируем length, используем unchecked для i++
function rewardAll() external {
    uint256 len = users.length;                     // 1 SLOAD
    for (uint256 i = 0; i < len;) {
        users[i].reward += 100;
        unchecked { ++i; }                          // i++ → ++i, no overflow check
    }
}

// Экономия на 100 итерациях: ~5 000 газа (от 1 SLOAD + 100 × 30 на ++i).
Когда unchecked { ++i } безопасен? Когда условие цикла гарантирует, что i не дойдёт до type(uint256).max. Если i < len и len — обычное число, overflow физически невозможен. В Solidity 0.8.22+ компилятор сам делает эту оптимизацию для for-циклов в --via-ir режиме.

7. --via-ir и оптимизатор

Solidity-компилятор имеет два бэкенда: классический legacy и Yul-based --via-ir (intermediate representation). via-ir включает inter-function optimisation, лучшее распределение регистров и устранение дублирующих SLOAD. Цена: компиляция в 3–5× медленнее, но bytecode чаще на 5–15% дешевле. 

# foundry.toml
[profile.default]
solc = "0.8.24"
optimizer = true
optimizer_runs = 200
via_ir = true             # включаем IR-pipeline

# Также можно поднимать optimizer_runs:
# - 200    — оптимизация под РАЗМЕР bytecode (для редко вызываемых функций)
# - 10000  — оптимизация под СКОРОСТЬ выполнения (для горячих функций)
# - 1000000 — экстрим, имеет смысл только для core-протоколов

Запускайте forge build --sizes для контроля размера контракта: EIP-170 ограничивает деплой до 24 576 байт. via-ir обычно сжимает на 10–20%.

9. Практические задачи

Задача 1 — Запаковать структуру User

Дана структура из 4 полей. Перепишите её так, чтобы она занимала минимум slot'ов. Измерьте экономию через forge test --gas-report. 

// BEFORE — 4 slot'а
struct UserV1 {
    uint8   level;      // slot 0
    uint256 balance;    // slot 1
    address account;    // slot 2
    uint16  fee;        // slot 3
}

// ЗАДАЧА: перепишите в struct UserV2 так, чтобы было ≤2 slot'ов.
// Подсказка: address + uint8 + uint16 = 23 байта, влезает в один slot
// с uint64. balance оставьте uint256 отдельно.

// test/Pack.t.sol
contract PackTest is Test {
    UserStore store;

    function setUp() public { store = new UserStore(); }

    function test_writeV1() public {
        store.writeV1(1, 100, address(0x1), 50);
    }

    function test_writeV2() public {
        store.writeV2(1, 100, address(0x1), 50);
    }
}

# Запустить:
forge test --match-test test_write --gas-report

# Ожидаемая экономия: ~22 000 газа (1 SSTORE с 0 на ненуль) за каждый
# slot, которым реже пользуемся.

Задача 2 — Заменить require-строки на custom errors

Возьмите контракт SafeVault из Lesson 09. Замените все require на custom errors. Измерьте: размер bytecode (forge build --sizes) и газ на revert-path (через vm.expectRevert(...)). 

// BEFORE
contract VaultV1 {
    mapping(address => uint256) public balances;

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "Vault: insufficient balance");
        require(amount > 0, "Vault: zero amount");
        balances[msg.sender] -= amount;
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok, "Vault: ETH transfer failed");
    }
}

// AFTER
contract VaultV2 {
    mapping(address => uint256) public balances;

    error InsufficientBalance(uint256 requested, uint256 available);
    error ZeroAmount();
    error TransferFailed();

    function withdraw(uint256 amount) external {
        uint256 bal = balances[msg.sender];
        if (amount == 0) revert ZeroAmount();
        if (bal < amount) revert InsufficientBalance(amount, bal);

        balances[msg.sender] = bal - amount;
        (bool ok, ) = msg.sender.call{value: amount}("");
        if (!ok) revert TransferFailed();
    }
}

# Сравнение через forge:
# forge build --sizes
# VaultV1 ≈ 2 400 байт, VaultV2 ≈ 1 900 байт (экономия ~500 байт на 3 строки)
# forge test --gas-report покажет разницу на revert-path.

Задача 4 — Storage layout инспекция

Используйте forge inspect для проверки реального layout контракта. Это особенно важно перед upgrade (Lesson 07): неправильный layout = storage collision. 

# Получить layout в JSON
forge inspect MyToken storageLayout

# Пример вывода:
# {
#   "storage": [
#     { "label": "balanceOf",  "slot": "0", "type": "t_mapping(address,uint256)", "offset": 0 },
#     { "label": "totalSupply","slot": "1", "type": "t_uint256",                  "offset": 0 },
#     { "label": "name",       "slot": "2", "type": "t_string",                   "offset": 0 },
#     { "label": "decimals",   "slot": "3", "type": "t_uint8",                    "offset": 0 },
#     { "label": "owner",      "slot": "3", "type": "t_address",                  "offset": 1 }
#   ]
# }

# offset = 1 значит owner начинается с 1-го байта slot'а 3 (decimals = байт 0).
# Это и есть упаковка: decimals (1 байт) + owner (20 байт) живут в slot 3.

# Используйте для проверки V1/V2 совместимости при upgrade:
diff <(forge inspect CounterV1 storageLayout) <(forge inspect CounterV2 storageLayout)
# Все slot'ы V1 должны остаться на тех же позициях в V2.

10. Песочница · Storage packing в Remix

Iframe ниже содержит два контракта с одинаковым API, но разным layout'ом. В Remix задеплойте оба, вызовите writeAll(...) с одинаковыми аргументами, посмотрите gas в transaction log. Разница в storage packing на 1 SSTORE = ~22 000 газа (при первой записи) или ~5 000 (при обновлении). 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

// BAD: 3 slot'а — каждое поле в своём слоте
contract Unpacked {
    uint8   public level;       // slot 0
    uint256 public balance;     // slot 1
    address public account;     // slot 2
    uint16  public fee;         // slot 3
    // итого 4 SSTORE при writeAll()

    function writeAll(uint8 _level, uint256 _balance, address _account, uint16 _fee) external {
        level   = _level;
        balance = _balance;
        account = _account;
        fee     = _fee;
    }
}

// GOOD: 2 slot'а — level/account/fee упакованы вместе
contract Packed {
    uint256 public balance;     // slot 0 (32 байта)
    uint8   public level;       // slot 1 (1 байт)  ─┐
    address public account;     // slot 1 (20 байт) ─┤ 23 байта в slot 1
    uint16  public fee;         // slot 1 (2 байта) ─┘
    // итого 2 SSTORE при writeAll(), экономия ~22000 газа

    function writeAll(uint8 _level, uint256 _balance, address _account, uint16 _fee) external {
        balance = _balance;
        level   = _level;
        account = _account;
        fee     = _fee;
    }
}
