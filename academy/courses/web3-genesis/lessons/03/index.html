Модуль I · Lesson 03 · ноды и сеть

Ноды, JSON-RPC и L1 / L2

→ продолжение Lesson 02 — ERC-20 в песочнице. Там мы развернули контракт «локально». Здесь мы понимаем, через что реальный фронтенд разговаривает с блокчейном — и пишем эти запросы руками.

Любой dApp, MetaMask, viem и Etherscan общаются с блокчейном через одну и ту же дверь: JSON-RPC 2.0. Это значит, что вы можете воспроизвести любой запрос через curl, Postman, Insomnia или Swagger UI — и понять, что именно происходит «под капотом» библиотек. В этом уроке мы разбираемся с архитектурой ноды (execution + consensus), с консенсусом Proof-of-Stake (attestations, finality, slashing), с экосистемой L2 (Arbitrum, Optimism), и решаем четыре практические задачи.

Что вы получите. После этого урока вы умеете: за 1 минуту определить, контракт ли по адресу или EOA; узнать, сколько газа сожгла транзакция; прочитать receipt и события; вычислить, финален ли блок; и сделать всё это четырьмя способами — curl, Postman, Foundry Cast и Swagger UI.

1.1 Клиенты EL: Geth, Besu, Nethermind, Erigon, Reth

КлиентСтекСильные стороныГде применяется
GethGo (go-ethereum)Reference-имплементация, наибольшее покрытие тестов~50% mainnet валидаторов
BesuJava (Hyperledger)Enterprise: permissioned-сети, GraphQL, plugin-APIКорпоративные / permissioned (Quorum, LACChain)
Nethermind.NETВысокая производительность синка, plugins~20% mainnet, любим L2 (zkEVM)

Все они реализуют один и тот же JSON-RPC API — поэтому ваш viem-код работает одинаково. Различия — в скорости синхронизации, потреблении диска, поддержке экзотических методов (debug_traceTransaction доступен на Geth/Erigon/Reth, но не у всех публичных RPC), и в форме log-API.

Клиент-диверсификация — это безопасность сети. Если 80% валидаторов запускают один клиент и в нём найдут консенсус-баг, сеть форкнётся и эти валидаторы будут оштрафованы (slashing). Поэтому Ethereum Foundation активно продвигает не-Geth клиенты.

1.2 Консенсус и награды за блок

Proof-of-Stake разделён на слоты (12 секунд) и эпохи (32 слота = 6 минут 24 секунды). В каждом слоте:

  • RANDAO-алгоритм выбирает одного proposer'а — валидатора, чья очередь предлагать блок.
  • Все остальные валидаторы (~1 млн на mainnet) делятся на 32 «комитета» (по одному на слот) и в назначенный им слот делают attestation — подписанный голос «я видел блок X, head канонической цепи — это he».

Награды валидатора (стейк 32 ETH) складываются из:

ИсточникКогдаДоля
Attestation rewardКаждую эпоху~75% дохода
Proposer rewardКогда выпала очередь предложить блок (~раз в неделю)~12.5%
Sync committee rewardЕсли выбран в sync committee (256 валидаторов на 256 эпох)~3%
MEV / priority feesTip'ы пользователей за приоритет~10% (сильно варьируется)

Базовая инфляция Ethereum (issuance) при ~1 млн валидаторов — около 0.5% годовых. При этом baseFee сжигается (EIP-1559), поэтому при высоком объёме транзакций ETH становится дефляционным.

1.3 Slashing: что нельзя делать валидатору

Slashing — это сжигание части стейка плюс принудительный выход из активного сета. Условия — только три:

  1. Double-proposing. Один валидатор подписал два разных блока на одном слоте.
  2. Surround vote. Голосует за epoch A → B, потом голосует за epoch A−1 → C (где C > B). «Окружил» предыдущий голос — атака на finality.
  3. Double-vote. Две attestation'а с одним target epoch и разными head-блоками.

Минимальный штраф — 1 ETH (1/32 стейка). Максимальный («correlation penalty») — до всех 32 ETH, если в ту же эпоху slashed много валидаторов одного оператора (защита от скоординированных атак).

1.4 Финальность

В отличие от Bitcoin, где «финальность» вероятностная (6 confirmations ≈ 99.9%), Ethereum даёт детерминированную финальность через Casper FFG. 

slot   slot+1  …  slot+32       slot+64        slot+96
─────────────────────────────────────────────────────────────►
                  ↑              ↑              ↑
                  justified      finalized      next finalization
                  (1 epoch)      (2 epochs)
                  ↑              ↑
            tag="safe"     tag="finalized"

   tag="latest"  = head (любой блок, может быть реорганизован)
   tag="safe"    = justified — >2/3 валидаторов проголосовали
   tag="finalized" = finalized — два последовательных justified epoch'а

Финальный блок откатить можно только если > 1/3 всего стейка согласованно нарушают правила — и они потеряют свои депозиты. Это > 11 миллиардов долларов экономической безопасности на момент написания. Поэтому finalized для критичных операций (биржевые депозиты, бридж-окна) — стандарт индустрии.

2. JSON-RPC: общая структура

Каждый запрос — POST на единый endpoint с JSON-телом: 

POST /  HTTP/1.1
Host: eth.llamarpc.com
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id":      1,
  "method":  "eth_blockNumber",
  "params":  []
}

Ответ — JSON-RPC envelope: 

{ "jsonrpc": "2.0", "id": 1, "result": "0x14589ce" }
                                                ↑
                                       hex-строка → 21_341_134 (BigInt!)

Все числа — hex-строки с префиксом 0x. JavaScript не умеет нативно работать с числами больше 253, поэтому везде используется BigInt или строка. viem делает это автоматически; в curl-сценариях — конвертируем руками.

4. Четыре практические задачи

4.1 Задача №1 — наличие контракта по адресу

Метод: eth_getCode(address, blockTag). EOA вернёт "0x", контракт — bytecode. 

# curl
curl -s -X POST 'https://eth.llamarpc.com' \
  -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_getCode",
           "params":["0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D","latest"]}' \
  | jq -r '.result | if . == "0x" then "EOA" else "Contract (" + (.|length|tostring) + " hex chars)" end'

# Foundry / Cast
cast code 0x7a250d5630B4cF539739dF2C5dAcb4c659F2488D --rpc-url https://eth.llamarpc.com

# viem (Node.js или браузер)
import { createPublicClient, http } from "viem";
import { mainnet } from "viem/chains";
const client = createPublicClient({ chain: mainnet, transport: http() });
const code = await client.getCode({ address: "0x7a250d…488D" });
console.log(code === undefined ? "EOA" : "Contract");

4.2 Задача №2 — стоимость транзакции по газу

Из receipt берём gasUsed и effectiveGasPrice: fee = gasUsed × effectiveGasPrice. Для legacy-tx — gasPrice. 

# curl + jq
curl -s -X POST 'https://eth.llamarpc.com' \
  -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt",
           "params":["0x88df016429689c079f3b2f6ad39fa052532c56795b733da78a91ebe6a713944b"]}' \
  | jq -r '.result | (.gasUsed|tonumber) * (.effectiveGasPrice|tonumber) | "fee = \(. ) wei"'

# Foundry / Cast — то же одной командой
cast receipt 0x88df016… --rpc-url $RPC \
  --json | jq -r '(.gasUsed|tonumber) * (.effectiveGasPrice|tonumber) / 1e18 | "\(. ) ETH"'

# eth_feeHistory — для оценки будущего fee
cast rpc eth_feeHistory 0x14 latest '[10,50,90]' --rpc-url $RPC

4.3 Задача №3 — получить receipt

Receipt появляется только после включения транзакции в блок. До этого — null. Полный pseudocode polling-цикла: 

async function waitForReceipt(hash, maxAttempts = 60) {
  for (let i = 0; i < maxAttempts; i++) {
    const res = await fetch(RPC_URL, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({
        jsonrpc: "2.0", id: 1, method: "eth_getTransactionReceipt", params: [hash]
      })
    }).then(r => r.json());

    if (res.result) return res.result;             // ✓ mined
    await new Promise(r => setTimeout(r, 2000));   // wait 2 s
  }
  throw new Error("timeout — tx still pending after 2 min");
}

viem делает это однострочно: client.waitForTransactionReceipt({ hash, confirmations: 1 }).

4.4 Задача №4 — финальность блока

Запрашиваем три блока (latest, safe, finalized) и сравниваем номера с нашим блоком. 

# Один batch-запрос вместо трёх:
curl -s -X POST 'https://eth.llamarpc.com' \
  -H 'content-type: application/json' \
  --data '[
    {"jsonrpc":"2.0","id":1,"method":"eth_getBlockByNumber","params":["latest",false]},
    {"jsonrpc":"2.0","id":2,"method":"eth_getBlockByNumber","params":["safe",false]},
    {"jsonrpc":"2.0","id":3,"method":"eth_getBlockByNumber","params":["finalized",false]}
  ]' | jq '.[] | { tag: .id, number: .result.number }'

Логика классификации (см. finalityOf() в academy/courses/web3-genesis/assets/rpc-helpers.js):

  • block ≤ finalized → finalized (можно засчитывать депозит)
  • finalized < block ≤ safe → safe
  • safe < block ≤ latest → unsafe (риск реорга)
  • block > latest → future (наша нода ещё не догнала)

5. Четыре способа сделать тот же запрос

5.1 curl + jq — для скриптов и CI

#!/usr/bin/env bash
set -euo pipefail
RPC=${RPC:-https://eth.llamarpc.com}

# Все hex-числа конвертируем в десятичные через jq:
curl -sS -X POST $RPC -H 'content-type: application/json' \

6. Layer 2: Arbitrum и Optimism

L1 (Ethereum mainnet) даёт максимальную безопасность, но дорогой газ (~5–30 $ за swap). L2 переносит исполнение в отдельную сеть, а на L1 публикует только сжатые данные транзакций («calldata» или EIP-4844 «blob») и доказательство корректности.

6.1 Системные транзакции

На L2 есть транзакции, которые пользователь не отправлял — их инициирует сама сеть.

Optimism — L1Block.setL1BlockValues(): первая транзакция в каждом L2-блоке. Записывает в storage предикомпиля 0x4200000000000000000000000000000000000015 текущие L1 baseFee, timestamp, blob fee. Это позволяет L2-контрактам читать актуальное состояние L1.

Arbitrum — ArbOS: системный «контракт-операционка» по адресу 0x0000…0064. Через него ходят update'ы цены газа, ретраи bridge-сообщений.

6.2 Бриджи L1 ↔ L2

L1 (Ethereum)                              L2 (Arbitrum / Optimism)
─────────────────                          ────────────────────────

L1 → L2 (deposit, fast: ~10 мин)
─────────────────────────────────
user → L1Bridge.depositETH()
       │
       │ emits MessageSent event
       ▼
   Inbox / OptimismPortal contract
       │
       │ sequencer прочитал event,
       │ включил в L2-блок через "force include" механизм
       ▼
                                       L2 system tx: mint ETH на user

L2 → L1 (withdraw, slow: ~7 дней!)
─────────────────────────────────
                                       user → L2Bridge.withdrawETH()
                                              │
                                              │ записывает запрос в Merkle-trie
                                              ▼
                                       (challenge window 7 дней)
                                              │
       ◄──────────────────── Sequencer публикует state root на L1 ──┘
       │
       │ После окна:
   user → L1Bridge.finalizeWithdrawal(proof)
       │
       │ Verifier проверяет Merkle-proof
       ▼
   ETH разблокирован user'у на L1

«7 дней» — это challenge window: время, в течение которого любой watcher может оспорить state root и инициировать fraud-proof. На zk-rollup'ах (zkSync Era, Scroll) этого окна нет — проверка криптографическая и моментальная.

6.3 Особенности RPC на L2

  • Финальность тега «finalized» на L2 — это не L1-финальность. На Optimism «finalized» означает «sequencer опубликовал блок и истёк challenge window» (~7 дней). Для критичных операций используйте safe + 7 дней или подтверждение от индексера.
  • eth_chainId: Arbitrum One = 42161 (0xa4b1), OP = 10 (0xa), Base = 8453 (0x2105), Sepolia = 11155111.
  • Газ на Arbitrum делится на L1-cost (calldata, публикация) и L2-cost (исполнение). eth_estimateGas возвращает суммарное.
  • Optimism-специфичный метод optimism_outputAtBlock — возвращает output root для построения withdraw-proof.

7. Чек-лист «безопасный RPC-провайдер»

  • Никогда не отдавайте seed-фразу или приватный ключ RPC-провайдеру. Подписи — только в кошельке.
  • Проверяйте eth_chainId перед отправкой транзакции — защита от «подмены сети» атакующим RPC.
  • Для production используйте dedicated-RPC (Alchemy, Infura, Quicknode) или собственную ноду. Публичные RPC имеют rate-limits и могут падать.
  • debug_traceTransaction доступен не везде — для дебага форкайте через Anvil или используйте Tenderly.
  • Кешируйте read-запросы (chainId, blockByNumber) на стороне фронтенда — экономит квоту провайдера.

8. Песочница — настоящий live-RPC

Мок выше отдаёт стабильные данные, потому что важна была форма запроса. Теперь — то же самое, но против реальной публичной ноды. Выберите метод и параметр, нажмите «Вызвать»: браузер отправит POST на eth.llamarpc.com (или rpc.sepolia.org), и вы увидите неотредактированный JSON-RPC ответ.
