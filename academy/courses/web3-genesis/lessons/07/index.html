Upgradeable Proxies — UUPS, Transparent и ERC-1967

→ продолжение Lesson 06 — Ownable & AccessControl. Там мы разобрали, кто управляет контрактом. Здесь — как поменять сам контракт без потери данных, пользователей и адреса.

Смарт-контракты по умолчанию неизменяемы: байткод задеплоен по адресу и живёт там навсегда. Это хорошо для доверия — никто не может тихо переписать правила игры. Но это создаёт проблему: что делать, когда вы нашли баг в продакшне, или хотите добавить новую функцию, не заставляя всех пользователей мигрировать на новый адрес? Ответ — proxy-паттерн: адрес остаётся прежним, а логику можно поменять. В этом уроке мы разберём два стандартных подхода — Transparent Proxy и UUPS — и поймём, почему ERC-1967 slot избавляет нас от storage collision.

Что вы получите. После этого урока вы умеете: объяснить, как delegatecall позволяет разделить логику и хранилище; правильно выбрать между Transparent Proxy и UUPS; написать upgradeble-контракт с нуля на OpenZeppelin 5.x; читать ERC-1967 слот напрямую через cast storage; и находить storage collision bug до деплоя.

1. Зачем нужны обновляемые контракты

Когда контракт деплоится, его байткод записывается в state блокчейна под определённым адресом — и изменить его невозможно. Это фундаментальное свойство EVM. Но у приложений в продакшне возникают вполне земные нужды:

  • Исправление багов. Даже опытные команды делают ошибки. Audit-фирмы находят уязвимости после деплоя. Без upgrade-механизма единственный вариант — задеплоить новый контракт и попросить всех пользователей мигрировать вручную.
  • Добавление функций. Продукт развивается: нужны новые параметры, новые операции, новые интеграции. Без апгрейда — снова миграция и перепись всех интеграций.
  • Сохранение state. Самое ценное в контракте — накопленные данные: балансы, mapping'и, history. При деплое нового контракта всё это надо мигрировать, что дорого и небезопасно.
  • Постоянный адрес. Пользователи, другие контракты, фронтенды, CEX-листинги — все завязаны на адрес. Смена адреса означает повторное прохождение всех интеграций.

Proxy-паттерн решает эти проблемы одновременно: proxy-контракт живёт по постоянному адресу и хранит state, а implementation-контракт содержит логику и может быть заменён. Пользователи и интеграции видят только адрес proxy — им всё равно, какой implementation за ним стоит.

Важный компромисс. Upgradeability — это централизация. Если у вас есть право делать upgrade, значит вы (или злоумышленник, получивший контроль) можете изменить любое правило. Многие зрелые проекты (Uniswap v3, Compound v3 governance) выбирают immutable контракты именно для максимального доверия. Используйте upgrade-паттерн осознанно: ограничьте upgrade-право multisig или DAO, публикуйте timelock.

2. delegatecall — ключевое понятие

Весь proxy-паттерн строится на одной опкод-инструкции EVM: DELEGATECALL. Она похожа на обычный CALL, но с принципиальным отличием: код вызывается в контексте вызывающего. 

// Обычный CALL — код и storage находятся у адресата:
Proxy.call(Implementation) {
  msg.sender  = Proxy                // адрес Proxy
  storage     = Implementation       // читает/пишет storage Implementation
}

// DELEGATECALL — код берётся у адресата, но storage остаётся у caller'а:
Proxy.delegatecall(Implementation) {
  msg.sender  = EOA (original caller) // оригинальный отправитель
  address(this) = Proxy              // this = Proxy, не Implementation
  storage     = Proxy                // читает/пишет storage Proxy!
}

Это означает: Implementation-контракт содержит логику (байткод), а все данные (balances, owner и т.д.) хранятся в storage Proxy-контракта. Когда мы делаем upgrade и меняем Implementation, старые данные в Proxy никуда не деваются.

Минимальный proxy в Solidity выглядит так: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract NaiveProxy {
    address public implementation;
    address public admin;

    constructor(address _impl) {
        implementation = _impl;
        admin = msg.sender;
    }

    function upgrade(address _newImpl) external {
        require(msg.sender == admin, "not admin");
        implementation = _newImpl;
    }

    // Все остальные вызовы делегируются в implementation
    fallback() external payable {
        address impl = implementation;
        assembly {
            // Копируем calldata в память
            calldatacopy(0, 0, calldatasize())
            // Делаем delegatecall
            let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
            // Копируем returndata
            returndatacopy(0, 0, returndatasize())
            // Возвращаем результат или revert
            switch result
            case 0  { revert(0, returndatasize()) }
            default { return(0, returndatasize()) }
        }
    }

    receive() external payable {}
}
Почему assembly? Встроенный delegatecall в Solidity не умеет «прокидывать» произвольный return-тип. Assembly-вариант через returndatacopy передаёт байты без изменений, что позволяет proxy быть полностью прозрачным для любых возвращаемых типов.

3. Проблема storage collision и как её решает ERC-1967

У наивного proxy выше есть критический баг. Посмотрим на storage обоих контрактов: 

// NaiveProxy:
// slot 0: address public implementation
// slot 1: address public admin

// CounterV1 (implementation):
// slot 0: uint256 public count      ← КОНФЛИКТ! Занят proxy.implementation
// slot 1: address public owner      ← КОНФЛИКТ! Занят proxy.admin

Поскольку delegatecall исполняет код Implementation в storage Proxy, переменная count из Implementation пишется в slot 0 — туда же, где Proxy хранит адрес Implementation. Вызов increment() перезапишет адрес реализации числом 1. Это критическая уязвимость.

ERC-1967 решает эту проблему, размещая служебные переменные proxy в случайных, непересекающихся слотах. Адрес реализации и другие внутренние данные proxy хранятся в специально вычисленных слотах в дальней части storage, а не в слотах 0, 1, 2...

3.1 ERC-1967 слоты

// Слот для адреса implementation:
bytes32 internal constant IMPLEMENTATION_SLOT =
    bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1);
// = 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc

// Слот для адреса admin:
bytes32 internal constant ADMIN_SLOT =
    bytes32(uint256(keccak256("eip1967.proxy.admin")) - 1);
// = 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103

// Слот для адреса beacon:
bytes32 internal constant BEACON_SLOT =
    bytes32(uint256(keccak256("eip1967.proxy.beacon")) - 1);
// = 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50

Формула keccak256(...) - 1 (а не просто хеш) защищает от атаки, при которой злоумышленник мог бы подобрать preimage для известного хеша. Вычтенная единица делает обратный перебор практически невозможным.

Чтение и запись по таким слотам делается через inline assembly: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

abstract contract ERC1967Storage {
    bytes32 private constant IMPLEMENTATION_SLOT =
        0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc;

    function _getImplementation() internal view returns (address impl) {
        assembly {
            impl := sload(IMPLEMENTATION_SLOT)
        }
    }

    function _setImplementation(address newImpl) internal {
        require(newImpl.code.length > 0, "ERC1967: not a contract");
        assembly {
            sstore(IMPLEMENTATION_SLOT, newImpl)
        }
    }
}

Теперь слоты 0, 1, 2... у proxy полностью свободны для переменных Implementation, а слот реализации находится в позиции с огромным номером, с которой никогда не пересечётся обычный контракт.

4. Transparent Proxy Pattern

Transparent Upgradeable Proxy (TUP) — стандарт от OpenZeppelin, исторически первый production-ready proxy. Его идея: разделить вызовы по роли отправителя. 

┌────────────────────────────────────────────────────────────────┐
│                 TransparentUpgradeableProxy                      │
│                                                                   │
│   if (msg.sender == admin)                                        │
│     → исполнить admin-функции (upgradeTo, changeAdmin)            │
│   else                                                            │
│     → delegatecall в implementation                               │
│                                                                   │
│   Admin не может вызвать функции implementation через proxy!      │
└────────────────────────────────────────────────────────────────┘

Ключевые компоненты:

  • TransparentUpgradeableProxy — сам proxy-контракт. Содержит fallback() и минимальную логику маршрутизации.
  • ProxyAdmin — отдельный контракт-владелец proxy. Через него admin вызывает upgradeAndCall. Это позволяет чётко разделить роли: admin всегда идёт через ProxyAdmin, а не напрямую.

4.1 Деплой Transparent Proxy через OpenZeppelin 5.x

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

// --- Implementation контракт ---
contract CounterV1 is Initializable, OwnableUpgradeable {
    uint256 public count;

    // Конструктор ЗАПРЕЩЁН для логики — используем initializer
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    // Вместо constructor — initializer (вызывается один раз через proxy)
    function initialize(address initialOwner) public initializer {
        __Ownable_init(initialOwner);
        count = 0;
    }

    function increment() external {
        count += 1;
    }
}

// Деплой через Foundry script:
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Script.sol";
import "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import "@openzeppelin/contracts/proxy/transparent/ProxyAdmin.sol";
import "../src/CounterV1.sol";

contract DeployTransparent is Script {
    function run() external {
        vm.startBroadcast();

        // 1. Деплоим implementation
        CounterV1 impl = new CounterV1();

        // 2. Кодируем вызов initializer
        bytes memory initData = abi.encodeCall(
            CounterV1.initialize,
            (msg.sender)
        );

        // 3. Деплоим ProxyAdmin (владелец proxy)
        ProxyAdmin proxyAdmin = new ProxyAdmin(msg.sender);

        // 4. Деплоим сам proxy
        TransparentUpgradeableProxy proxy = new TransparentUpgradeableProxy(
            address(impl),
            address(proxyAdmin),
            initData
        );

        vm.stopBroadcast();

        console.log("Proxy address:     ", address(proxy));
        console.log("ProxyAdmin address:", address(proxyAdmin));
        console.log("Implementation:    ", address(impl));
    }
}

4.2 Недостатки Transparent Proxy

  • Два контракта. Каждый деплой требует и proxy, и ProxyAdmin. Больше контрактов — больше газа на деплой, сложнее аудит.
  • Gas overhead на каждый вызов. Proxy проверяет msg.sender == admin на каждый вызов, даже обычный read-only. Это дополнительный SLOAD.
  • Admin не может взаимодействовать с логикой. Если admin хочет вызвать increment(), ему нужно использовать другой адрес. Это неочевидное ограничение, которое ловят даже опытные разработчики.

5. UUPS Pattern (ERC-1822)

Universal Upgradeable Proxy Standard (UUPS) — альтернативный подход, где логика upgrade перенесена в implementation-контракт, а не в proxy. Proxy становится максимально тонким: только ERC-1967 storage и делегирование через fallback. 

┌────────────────────────────────────────────────────────────────┐
│  UUPSProxy (тонкий)                                              │
│  • ERC-1967 слот для implementation                              │
│  • fallback() → delegatecall(implementation)                     │
│  • НЕТ логики upgrade                                            │
└────────────────────────┬───────────────────────────────────────┘
                         │ delegatecall
                         ▼
┌────────────────────────────────────────────────────────────────┐
│  CounterV1 (implementation)                                      │
│  is UUPSUpgradeable, OwnableUpgradeable                          │
│                                                                   │
│  function upgradeToAndCall(address newImpl, bytes calldata data) │
│    → _authorizeUpgrade(newImpl)   // проверка прав               │
│    → _upgradeToAndCallUUPS(...)   // пишет в ERC-1967 слот       │
│                                                                   │
│  function _authorizeUpgrade(address) internal override onlyOwner │
└────────────────────────────────────────────────────────────────┘

5.1 Реализация UUPS-контракта

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

contract CounterV1 is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    uint256 public count;

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    function initialize(address initialOwner) public initializer {
        __Ownable_init(initialOwner);
        __UUPSUpgradeable_init();
        count = 0;
    }

    function increment() external {
        count += 1;
    }

    // Переопределяем: только owner может инициировать upgrade
    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner
    {}
}

// Деплой UUPS через Foundry script:
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Script.sol";
import "@openzeppelin/contracts/proxy/ERC1967/ERC1967Proxy.sol";
import "../src/CounterV1.sol";

contract DeployUUPS is Script {
    function run() external {
        vm.startBroadcast();

        // 1. Деплоим implementation
        CounterV1 impl = new CounterV1();

        // 2. Кодируем вызов initializer
        bytes memory initData = abi.encodeCall(
            CounterV1.initialize,
            (msg.sender)
        );

        // 3. Деплоим ERC1967Proxy (тонкий proxy без ProxyAdmin)
        ERC1967Proxy proxy = new ERC1967Proxy(address(impl), initData);

        vm.stopBroadcast();

        console.log("Proxy address:    ", address(proxy));
        console.log("Implementation:   ", address(impl));
    }
}

5.2 Upgrade с V1 на V2

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

// V2: добавляем decrement() и новую переменную decrementCount
contract CounterV2 is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    uint256 public count;          // slot 0 — совпадает с V1
    uint256 public decrementCount; // slot 1 — НОВАЯ переменная, безопасно

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    // reinitializer(2) — для инициализации V2-специфичных полей
    function initializeV2() public reinitializer(2) {
        decrementCount = 0;
    }

    function increment() external {
        count += 1;
    }

    function decrement() external {
        require(count > 0, "CounterV2: underflow");
        count -= 1;
        decrementCount += 1;
    }

    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner
    {}
}

// Апгрейд через Foundry script:
pragma solidity ^0.8.24;

import "forge-std/Script.sol";
import "../src/CounterV1.sol";
import "../src/CounterV2.sol";

contract UpgradeToV2 is Script {
    address constant PROXY = 0x1234...;   // адрес задеплоенного proxy

    function run() external {
        vm.startBroadcast();

        // Деплоим новую реализацию
        CounterV2 implV2 = new CounterV2();

        // Вызываем upgradeToAndCall через proxy (proxy делегирует в V1)
        // V1._authorizeUpgrade() проверит onlyOwner, затем запишет новый адрес
        bytes memory callData = abi.encodeCall(CounterV2.initializeV2, ());
        CounterV1(PROXY).upgradeToAndCall(address(implV2), callData);

        vm.stopBroadcast();

        console.log("Upgraded to V2:", address(implV2));
    }
}

6. UUPS vs Transparent Proxy: сравнение

Параметр Transparent Proxy UUPS (ERC-1822)
Где логика upgrade В proxy-контракте В implementation-контракте
Нужен ProxyAdmin Да (отдельный контракт) Нет (достаточно ERC1967Proxy)
Gas на каждый вызов +1 SLOAD (проверка admin) Минимальный overhead
Стоимость деплоя Proxy + ProxyAdmin (~два контракта) Proxy + Implementation (~один шаг)
Безопасность при ошибке Если нет прав upgrade — proxy застрянет Если implementation без _authorizeUpgrade — навсегда заблокирован
Может ли admin вызвать логику Нет (маршрутизация по sender) Да (нет разделения на уровне proxy)
Рекомендуется OZ Для большинства случаев до OZ v4 Начиная с OZ v4 (текущий стандарт)
EIP ERC-1967 (storage slots) ERC-1822 + ERC-1967
Текущая рекомендация OpenZeppelin (v5.x). Для новых проектов используйте UUPS: меньше газа, проще архитектура, не нужен ProxyAdmin. Transparent Proxy актуален для проектов, где команда предпочитает иметь возможность upgrade даже если потеряла контроль над owner-ролью в implementation (edge case корпоративных сред).

7. Инициализаторы вместо конструкторов

У proxy-контрактов есть тонкость: конструктор implementation вызывается один раз при деплое implementation, но не при деплое proxy. Когда пользователи взаимодействуют через proxy, они видят storage proxy — и там нет переменных, инициализированных конструктором implementation. 

// НЕПРАВИЛЬНО: конструктор не выполнится в контексте proxy
contract BadCounter {
    address public owner;
    uint256 public count;

    constructor() {
        owner = msg.sender;  // Устанавливает owner в impl-контракте,
        count = 0;           // но НЕ в proxy!
    }
}

// ПРАВИЛЬНО: используем initializer-паттерн
import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";

contract GoodCounter is Initializable {
    address public owner;
    uint256 public count;

    // Запрещаем вызов конструктора, чтобы никто не инициализировал impl напрямую
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    // initialize() вызывается через proxy один раз — аналог конструктора
    function initialize(address _owner) public initializer {
        owner = _owner;
        count = 0;
    }
}

Модификатор initializer из OpenZeppelin гарантирует:

  • Функция может быть вызвана только один раз.
  • Во время инициализации допускается вызов других initializer-функций (цепочка __Ownable_init, __UUPSUpgradeable_init и т.д.).
  • После вызова флаг _initialized устанавливается в 1 (или в версию для reinitializer).
_disableInitializers() в конструкторе. Это защита от атаки: если не отключить initializer на implementation-контракте, кто угодно может вызвать initialize() напрямую на impl (не через proxy) и стать owner'ом этого контракта. Хотя это не влияет на proxy, плохой owner impl может навредить, если implementation используется как beacon или имеет selfdestruct.

7.1 Цепочка инициализаторов

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";

// Upgradeble ERC-20 токен — полный пример
contract MyTokenV1 is
    Initializable,
    ERC20Upgradeable,
    OwnableUpgradeable,
    UUPSUpgradeable
{
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    function initialize(
        string memory name,
        string memory symbol,
        address initialOwner,
        uint256 initialSupply
    ) public initializer {
        __ERC20_init(name, symbol);        // инициализирует ERC20 storage
        __Ownable_init(initialOwner);      // устанавливает owner
        __UUPSUpgradeable_init();          // устанавливает версию ERC-1967

        _mint(initialOwner, initialSupply);
    }

    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner
    {}
}

8. Опасности и антипаттерны

8.1 Storage collision при upgrade

Самая распространённая ошибка при upgrade: добавить переменную в неправильное место, нарушив порядок слотов. 

// V1: layout слотов
contract CounterV1 {
    uint256 public count;   // slot 0
    address public owner;   // slot 1
}

// НЕПРАВИЛЬНО: добавили переменную в начало
contract CounterV2_BAD {
    uint256 public version; // slot 0 — КОНФЛИКТ! Перезапишет count
    uint256 public count;   // slot 1 — КОНФЛИКТ! Перезапишет owner
    address public owner;   // slot 2 — теперь здесь
}

// ПРАВИЛЬНО: новые переменные добавляются только в конец
contract CounterV2_GOOD {
    uint256 public count;        // slot 0 — без изменений
    address public owner;        // slot 1 — без изменений
    uint256 public decrementCount; // slot 2 — новая переменная, безопасно
}
Нельзя: удалять существующие переменные, менять их тип, менять порядок, вставлять новые переменные перед существующими. Можно: добавлять новые переменные в конец, переименовывать переменные (имя не хранится в storage). OpenZeppelin Upgrades Plugin проверяет storage layout автоматически перед каждым upgrade.

8.2 Uninitialized proxy

// Опасный сценарий: deploy без вызова initialize()
ERC1967Proxy proxy = new ERC1967Proxy(
    address(impl),
    ""   // пустой initData — initialize() не вызовется!
);

// Теперь owner = address(0), контракт заморожен навсегда
// (или может быть захвачен первым вызывающим initialize)

// Безопасный деплой — всегда передавайте initData:
bytes memory initData = abi.encodeCall(CounterV1.initialize, (msg.sender));
ERC1967Proxy proxy = new ERC1967Proxy(address(impl), initData);

8.3 selfdestruct в implementation

// Критический баг: implementation с selfdestruct
contract DangerousImpl {
    function destroy() external {
        selfdestruct(payable(msg.sender));
    }
}

// Что происходит:
// 1. Proxy делегирует вызов destroy() в implementation
// 2. НО selfdestruct работает в контексте Proxy (delegatecall!)
// 3. PROXY-контракт уничтожается, все данные теряются навсегда
//
// Правило: никогда не используйте selfdestruct в implementation-контрактах.
// После EIP-6780 (Cancun) selfdestruct только переводит ETH, если
// контракт создан в том же transaction — это снижает риск, но не
// отменяет правило хорошего тона.

8.4 Delegatecall в implementation

// Опасная конструкция: implementation делает delegatecall в произвольный адрес
contract VulnerableImpl {
    function execute(address target, bytes calldata data) external {
        // Если target — вредоносный контракт, он может
        // перезаписать ERC-1967 слот implementation в proxy storage
        (bool ok,) = target.delegatecall(data);
        require(ok);
    }
}
// Это позволяет злоумышленнику захватить контроль над proxy.

Задача 2 — Написать CounterV2 и сделать upgrade через upgradeToAndCall

Добавьте функцию decrement() и переменную decrementCount в CounterV2, задеплойте новую реализацию, вызовите upgrade и убедитесь, что старый count сохранился.

# script/Upgrade.s.sol
# SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Script.sol";
import "../src/CounterV1.sol";
import "../src/CounterV2.sol";

contract UpgradeScript is Script {
    function run() external {
        address proxy = vm.envAddress("PROXY_ADDR");
        vm.startBroadcast();

        // Деплоим V2 implementation
        CounterV2 implV2 = new CounterV2();
        console.log("New impl:", address(implV2));

        // Читаем текущее состояние ДО upgrade
        CounterV1 counterBefore = CounterV1(proxy);
        console.log("count before upgrade:", counterBefore.count());

        // Upgrade + вызов initializeV2
        bytes memory callData = abi.encodeCall(CounterV2.initializeV2, ());
        counterBefore.upgradeToAndCall(address(implV2), callData);

        // Читаем состояние ПОСЛЕ upgrade
        CounterV2 counterAfter = CounterV2(proxy);

        console.log("decrementCount:", counterAfter.decrementCount()); // 0

        // Тестируем новую функцию
        counterAfter.decrement();
        console.log("count after decrement:", counterAfter.count());    // count - 1
        console.log("decrementCount:", counterAfter.decrementCount()); // 1

        vm.stopBroadcast();
    }
}

Задача 4 — Найти storage collision bug в плохом контракте

Ниже — демонстрационный контракт с намеренной ошибкой. Найдите, где происходит storage collision, и объясните, как её исправить. 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

// BUG: Плохой proxy без ERC-1967 защиты
contract BuggyProxy {
    address public implementation;  // slot 0
    address public admin;           // slot 1

    constructor(address _impl, address _admin) {
        implementation = _impl;
        admin = _admin;
    }

    function upgrade(address _newImpl) external {
        require(msg.sender == admin, "not admin");
        implementation = _newImpl;
    }

    fallback() external payable {
        address impl = implementation;
        assembly {
            calldatacopy(0, 0, calldatasize())
            let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            switch result
            case 0  { revert(0, returndatasize()) }
            default { return(0, returndatasize()) }
        }
    }
}

// Implementation с коллизией:
contract VulnerableCounter {
    uint256 public count;       // slot 0 — конфликт с BuggyProxy.implementation!
    address public tokenOwner;  // slot 1 — конфликт с BuggyProxy.admin!

    function increment() external {
        count += 1;  // Это перезаписывает адрес implementation в BuggyProxy!
    }

    function setOwner(address newOwner) external {
        tokenOwner = newOwner;  // Это перезаписывает admin в BuggyProxy!
    }
}

// ВОПРОСЫ:
// 1. Что произойдёт с BuggyProxy.implementation после вызова increment() через proxy?
// 2. Сможет ли admin после этого сделать upgrade?
// 3. Перепишите BuggyProxy с использованием ERC-1967 слотов, чтобы устранить коллизию.

// ПОДСКАЗКА: замените хранение implementation и admin на:
// assembly { sstore(IMPLEMENTATION_SLOT, newImpl) }
// где IMPLEMENTATION_SLOT = bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1)

Запустите тест для верификации вашего ответа: 

// test/StorageCollision.t.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Test.sol";
import "../src/BuggyProxy.sol";
import "../src/VulnerableCounter.sol";

contract StorageCollisionTest is Test {
    BuggyProxy proxy;
    VulnerableCounter impl;

    function setUp() public {
        impl = new VulnerableCounter();
        proxy = new BuggyProxy(address(impl), address(this));
    }

    function test_StorageCollisionOnIncrement() public {
        VulnerableCounter counter = VulnerableCounter(address(proxy));

        // Читаем implementation ДО increment
        address implBefore = proxy.implementation();
        assertEq(implBefore, address(impl));

        // Вызываем increment() через proxy
        counter.increment();

        // BUG: implementation теперь испорчен (count = 1, но это адрес!)
        address implAfter = proxy.implementation();

        assertNotEq(implAfter, implBefore, "COLLISION: implementation overwritten by count=1");

        // Теперь upgrade невозможен — delegatecall пойдёт по адресу 0x000...001
    }
}

12. Diamond Proxy (EIP-2535) — масштаб за пределами лимита 24 КБ

У EVM есть жёсткое ограничение: байт-код одного развёрнутого контракта не может превышать 24 КБ (EIP-170). Для крупного корпоративного dApp — аналога Uber, глобального маркетплейса или биржи — этого не хватает: вся бизнес-логика не помещается в один implementation. Transparent и UUPS опираются на единственный контракт логики и этот барьер не снимают.

Паттерн Diamond (EIP-2535) — «бриллиантовый» multi-facet proxy — даёт приложению фактически неограниченное число функций. Это переносит на блокчейн микросервисную декомпозицию, сопоставимую по сложности с кластером Kubernetes: один адрес снаружи, множество изолированных модулей логики внутри.

12.1 Два элемента архитектуры

  • Diamond (Бриллиант) — центральный proxy-контракт. Хранит общий storage и fallback-функцию-маршрутизатор. Именно с этим единственным адресом взаимодействуют пользователи.
  • Facets (Грани) — множество независимых контрактов логики (implementation). Diamond читает первые 4 байта calldata (селектор функции) и через delegatecall маршрутизирует вызов в нужную грань — по таблице selector → facet.
// Упрощённый fallback Бриллианта (роутинг по селектору)
fallback() external payable {
    DiamondStorage storage ds = diamondStorage();
    address facet = ds.selectorToFacet[msg.sig];   // msg.sig = первые 4 байта
    require(facet != address(0), "Diamond: function does not exist");
    assembly {
        calldatacopy(0, 0, calldatasize())
        let ok := delegatecall(gas(), facet, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch ok
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

12.2 diamondCut — атомарное обновление по функциям

Вместо того чтобы заменять весь массив кода (как в UUPS/Transparent), Diamond обновляется на уровне отдельных функций через единственную операцию diamondCut: можно атомарно добавить (Add), заменить (Replace) или удалить (Remove) конкретные селекторы прямо в рабочей сети — без редеплоя остального кода. 

enum FacetCutAction { Add, Replace, Remove }

struct FacetCut {
    address facetAddress;
    FacetCutAction action;
    bytes4[] functionSelectors;
}

// Заменить только функцию quote() новой гранью, остальное не трогаем
FacetCut[] memory cut = new FacetCut[](1);
cut[0] = FacetCut({
    facetAddress: address(newPricingFacet),
    action: FacetCutAction.Replace,
    functionSelectors: _selectors(PricingFacet.quote.selector)
});
IDiamondCut(diamond).diamondCut(cut, address(0), "");

12.3 EIP-7201 — Namespaced Storage против коллизий граней

Несколько граней пишут в один и тот же storage Бриллианта — это классический риск storage collision (см. раздел 8.1), только умноженный на число фасетов. Решение — EIP-7201 (Namespaced Storage Layout): данные каждого модуля размещаются в псевдослучайном слоте, вычисляемом криптографически, так что пространства имён граней не пересекаются. 

// EIP-7201: erc7201("myapp.pricing.storage")
library PricingStorage {
    // keccak256(abi.encode(uint256(keccak256("myapp.pricing.storage")) - 1))
    //   & ~bytes32(uint256(0xff))
    bytes32 private constant SLOT =
        0x9f3e...00;   // детерминированный, не пересекается с другими гранями

    struct Layout { uint256 baseFee; mapping(address => uint256) discounts; }

    function layout() internal pure returns (Layout storage l) {
        bytes32 slot = SLOT;
        assembly { l.slot := slot }
    }
}

12.4 Когда выбирать Diamond

Критерий UUPS / Transparent Diamond (EIP-2535)
Лимит 24 КБ Упирается: вся логика в одном implementation Снят: логика разбита по граням
Гранулярность upgrade Весь контракт логики целиком Отдельные функции (Add/Replace/Remove)
Сложность / аудит Низкая, хорошо изучена Высокая: роутинг, loupe, namespaced storage
Storage-безопасность ERC-1967 + storage gaps Обязателен EIP-7201 namespaced layout
Когда оправдан Большинство протоколов Крупные модульные приложения (биржа, маркетплейс, игровой движок)
Вывод. Diamond — не «лучший» прокси, а инструмент для модульного масштаба. Для одиночного контракта он избыточен и добавляет поверхность атаки. Для приложения уровня «микросервисы on-chain» он позволяет держать единый адрес и независимо эволюционировать десятки модулей — то, что в классике делает оркестратор контейнеров.
