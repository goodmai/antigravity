Основы блокчейна: блоки, консенсус, стейкинг

Прежде чем писать смарт-контракты и отправлять транзакции, нужно понять, как именно работает механизм, которому вы доверяете свои данные и деньги. Этот урок — технический фундамент курса: что такое блок и цепочка, почему все ноды приходят к одному состоянию без центрального сервера, что значит «стейкать» ETH и как можно потерять всё за нечестное поведение.

Что вы получите. После урока вы сможете объяснить: структуру блока; почему подмена одного блока ломает все последующие; разницу между PoW, PoS, DPoS и BFT; что такое финальность и почему она важна; как работает стейкинг и слэшинг; что такое форк и когда он «хардовый».

1. Что такое блокчейн

Блокчейн — это связанный список блоков, где каждый блок содержит хэш предыдущего. Это создаёт криптографическую цепочку: изменить блок посередине невозможно без пересчёта всех последующих, а значит — без согласия большинства сети.

Genesis Block #0
hash: 0x000000a1…
prev: 0x000000 (genesis)
→
Block #1
hash: 0x4f83c2d7…
prev: 0x000000a1…
→
Block #2
hash: 0xa9b1e305…
prev: 0x4f83c2d7…
→
Block #N (latest)
hash: 0x71cc9f02…
prev: 0xa9b1e305…

1.1 Структура блока Ethereum

Блок содержит два главных раздела: заголовок (header) — 30-40 полей метаданных — и тело (body) — список транзакций и список дядей (uncles / ommers, ныне не используется в PoS). 

Block Header {
  parentHash        bytes32   // keccak256 предыдущего заголовка — главная «ссылка»
  sha3Uncles        bytes32   // хэш списка ommer-блоков (legacy)
  miner / feeRecipient addr   // получатель наград за блок (PoW: miner; PoS: validator)
  stateRoot         bytes32   // корень Patricia-Merkle дерева всего состояния
  transactionsRoot  bytes32   // корень Merkle-Patricia дерева транзакций
  receiptsRoot      bytes32   // корень дерева чеков транзакций (events, gasUsed)
  logsBloom         [256]byte // Bloom-фильтр по всем событиям — для быстрого поиска
  difficulty        uint256   // сложность майнинга (0 в PoS после Merge)
  number            uint256   // номер блока
  gasLimit          uint256   // максимальное суммарное потребление газа в блоке
  gasUsed           uint256   // реально потраченный газ
  timestamp         uint256   // unix time создания блока
  extraData         bytes     // произвольные данные валидатора (≤32 байт)
  mixHash / prevRandao bytes32 // PoW: mixHash; PoS: RANDAO — источник случайности
  nonce             bytes8    // PoW: 64-бит nonce; PoS: 0x000…000
  baseFeePerGas     uint256   // EIP-1559 базовая цена (с London hardfork)
  withdrawalsRoot   bytes32   // EIP-4895 (Shapella): корень дерева выводов стейка
  blobGasUsed       uint64    // EIP-4844 (Dencun): газ для blob-транзакций
  excessBlobGas     uint64    // EIP-4844: накопленный лишний blob-газ
}

1.2 Почему цепочку нельзя «подделать»

Попробуем изменить транзакцию в блоке №100. Тогда изменится transactionsRoot этого блока, а значит — и его хэш. Но хэш блока №100 записан в поле parentHash блока №101. Поэтому нужно пересчитать блок №101, потом №102… и так до самого последнего. Каждый пересчёт требует либо огромных вычислительных ресурсов (PoW) либо контроля над большинством стейка (PoS). Именно поэтому говорят, что атака требует 51%+ ресурсов сети — и становится дороже по мере роста сети.

1.3 Genesis-блок

Первый блок цепочки — Genesis — не имеет родителя: его поле parentHash заполнено нулями. Он содержит начальное распределение балансов (pre-allocations) и параметры сети: chainId, начальную сложность, gasLimit. В Ethereum Mainnet Genesis-блок датируется 30 июля 2015 года (блок #0).

2. Консенсусные механизмы

Консенсус — это алгоритм, с помощью которого тысячи независимых нод договариваются о том, какой следующий блок является «правильным». Без консенсуса каждая нода могла бы добавить свой блок — цепочка расщепилась бы.

⛏️ Proof of Work (PoW)

Валидатор (майнер) перебирает nonce, пока keccak256(header + nonce) не будет меньше target. Вероятность найти блок = доля хэшрейта.

Защита: для переписи цепи нужно >50% мирового хэшрейта.

Проверен годами (BTC с 2009) Огромный расход энергии Риск ASIC-централизации

Ethereum использовал PoW до сентября 2022 (The Merge). Сейчас — только Bitcoin, Litecoin и др.

🥩 Proof of Stake (PoS)

Валидатор блокирует (стейкает) залог в нативном токене. Право предложить следующий блок разыгрывается случайно, пропорционально стейку.

Защита: для атаки нужно >33% (finality) или >67% (переписать) от суммарного стейка.

Энергоэффективен (~99.95% vs PoW) Слэшинг наказывает нечестных Риск «богатые богатеют»

Ethereum (Casper FFG + LMD-GHOST), Solana, Avalanche, Cardano.

🗳️ Delegated Proof of Stake (DPoS)

Держатели токенов голосуют за небольшое число «делегатов» (например, 21 в EOS, 101 в LISK). Делегаты производят блоки по очереди.

Защита: честность обеспечивается репутацией и угрозой переголосования.

Высокий TPS, быстрые блоки Высокая централизация «Аристократия делегатов»

EOS, TRON, BitShares, BNB Chain (21 validator).

🏛️ Byzantine Fault Tolerance (BFT / pBFT)

Набор известных валидаторов обменивается сообщениями в несколько раундов (prepare → promise → commit). Блок финален, когда >⅔ проголосовали.

Защита: выдерживает до ⅓ нечестных / отказавших нод.

Мгновенная финальность Без майнинга, детерминировано Не масштабируется на тысячи нод

Tendermint (Cosmos), Hyperledger Fabric, PBFT, HotStuff (Libra/Diem).

🏔️ Proof of Authority (PoA)

Блоки производит список заранее одобренных, идентифицированных валидаторов. Авторитет — не деньги, а юридическая ответственность.

Защита: репутация и контракты с операторами.

Быстрый, дешёвый Подходит для enterprise Требует доверия к операторам

Polygon Edge (Bor), Sepolia testnet, Goerli (исторически), BSC Parlia, многие корпоративные сети.

📜 Proof of History (PoH)

Лидер создаёт верифицируемую хронологию событий через VDF (итеративный sha256). Не консенсус сам по себе, а часовой механизм поверх PoS.

Идея: доказать, что транзакция произошла до определённого момента времени.

Очень высокий TPS (~65 000) Высокие требования к железу Молодой протокол

Используется только в Solana (в сочетании с Tower BFT).

2.1 Как Ethereum выбирает лидера (LMD-GHOST + Casper FFG)

Ethereum PoS работает на двух алгоритмах, которые дополняют друг друга:

  • LMD-GHOST (Latest Message Driven Greedy Heaviest Observed SubTree) — алгоритм выбора «каноничной» цепочки. Из всех возможных веток выбирается та, где суммарный стейк последних аттестаций максимален (самая «тяжёлая» ветка).
  • Casper FFG (Friendly Finality Gadget) — механизм финальности. Каждые два эпохи (~12.8 мин) валидаторы голосуют за «checkpoint»-блок. Когда >⅔ стейка аттестует checkpoint как «justified» и следующий epoch тоже «justified» — checkpoint становится finalized.

Каждые 12 секунд — один слот. Каждые 32 слота — одна эпоха (~6.4 минуты). Один случайно выбранный валидатор в каждом слоте предлагает блок; 128 случайных валидаторов образуют комитет аттестаторов и голосуют за предложенный блок. 

Slot  0  1  2  3  … 31 │ Slot 32  33  … 63 │ Slot 64 …
      ──────────────── │ ─────────────────  │ ─────────
       Epoch 0         │     Epoch 1         │   Epoch 2

Epoch 0 finalized (justified → justified → finalized) после Epoch 2.

3.2 Как начисляются награды

Валидатор зарабатывает в трёх источниках:

  • Attestation reward — базовая награда за правильное и своевременное голосование за head-блок (LMD-GHOST), source и target checkpoint (Casper FFG). Составляет ~85% суммарного дохода.
  • Block proposal reward — дополнительная награда тому валидатору, который был выбран предложить блок в данном слоте. Плюс все приоритетные сборы (tips) от транзакций.
  • MEV (Maximal Extractable Value) — дополнительный доход от перестановки транзакций в блоке (арбитраж, sandwich-атаки). Большинство валидаторов используют MEV-Boost (Flashbots) для этого.

3.3 Слэшинг (Slashing)

Слэшинг — это наказание за нечестное поведение, которое автоматически уничтожает часть стейка валидатора. Слэшинг происходит при:
  • Double voting (equivocation): валидатор подписал два разных блока для одного слота (double propose) или проголосовал за два разных checkpoint в одну эпоху (surround vote).
  • Вилки без уважительной причины: вложенные голоса, нарушающие Casper правила окружения.

При слэшинге валидатор немедленно теряет минимум 1/32 от 32 ETH = 1 ETH, принудительно выходит из очереди, получает корреляционный штраф (пропорционален доле слэшенных валидаторов в тот же период — если 1/3 сети слэшится одновременно, штраф может достигать 100% стейка). 

// Формула корреляционного штрафа (упрощённо):
penalty = effective_balance × (3 × slashed_fraction) / WHISTLEBLOWER_REWARD_QUOTIENT

// При 1 слэшенном из 500 000 валидаторов:
slashed_fraction ≈ 0.000002  →  penalty ≈ 0.0001 ETH (минимум)

// При одновременном слэшинге 33% (167 000 валидаторов):
slashed_fraction ≈ 0.33  →  penalty ≈ 100% стейка (уничтожение)

4. Финальность

Финальность — гарантия того, что блок уже нельзя изменить или откатить. Разные блокчейны дают разные гарантии:

Сеть Тип финальности Время Гарантия
Ethereum PoS Экономическая (Casper FFG) ~13 минут (2 эпохи) Отмена потребует сжечь >⅓ суммарного стейка (~10B$)
Bitcoin PoW Вероятностная ~60 мин (6 подтверждений) Вероятность отмены <0.1% при 6 блоках
Cosmos (Tendermint) Детерминированная (BFT) ~6 секунд Блок финален сразу после commit (>⅔ подписей)
Solana Оптимистичная + Tower BFT ~400 ms (opt.) / ~32s (confirmed) «Confirmed» = ≥⅔ стейка проголосовали
Arbitrum / Optimism Унаследованная от L1 ~13 мин (Ethereum finality) Транзакция финальна вместе с L1-блоком
Практически: для большинства dApp достаточно 2-3 подтверждений Ethereum (~24-36 сек). Для крупных переводов через биржи — ждут полную финальность (~13 мин). Для MEV-ботов — «soft finality» первого блока.

5. Форки

Форк в блокчейне — это расхождение в правилах протокола или в истории цепочки. Различают три вида:

Soft Fork (обратно совместимый): Старые ноды: A → B → C → D → E (принимают новые блоки как валидные) Новые ноды: A → B → C → D → E (применяют новые правила) Пример: SegWit в Bitcoin (BIP141), EIP-1559 в Ethereum. Hard Fork (несовместимое изменение правил): До форка: A → B → C ↘ D' → E' (новые ноды / новая сеть) ↘ D → E (старые ноды → «умирают» или образуют другую сеть) Пример: Ethereum / Ethereum Classic (2016, DAO hack); Ethereum PoW vs Ethereum PoS (2022, The Merge). Soft Fork высоты (временный форк): Slot N: Validator A и B одновременно предложили блок. Оба блока попали в сеть — временная вилка. LMD-GHOST выбирает «тяжелее» → одна ветка становится канонической.

6. Как транзакция попадает в блок

Полный жизненный цикл транзакции от подписи до финальности: 

Пользователь
  │  wallet.sendTransaction({to, value, data, …})
  ▼
JSON-RPC нода (eth_sendRawTransaction)
  │  проверяет подпись, nonce, balance, gasLimit
  ▼
Mempool (transaction pool)
  │  сортировка по maxPriorityFeePerGas (EIP-1559)
  │  propagation через p2p (gossip protocol)
  ▼
Validator (в назначенном слоте)
  │  1. consensus client запрашивает execution payload у execution client
  │  2. execution client выбирает до gasLimit транзакций из mempool
  │     (алгоритм MEV-Boost / builder API)
  │  3. execution client исполняет транзакции в EVM, строит новый stateRoot
  │  4. consensus client подписывает beacon-блок и BLS-ключом
  ▼
Attesters (128 случайных валидаторов)
  │  проверяют блок за 4 секунды, отправляют attestation
  ▼
Включение в блокчейн (slot + 1)
  │  агрегатор собирает attestations в aggregated signature
  ▼
Финальность (через ~2 эпохи / 13 мин)
  └─ checkpoint стал finalized → транзакция навсегда в истории

7. Виртуальная машина EVM

EVM (Ethereum Virtual Machine) — это детерминированная стек-машина с 256-битными словами. Каждая нода запускает одинаковый код контракта и получает одинаковый результат — это и есть основа консенсуса на уровне смарт-контрактов.

КомпонентОписание
Stack 256-бит, глубина до 1024 слотов. Все операции читают/пишут сюда.
Memory Байтовый массив, расширяется по мере нужды. Очищается после каждого вызова. Стоимость растёт квадратично.
Storage 32→32 bytes ключ-значение, постоянное между вызовами. Самое дорогое: SSTORE = 20 000 gas при записи нового слота.
Calldata Входные данные транзакции. Иммутабельны, дешевле memory (16 gas/байт vs 3).
Code Байткод контракта. Иммутабелен после деплоя (кроме proxy-паттернов).
