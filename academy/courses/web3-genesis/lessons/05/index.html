Tenderly Virtual Testnet — облачный fork и Simulation API

→ продолжение Lesson 04 — Anvil & Foundry. Там мы поднимали локальный fork командой anvil --fork-url. Здесь мы делаем то же самое в облаке, добавляем визуальный отладчик транзакций и Simulation API, который позволяет проверить вызов контракта до отправки в сеть.

Tenderly — это платформа для разработки, отладки и мониторинга смарт-контрактов. Её ключевой инструмент для разработки — Virtual Testnet: управляемый облачный форк любой EVM-сети с публичным RPC, Simulation API, визуальным трассировщиком вызовов и возможностью изменять состояние блокчейна без деплоя. В этом уроке мы разбираем Virtual Testnet от создания до отладки упавших транзакций и решаем четыре практические задачи.

Что вы получите. После этого урока вы умеете: создать Virtual Testnet через UI и через REST API; подключить его к viem и ethers; симулировать транзакцию через Simulation API с state overrides; читать пошаговый execution trace в визуальном отладчике; и воспроизвести упавшую транзакцию без доступа к live-сети.

1. Что такое Tenderly и когда нужен Virtual Testnet

Tenderly предоставляет несколько инструментов, которые часто путают:

Инструмент Что делает Когда использовать
Virtual Testnet Облачный форк сети: постоянный RPC, управляемое состояние, общий доступ по URL Командная разработка, staging-окружение, интеграционные тесты поверх mainnet-состояния
Simulation API Симулировать одну транзакцию или пачку транзакций без отправки, с state overrides Проверить вызов до отправки, посчитать gas, протестировать edge-cases без стоимости
Debugger / Trace Пошаговый визуальный trace EVM-исполнения: opcodes, стек, storage diff Разобрать упавшую транзакцию, найти источник revert, проанализировать gas-потребление
Monitoring / Alerts Мониторинг транзакций на mainnet в реальном времени, вебхуки и Slack-уведомления Production-мониторинг: атаки, неожиданные вызовы, превышение порогов
Web3 Gateway (Node RPC) Managed RPC endpoint к реальным сетям (аналог Alchemy / Infura) Production-RPC с трейсингом «из коробки»

В этом уроке фокус — Virtual Testnet и Simulation API. Мониторинг и Gateway — отдельная тема.

1.1 Virtual Testnet vs Anvil: когда что выбрать

Оба инструмента — форки EVM-сети. Разница — в где они живут и что умеют сверх базового RPC. Детальное сравнение — в разделе 9. Коротко: Anvil лучше для unit-тестов и CI, Virtual Testnet — для командного staging и ручной отладки через UI.

Аккаунт Tenderly. Для этого урока нужен аккаунт на dashboard.tenderly.co. Бесплатный план включает 1 Virtual Testnet, 50 000 симуляций в месяц и доступ к Debugger. Для задач урока этого достаточно.

2. Создание Virtual Testnet через UI (Tenderly Dashboard)

Самый быстрый способ — через браузер. Последовательность действий:

  1. Войдите в dashboard.tenderly.co → выберите или создайте проект.
  2. В левом меню — Virtual Testnets → кнопка Create Virtual Testnet.
  3. Заполните форму:
    • Network — сеть для форка. Доступны Ethereum mainnet, Sepolia, Arbitrum, Optimism, Base, Polygon и другие.
    • Fork Block — номер блока. Оставьте пустым для форка от последнего блока. Для воспроизводимых тестов — зафиксируйте конкретный номер.
    • Chain ID — ID для форка. По умолчанию — 73571. Можно задать произвольный, но не совпадающий с реальными сетями во избежание путаницы в кошельке.
    • Slug — короткое имя для URL. Станет частью RPC endpoint'а.
    • Public/Private — публичный testnet доступен по прямой ссылке без аутентификации; приватный требует токена.
  4. Нажмите Create. Через 5–10 секунд вы получите готовый RPC endpoint вида:
https://virtual.mainnet.rpc.tenderly.co/<YOUR-SLUG>

# Или с явным проектом и токеном (для приватного testnet):
https://virtual.mainnet.rpc.tenderly.co/<ACCOUNT>/<PROJECT>/<SLUG>

После создания на странице Virtual Testnet вы увидите:

  • RPC URL — главный endpoint для MetaMask, viem, cast.
  • Admin RPC URL — для управляющих методов: tenderly_setBalance, tenderly_setStorageAt, evm_snapshot и т.д.
  • Explorer URL — встроенный block explorer, где видны все транзакции на вашем форке.
  • Block number — от какого блока сделан форк.
Admin RPC vs Public RPC. Tenderly разделяет два endpoint'а. Основной RPC работает как обычная нода — только стандартные ETH-методы. Admin RPC добавляет методы управления: установка баланса, манипуляция storage, пауза/продолжение майнинга блоков. В коде держите их раздельно и никогда не отдавайте Admin RPC во фронтенд.

3. Создание через CLI и REST API

В CI/CD и скриптах создавать testnet через браузер неудобно. Tenderly предоставляет REST API и официальный CLI.

3.1 Tenderly CLI

# Установка CLI (требует Node.js 18+)
npm install -g @tenderly/cli

# Авторизация (откроет браузер или предложит ввести токен)
tenderly login

# Создать Virtual Testnet для проекта my-project в аккаунте my-account
tenderly virtual-testnet create \
  --project    my-project \
  --account    my-account \
  --network-id 1 \
  --block-number latest \
  --display-name "mainnet-staging" \
  --slug       mainnet-staging

# Вывод:
# RPC URL: https://virtual.mainnet.rpc.tenderly.co/my-account/my-project/mainnet-staging
# Admin RPC: https://virtual.mainnet.rpc.tenderly.co/my-account/my-project/mainnet-staging/admin

# Список всех testnet'ов в проекте
tenderly virtual-testnet list --project my-project --account my-account

# Удалить testnet
tenderly virtual-testnet delete <TESTNET_ID> --project my-project

3.2 REST API

REST API — более гибкий вариант. Нужен API-ключ: в Dashboard → Account Settings → Authorization → Generate API Key. 

#!/usr/bin/env bash
# Создать Virtual Testnet через REST API
TENDERLY_ACCOUNT="my-account"
TENDERLY_PROJECT="my-project"
TENDERLY_TOKEN="YOUR_API_KEY"

curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/vnets" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data '{
    "slug":          "mainnet-staging",
    "display_name":  "Mainnet Staging Fork",
    "fork_config": {
      "network_id":    1,
      "block_number":  "latest"
    },
    "virtual_network_config": {
      "chain_config": {
        "chain_id": 73571
      }
    },
    "sync_state_config": {
      "enabled": true
    },
    "explorer_page": {
      "enabled": true
    }
  }' | jq '{
    id:       .id,
    rpc_url:  .rpcs[0].url,
    admin_rpc: .rpcs[1].url
  }'

Ответ содержит массив rpcs: первый элемент — публичный RPC, второй — Admin RPC. В скрипте сохраните оба в переменные окружения и передайте в следующие шаги CI. 

# Пример скрипта CI (GitHub Actions): создать testnet, запустить тесты, удалить
#!/usr/bin/env bash
set -euo pipefail

# 1. Создать testnet
RESPONSE=$(curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/vnets" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data "{
    \"slug\": \"ci-run-${GITHUB_RUN_ID}\",
    \"display_name\": \"CI Run ${GITHUB_RUN_ID}\",
    \"fork_config\": { \"network_id\": 1, \"block_number\": \"latest\" },
    \"virtual_network_config\": { \"chain_config\": { \"chain_id\": 73571 } }
  }")

VNET_ID=$(echo "$RESPONSE" | jq -r '.id')
RPC_URL=$(echo  "$RESPONSE" | jq -r '.rpcs[0].url')
ADMIN_RPC=$(echo "$RESPONSE" | jq -r '.rpcs[1].url')

export RPC_URL ADMIN_RPC

# 2. Запустить forge-тесты
forge test --rpc-url "$RPC_URL" -vvv

# 3. Удалить testnet (cleanup)
curl -s -X DELETE \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/vnets/${VNET_ID}" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}"

4. Подключение через viem и ethers

С точки зрения клиентской библиотеки Virtual Testnet — это обычный JSON-RPC endpoint. Никаких специальных SDK не нужно.

4.1 viem

// viem v2 — подключение к Virtual Testnet
import { createPublicClient, createWalletClient, http, defineChain } from "viem";
import { privateKeyToAccount } from "viem/accounts";

// Описываем цепочку (chain ID должен совпадать с тем, что задали при создании)
const tenderlyVnet = defineChain({
  id:   73571,
  name: "Tenderly Virtual Testnet",
  nativeCurrency: { name: "Ether", symbol: "ETH", decimals: 18 },
  rpcUrls: {
    default: {
      http: ["https://virtual.mainnet.rpc.tenderly.co/YOUR-SLUG"],
    },
  },
});

// Публичный клиент — для чтения
const publicClient = createPublicClient({
  chain:     tenderlyVnet,
  transport: http(),
});

// Кошелёк для отправки транзакций
const account = privateKeyToAccount("0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80");
const walletClient = createWalletClient({
  account,
  chain:     tenderlyVnet,
  transport: http(),
});

// Проверяем подключение
const blockNumber = await publicClient.getBlockNumber();
console.log("Block:", blockNumber);

// Читаем баланс
const balance = await publicClient.getBalance({
  address: account.address,
});
console.log("Balance:", balance); // BigInt в wei

5. Simulation API — симуляция транзакций до отправки

Simulation API — самая мощная возможность Tenderly. Он принимает параметры транзакции (from, to, data, value) и возвращает полный результат исполнения: возвращаемые значения, потреблённый газ, все события (logs), storage diff и execution trace — всё это не отправляя транзакцию в сеть и не тратя реальный газ.

5.1 Базовый запрос симуляции

#!/usr/bin/env bash
# Симулировать вызов ERC-20 transfer

TENDERLY_ACCOUNT="my-account"
TENDERLY_PROJECT="my-project"
TENDERLY_TOKEN="YOUR_API_KEY"

# Адрес USDC на mainnet
USDC="0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48"

# Кодируем calldata для transfer(address,uint256)
# transfer(0x70997970..., 1000_000) = 1 USDC (6 decimals)
# ABI-кодирование функции transfer:
#   selector: a9059cbb
#   to:       000000000000000000000000 70997970c51812dc3a010c7d01b50e0d17dc79c8
#   amount:   00000000000000000000000000000000000000000000000000000000000f4240

curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/simulate" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data '{
    "network_id":   "1",
    "from":         "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266",
    "to":           "0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48",
    "input":        "0xa9059cbb00000000000000000000000070997970c51812dc3a010c7d01b50e0d17dc79c800000000000000000000000000000000000000000000000000000000000f4240",
    "gas":          100000,
    "gas_price":    "0",
    "value":        "0",
    "save":         true,
    "save_if_fails": true
  }' | jq '{
    status:   .transaction.status,
    gas_used: .transaction.gas_used,
    logs:     [.transaction.transaction_info.logs[]?.raw.topics],
    revert:   .transaction.error_message
  }'

Ответ при успешной симуляции:

{
  "status":   true,
  "gas_used": 34217,
  "logs":     [
    ["0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef",
     "0x000000000000000000000000f39fd6e51aad88f6f4ce6ab8827279cfffb92266",
     "0x00000000000000000000000070997970c51812dc3a010c7d01b50e0d17dc79c8"]
  ],
  "revert": null
}

Первый topic в logs — это keccak256 сигнатуры события Transfer(address,address,uint256). Мы видим, что симуляция выпустила Transfer-событие, то есть transfer() завершился успешно, хотя ни одна реальная транзакция в сеть не отправлялась.

5.2 State Overrides в симуляции

Главная возможность — указать state overrides: переопределить баланс, код контракта или конкретные storage-слоты только для этой симуляции, не изменяя реальное состояние сети. 

# Симуляция с state overrides: устанавливаем баланс USDC для адреса before simulate
# Это позволяет проверить transfer от адреса, у которого нет USDC на mainnet

curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/simulate" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data '{
    "network_id": "1",
    "from":       "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266",
    "to":         "0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48",
    "input":      "0xa9059cbb00000000000000000000000070997970c51812dc3a010c7d01b50e0d17dc79c800000000000000000000000000000000000000000000000000000000000f4240",
    "gas":        100000,
    "gas_price":  "0",
    "value":      "0",
    "state_objects": {
      "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266": {
        "balance": "0xDE0B6B3A7640000"
      },
      "0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48": {
        "storage": {
          "0x10d6a54a4754c8869d6886b5f5d7fbfa5b4522237ea5c60d11bc4e7a1ff9390b":
            "0x0000000000000000000000000000000000000000000000000000000005F5E100"
        }
      }
    },
    "save": true
  }'
Вычисление storage slot для mapping. В ERC-20 (OpenZeppelin) балансы хранятся в mapping(address => uint256) _balances (slot 0). Slot для конкретного ключа: keccak256(abi.encode(address, slot_index)). Для адреса 0xf39F... и slot 0 вычисляем: cast index address 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266 0. Для USDC (upgradeable proxy) структура другая — сначала проверьте layout через forge inspect USDC storage-layout или Tenderly Storage Inspector.

6. Визуальный отладчик — trace execution шаг за шагом

Каждая симуляция с параметром "save": true, а также каждая транзакция, отправленная через Virtual Testnet, появляется в списке Simulations или Transactions в Dashboard. Нажмите на любую из них, чтобы открыть Debugger.

6.1 Execution Trace

Центральный элемент Debugger — Execution Trace: дерево вызовов, где каждая строка — один CALL, STATICCALL, DELEGATECALL или внутренний вызов функции. Для каждого вызова видны:

  • Вызываемая функция (декодированное имя, если контракт верифицирован).
  • Параметры вызова (декодированные из calldata).
  • Возвращаемое значение.
  • Gas spent на этот вызов.
  • Статус: success / revert (и причина revert).
Пример Execution Trace для USDC transfer():

Transaction: 0xabc...
  Status: Success
  Gas used: 34 217 / 100 000

[0] ERC20.transfer(to=0x7099..., amount=1000000)
    Gas: 34 217
    Return: true
  [1] ERC20._transfer(from=0xf39F..., to=0x7099..., amount=1000000)
      Gas: 29 051
    [2] ERC20._beforeTokenTransfer(...)
        Gas: 421
    [2] ERC20._afterTokenTransfer(...)
        Gas: 389
    [2] emit Transfer(from=0xf39F..., to=0x7099..., amount=1000000)
        Gas: 1 125
  [1] Return: void

6.2 Opcodes View

Переключитесь на вкладку Opcodes, чтобы увидеть пошаговое исполнение EVM: каждую инструкцию, состояние стека (stack), текущий memory и storage. Это нужно при анализе:

  • Точного места REVERT — на каком opcode упал контракт.
  • Reentrancy — видно повторный вход через CALL.
  • Gas optimization — найти SLOAD/SSTORE в неожиданных местах.

6.3 State Diff

Вкладка State Changes показывает все изменения storage по всем адресам, которые затронула транзакция. Формат: 

Contract: 0xa0b8...eb48 (USDC)
  Slot 0x10d6a5...390b (balances[0xf39F...]):
    Before: 0x0000...05F5E100   (100_000_000, то есть 100 USDC)
    After:  0x0000...04C4B400   (79_000_000 = 79 USDC)

  Slot 0xe6f1...9a2c (balances[0x7099...]):
    Before: 0x0000...00000000   (0 USDC)
    After:  0x0000...000F4240   (1_000_000 = 1 USDC)
Decoding без верифицированного кода. Если контракт не верифицирован на Etherscan, Tenderly попробует декодировать ABI из своей базы (отслеживает все опубликованные контракты). Для своих контрактов — загрузите ABI вручную через Settings → Contracts в проекте, или верифицируйте через forge verify-contract.

7. State Overrides на Virtual Testnet

В отличие от state overrides в симуляции (которые действуют только для одного вызова), постоянные state overrides на Virtual Testnet изменяют состояние форка навсегда — до следующего сброса или явного изменения. Это делается через Admin RPC или через UI (вкладка State в Virtual Testnet).

7.1 Установить баланс ETH

# Через Admin RPC (JSON-RPC метод tenderly_setBalance)
# Устанавливаем 100 ETH на адрес 0xf39F...

curl -s -X POST "$ADMIN_RPC" \
  -H "Content-Type: application/json" \
  --data '{
    "jsonrpc": "2.0",
    "id":      1,
    "method":  "tenderly_setBalance",
    "params": [
      ["0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266"],
      "0x56BC75E2D63100000"
    ]
  }'

# Проверить:
cast balance 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266 --ether \

7.4 Snapshot и Revert

Virtual Testnet поддерживает Ethereum-стандартные методы для создания снимка состояния и отката к нему: 

# Сохранить снимок текущего состояния
SNAPSHOT_ID=$(cast rpc evm_snapshot --rpc-url "$ADMIN_RPC" | tr -d '"')
echo "Snapshot: $SNAPSHOT_ID"

# ... делаем что-то: деплои, транзакции, изменения storage

# Откатиться к снимку
cast rpc evm_revert "$SNAPSHOT_ID" --rpc-url "$ADMIN_RPC"

# После revert нужен новый snapshot для следующего цикла
# (snapshot одноразовый — после использования недействителен)

Задача 2: Simulation API — симулировать ERC-20 transfer

Цель: через Simulation API симулировать USDC.transfer() от адреса, у которого нет USDC на mainnet, используя state override. 

#!/usr/bin/env bash
set -euo pipefail

TENDERLY_ACCOUNT="YOUR_ACCOUNT"
TENDERLY_PROJECT="YOUR_PROJECT"
TENDERLY_TOKEN="YOUR_API_KEY"

USDC="0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48"
FROM="0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266"
TO="0x70997970C51812dc3A010C7d01b50e0d17dc79C8"
AMOUNT=1000000   # 1 USDC (6 decimals)

# Вычислить storage slot для balances[FROM] в USDC (slot 9 для USDC-proxy layout)
# Для OpenZeppelin ERC-20: slot 0; для USDC FiatToken: используем slot 9
# Точное значение: cast index address $FROM 9
# Для примера берём заранее известный slot USDC:
USDC_BALANCE_SLOT="0x10d6a54a4754c8869d6886b5f5d7fbfa5b4522237ea5c60d11bc4e7a1ff9390b"

# calldata для transfer(address to, uint256 amount)
CALLDATA="0xa9059cbb"
CALLDATA+="00000000000000000000000070997970c51812dc3a010c7d01b50e0d17dc79c8"  # to (padded)
CALLDATA+="00000000000000000000000000000000000000000000000000000000000f4240"  # 1 USDC

RESPONSE=$(curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/simulate" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data "{
    \"network_id\":  \"1\",
    \"from\":        \"${FROM}\",
    \"to\":          \"${USDC}\",
    \"input\":       \"${CALLDATA}\",
    \"gas\":         100000,
    \"gas_price\":   \"0\",
    \"value\":       \"0\",
    \"state_objects\": {
      \"${FROM}\": {
        \"balance\": \"0x56BC75E2D63100000\"
      },
      \"${USDC}\": {
        \"storage\": {
          \"${USDC_BALANCE_SLOT}\": \"0x0000000000000000000000000000000000000000000000000000000005F5E100\"
        }
      }
    },
    \"save\": true,
    \"save_if_fails\": true
  }")

echo "$RESPONSE" | jq '{
  status:        .transaction.status,
  gas_used:      .transaction.gas_used,
  simulation_id: .simulation.id,
  error:         .transaction.error_message
}'

# Получить ссылку на debugger:
SIM_ID=$(echo "$RESPONSE" | jq -r '.simulation.id')
echo ""
echo "Debugger URL:"
echo "https://dashboard.tenderly.co/${TENDERLY_ACCOUNT}/${TENDERLY_PROJECT}/simulator/${SIM_ID}"

Задача 4: Воспроизвести failed transaction через Debugger

Цель: симулировать транзакцию, которая завершится с revert, открыть её в Debugger и найти точное место падения в коде контракта. 

### Шаг 1. Создать контракт с намеренным revert
cat > /tmp/Vault.sol << 'SOLIDITY'
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Vault {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "Vault: insufficient balance");
        balances[msg.sender] -= amount;
        (bool ok,) = msg.sender.call{value: amount}("");
        require(ok, "Vault: transfer failed");
    }
}
SOLIDITY

# Деплоим контракт (аналогично задаче 3)
VAULT_BYTECODE=$(forge inspect Vault bytecode 2>/dev/null || echo "")
# ... деплой ...
VAULT="0x..."   # адрес задеплоенного Vault

### Шаг 2. Симулировать withdraw без предварительного deposit (вызовет revert)
TENDERLY_ACCOUNT="YOUR_ACCOUNT"
TENDERLY_PROJECT="YOUR_PROJECT"
TENDERLY_TOKEN="YOUR_API_KEY"

# calldata для withdraw(uint256 amount) с amount=1 ETH
# withdraw(1000000000000000000) → selector: 2e1a7d4d + amount padded
CALLDATA="0x2e1a7d4d0000000000000000000000000000000000000000000000000de0b6b3a7640000"

curl -s -X POST \
  "https://api.tenderly.co/api/v1/account/${TENDERLY_ACCOUNT}/project/${TENDERLY_PROJECT}/simulate" \
  -H "Content-Type: application/json" \
  -H "X-Access-Key: ${TENDERLY_TOKEN}" \
  --data "{
    \"network_id\":   \"1\",
    \"from\":         \"0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266\",
    \"to\":           \"${VAULT}\",
    \"input\":        \"${CALLDATA}\",
    \"gas\":          100000,
    \"gas_price\":    \"0\",
    \"value\":        \"0\",
    \"save\":         true,
    \"save_if_fails\": true

    status:    .transaction.status,

#   "error_msg": "Vault: insufficient balance",

### Шаг 3. Открыть Debugger
# Dashboard → Simulations → кликнуть на упавшую симуляцию
# Во вкладке Execution Trace найти строку с REVERT:
#   [0] Vault.withdraw(amount=1000000000000000000)
#       Gas: 2 831
#       ERROR: Vault: insufficient balance
#     [1] require(balances[msg.sender] >= amount, ...)   ← revert здесь
#
# Вкладка Opcodes → прокрутить до REVERT:
#   PUSH1 0x00
#   REVERT
#
# Вкладка State Changes → пусто (транзакция не изменила state)
Revert reason. Tenderly декодирует причину revert автоматически: если это require(condition, "message") — показывает строку. Если кастомная ошибка (error InsufficientBalance(uint256 have, uint256 need)) — декодирует и параметры. Если revert без причины — показывает hex revert data и предлагает ввести ABI вручную.

9. Сравнение Tenderly Virtual Testnet vs Anvil

Параметр Anvil (Foundry) Tenderly Virtual Testnet
Где работает Локально, в памяти или на сервере В облаке Tenderly
Доступность Только пока запущен процесс anvil Постоянно по URL (пока не удалите)
Командный доступ Требует expose через ngrok/tunnel или VPN Публичный RPC URL, доступен всей команде
Визуальный дебаггер Нет (только CLI: cast run, forge test -vvvv) Полноценный UI с деревом вызовов, opcodes, state diff
Simulation API eth_call / forge simulate (нет state overrides для сторонних) Полноценный API с state overrides, batch-симуляцией, сохранением результатов
Скорость старта < 1 секунды (localhost) 5–15 секунд (cloud)
Latency запросов Минимальная (localhost) 50–200 мс (зависит от региона)
Интеграция с forge test Нативная: forge test --fork-url Через RPC URL: forge test --rpc-url $VNET_RPC
Persistence state Только через dump/load (--dump-state, --load-state) Постоянно, пока testnet существует
Snapshot / Revert evm_snapshot / evm_revert evm_snapshot / evm_revert (совместимо)
State overrides (постоянные) tenderly_setBalance / anvil_setBalance tenderly_setBalance / tenderly_setStorageAt
Цена Бесплатно (open-source) Бесплатный план: 1 testnet, 50k симуляций/месяц
Идеально для Unit-тесты, CI/CD, быстрая локальная разработка Staging, командные демо, отладка сложных сценариев

На практике оба инструмента используются вместе: Anvil — для быстрых unit-тестов (forge test), Tenderly Virtual Testnet — для staging-окружения и разбора инцидентов. Это не выбор «или / или».
