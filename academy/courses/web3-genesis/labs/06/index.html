Lab 06 · Upgradeable Proxy (UUPS)

Смарт-контракты на EVM по умолчанию неизменяемы: задеплоенный байткод нельзя переписать. Тем не менее большинство production-протоколов нуждаются в возможности исправлять баги и добавлять функции, сохраняя адрес контракта и все накопленные данные. Решение — паттерн прокси: пользователи взаимодействуют с «тонкой» оболочкой (proxy), которая через delegatecall перенаправляет вызовы в сменную реализацию (implementation). В этом лабе вы пройдёте полный цикл: деплой, апгрейд, сломаете хранилище намеренно и снова починете — чтобы понять риски изнутри.

Цели лаба. После выполнения всех заданий вы сможете: разворачивать контракты через UUPS-прокси с плагином OpenZeppelin Upgrades; объяснять разницу между UUPS и Transparent Proxy; безопасно добавлять переменные в storage layout, не вызывая коллизий; читать ERC-1967 слот, чтобы убедиться в смене реализации; воспроизводить и диагностировать storage collision при переименовании переменных; деплоить и верифицировать оба контракта на Sepolia.

Задание 1

Инициализируйте Hardhat-проект с плагином @openzeppelin/hardhat-upgrades и напишите простой счётчик CounterV1, готовый к проксированию через UUPS.

Подготовка окружения

mkdir counter-uups && cd counter-uups
npm init -y
npm install --save-dev hardhat @nomicfoundation/hardhat-toolbox \
  @openzeppelin/hardhat-upgrades \
  @openzeppelin/contracts-upgradeable

npx hardhat init   # выберите "Create a TypeScript project"

contracts/CounterV1.sol

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

contract CounterV1 is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    // Slot 0: _initialized + _initializing (Initializable)
    // Slot 1..n: OwnableUpgradeable внутренние переменные
    // --- ваши переменные ПОСЛЕ унаследованных ---
    uint256 public count;       // slot N (зависит от родителей)

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    function initialize(address initialOwner) public initializer {
        __Ownable_init(initialOwner);
        __UUPSUpgradeable_init();
        count = 0;
    }

    function increment() external {
        count += 1;
    }

    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner
    {}
}

scripts/deploy.ts

import { ethers, upgrades } from "hardhat";

async function main() {
  const [deployer] = await ethers.getSigners();
  console.log("Deploying with:", deployer.address);

  const CounterV1 = await ethers.getContractFactory("CounterV1");

  // deployProxy автоматически деплоит ERC1967Proxy + вызывает initialize()
  const proxy = await upgrades.deployProxy(CounterV1, [deployer.address], {
    kind: "uups",
  });
  await proxy.waitForDeployment();

  console.log("Proxy deployed at:", await proxy.getAddress());
}

main().catch((e) => { console.error(e); process.exitCode = 1; });
npx hardhat run scripts/deploy.ts --network localhost

Проверьте: после деплоя вызовите proxy.count() — должно вернуть 0. Вызовите proxy.increment() три раза, затем снова count() — ожидаемый результат: 3.

Задание 2

Изучите layout хранилища и добавьте новую переменную правильно — только в конец списка. Проверьте отсутствие коллизий с помощью плагина Foundry forge inspect и сравните слоты вручную.

Правила безопасного расширения storage

ДействиеБезопасно?Причина
Добавить переменную в конец Да Существующие слоты не сдвигаются
Добавить переменную в начало или между Нет Все последующие переменные сдвигаются на N слотов
Переименовать переменную (тот же тип) Да (на уровне EVM) Слоты определяются порядком, не именем; но плагин предупредит
Изменить тип переменной (uint128 → uint256) Нет Размер слота изменяется, прочитанные биты сдвигаются
Удалить переменную Нет Последующие переменные занимают освободившийся слот, значения перепутаются

# Если у вас установлен Foundry:

Задание 3

Напишите CounterV2 с новым методом incrementBy(uint256) и строковым полем label. Выполните апгрейд через upgrades.upgradeProxy().

contracts/CounterV2.sol

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";

contract CounterV2 is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    uint256 public count;       // slot N — сохраняем на месте
    string  public label;       // slot N+1 — новая переменная в конце

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() { _disableInitializers(); }

    function initialize(address initialOwner) public initializer {
        __Ownable_init(initialOwner);
        __UUPSUpgradeable_init();
    }

    function increment() external {
        count += 1;
    }

    // НОВАЯ функция:
    function incrementBy(uint256 amount) external {
        count += amount;
    }

    function setLabel(string calldata _label) external onlyOwner {
        label = _label;
    }

    function _authorizeUpgrade(address newImplementation)
        internal override onlyOwner {}
}

scripts/upgrade.ts

import { ethers, upgrades } from "hardhat";

const PROXY_ADDRESS = "0x..."; // адрес из Задания 1

async function main() {
  const CounterV2 = await ethers.getContractFactory("CounterV2");

  const upgraded = await upgrades.upgradeProxy(PROXY_ADDRESS, CounterV2);
  await upgraded.waitForDeployment();

  console.log("Proxy upgraded. Address (должен совпасть):", await upgraded.getAddress());

  // Проверяем новую функцию:
  await upgraded.incrementBy(10);
  console.log("count после incrementBy(10):", await upgraded.count());
}

main().catch((e) => { console.error(e); process.exitCode = 1; });
npx hardhat run scripts/upgrade.ts --network localhost

Адрес прокси не изменится. Изменится только адрес реализации, который прокси хранит во внутреннем ERC-1967 слоте.

Задание 4

Убедитесь в смене реализации напрямую через ERC-1967 storage slot. Проверьте адрес реализации до и после апгрейда.

Читаем ERC-1967 implementation slot

// ERC-1967 определяет фиксированный слот для адреса реализации:
// keccak256("eip1967.proxy.implementation") - 1
// = 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc

import { ethers } from "hardhat";

async function checkImplementation(proxyAddress: string) {
  const IMPL_SLOT =
    "0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc";

  const raw = await ethers.provider.getStorage(proxyAddress, IMPL_SLOT);
  // raw — 32 байта, адрес находится в последних 20 байтах
  const implAddress = ethers.getAddress("0x" + raw.slice(-40));
  console.log("Implementation address:", implAddress);
  return implAddress;
}

// Вызовите до и после upgrade:
const before = await checkImplementation(PROXY_ADDRESS);
// ... запустите upgrade ...
const after = await checkImplementation(PROXY_ADDRESS);
console.log("Changed:", before !== after);

Также воспользуйтесь встроенным хелпером плагина: 

import { upgrades } from "hardhat";

const implAddr = await upgrades.erc1967.getImplementationAddress(PROXY_ADDRESS);
console.log("Impl via plugin:", implAddr);

Задание 5

Проверьте сохранность хранилища после апгрейда: значение счётчика, установленное в V1, должно быть доступно через V2-интерфейс.

scripts/check-storage.ts

import { ethers, upgrades } from "hardhat";

const PROXY_ADDRESS = "0x...";

async function main() {
  // Шаг 1: получаем текущий count через V2 ABI
  const counter = await ethers.getContractAt("CounterV2", PROXY_ADDRESS);
  const countBefore = await counter.count();
  console.log("count до apgrade:", countBefore.toString());

  // Шаг 2: вызываем новую функцию
  const tx = await counter.incrementBy(5);
  await tx.wait();

  const countAfter = await counter.count();
  console.log("count после incrementBy(5):", countAfter.toString());

  // Проверяем инвариант: countAfter === countBefore + 5
  const expected = countBefore + 5n;
  console.assert(countAfter === expected, `Ожидали ${expected}, получили ${countAfter}`);
  console.log("Хранилище сохранено корректно.");
}

main().catch((e) => { console.error(e); process.exitCode = 1; });

Если апгрейд нарушил storage layout, значения смешаются и вы увидите неожиданные числа. В правильном сценарии countBefore должен совпасть со значением, накопленным в V1.

Задание 6

Намеренно сломайте хранилище: в новой версии контракта поменяйте порядок переменных — поставьте label перед count. Наблюдайте за коллизией.

contracts/CounterV2_BROKEN.sol — плохой пример

// ВНИМАНИЕ: это намеренно сломанный контракт для демонстрации коллизии
contract CounterV2_BROKEN is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    // ОШИБКА: label добавлена перед count — сдвигает count на следующий слот!
    string  public label;       // займёт slot N (бывший slot count)
    uint256 public count;       // переедет на slot N+1 — ТЕРЯЕТ старое значение
    // ...
}

Диагностика через forge

# Сравните layout до и после:
forge inspect CounterV1 storage-layout --pretty > layout_v1.txt
forge inspect CounterV2_BROKEN storage-layout --pretty > layout_broken.txt
diff layout_v1.txt layout_broken.txt

# Или используйте плагин hardhat-upgrades — он откажется апгрейдить:
# Error: New storage layout is incompatible:
# Storage variable "count" was removed at slot 1

Что произойдёт при апгрейде

// После апгрейда на сломанную версию:
const broken = await ethers.getContractAt("CounterV2_BROKEN", PROXY_ADDRESS);

// Слот N содержит старое значение count (например 3), но теперь он трактуется
// как bytes строки label — вы увидите мусор вместо строки:
console.log("label:", await broken.label());  // <- бинарный мусор

// Слот N+1 был пустым (нулём), поэтому count "потерял" своё значение:
console.log("count:", await broken.count());  // <- 0 вместо 3

Плагин @openzeppelin/hardhat-upgrades по умолчанию проверяет совместимость и отказывает в апгрейде с ошибкой. Чтобы воспроизвести эффект — используйте unsafeAllow: ["delegatecall"] или напишите тест с ручным delegatecall. Никогда не делайте это в production.

Задание 7

Задеплойте прокси и реализацию на Sepolia через Hardhat, затем верифицируйте оба контракта на Etherscan.

hardhat.config.ts — добавьте Sepolia

import { HardhatUserConfig } from "hardhat/config";
import "@nomicfoundation/hardhat-toolbox";
import "@openzeppelin/hardhat-upgrades";

const config: HardhatUserConfig = {
  solidity: "0.8.24",
  networks: {
    sepolia: {
      url: process.env.SEPOLIA_RPC_URL ?? "",
      accounts: process.env.PRIVATE_KEY ? [process.env.PRIVATE_KEY] : [],
    },
  },
  etherscan: {
    apiKey: process.env.ETHERSCAN_API_KEY ?? "",
  },
};

export default config;

Деплой на Sepolia

# .env
SEPOLIA_RPC_URL=https://sepolia.infura.io/v3/YOUR_KEY
PRIVATE_KEY=0xabc...   # тестовый ключ без реальных средств
ETHERSCAN_API_KEY=YOUR_ETHERSCAN_KEY

npx hardhat run scripts/deploy.ts --network sepolia

Верификация

# Верификация реализации:
npx hardhat verify --network sepolia IMPLEMENTATION_ADDRESS

# Верификация прокси (Etherscan умеет распознавать ERC-1967):
npx hardhat verify --network sepolia PROXY_ADDRESS

# Плагин предоставляет удобную обёртку:
# upgrades.verifyProxy(PROXY_ADDRESS)

После верификации на Sepolia Etherscan вы увидите вкладку «Read as Proxy» / «Write as Proxy» — Etherscan автоматически показывает ABI реализации поверх адреса прокси благодаря ERC-1967 слоту.

Контракты используют OpenZeppelin Contracts Upgradeable v5. Для Foundry-проектов аналогичную функциональность предоставляет forge-std с UUPSUpgradeable из @openzeppelin/contracts-upgradeable. Никогда не деплойте тестовые ключи с реальными средствами на mainnet.
