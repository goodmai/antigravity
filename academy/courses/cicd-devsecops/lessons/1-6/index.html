Module 1 — CI/CD Foundations · Lesson 1.6 · promotion

Правильный деплой: PR → test → dev → prod

→ продолжение Lesson 1.5 — Runners. Там вы научились где выполняется пайплайн; здесь — куда и в каком порядке едет ваш артефакт, прежде чем его увидит пользователь.

Канон: GitHub Environments, The Twelve-Factor App · Config, Fowler · Blue-Green Deployment, GitHub: secrets vs variables.

Деплой «правильно» — это не «нажал кнопку и выкатил на прод». Это конвейер сред (environment promotion): один и тот же неизменяемый артефакт последовательно проходит изолированные среды, и на каждой границе стоит автоматический или ручной гейт. Код двигается только вперёд и только через Pull Request — никаких прямых пушей в защищённые ветки.

Главный принцип — build once, promote many. Артефакт (контейнер по digest @sha256:…, а не по тегу latest) собирается один раз и затем продвигается между средами как есть. Если для прода вы пересобираете образ — вы тестировали не то, что выкатываете.

1. Карта сред и поток продвижения

Минимальная зрелая модель — четыре границы. Feature-ветка живёт меньше дня (trunk-based, см. Lesson 1.2), попадает в main только через PR, а дальше один и тот же build «всплывает» по средам.

Почему именно так. test ловит регрессии без участия человека (быстрая обратная связь). dev/staging — последняя «человеческая» проверка на максимально prod-подобной среде. prod получает ровно тот же цифровой отпечаток артефакта, что прошёл dev — отсюда предсказуемость.

2. Pull Request как единственный вход

Ветка main защищена (см. Lesson 1.2 — protected branches): прямой git push запрещён, форс-пуш заблокирован, нужен ≥1 ревьюер по CODEOWNERS, обязательны зелёные статус-чеки и подписанные коммиты. Поток разработчика:

  1. Создаёт feature/JIRA-123-short-slug от свежего main.
  2. Пушит — открывается PR, поднимается эфемерное PR-preview окружение.
  3. CI прогоняет lint → unit → SAST → SCA → build → e2e на preview.
  4. Ревьюер аппрувит, ветка сливается squash-merge в main.
  5. Merge в main автоматически запускает деплой в test.
# .github/workflows/promote.yml
name: build-and-promote
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write          # OIDC, без long-lived ключей
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - id: push
        run: |
          IMAGE=ghcr.io/${{ github.repository }}
          docker build -t "$IMAGE:${{ github.sha }}" .
          docker push "$IMAGE:${{ github.sha }}"
          echo "digest=$(docker inspect --format='{{index .RepoDigests 0}}' \
            "$IMAGE:${{ github.sha }}")" >> "$GITHUB_OUTPUT"

  deploy-test:
    needs: build
    environment: test            # без required reviewers — авто
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh "${{ needs.build.outputs.digest }}"

  deploy-dev:
    needs: [build, deploy-test]
    environment: dev             # required reviewers → ручной approve
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh "${{ needs.build.outputs.digest }}"

  deploy-prod:
    needs: [build, deploy-dev]
    environment: prod            # required reviewers + wait timer + branch rule
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh "${{ needs.build.outputs.digest }}"
Обратите внимание: deploy-prod зависит от build и переиспользует needs.build.outputs.digest. Один digest проходит test → dev → prod. Гейты настраиваются не в YAML, а в GitHub → Settings → Environments (required reviewers, wait timer, deployment branches), чтобы правила нельзя было обойти правкой workflow в PR.

3. Стратегия выката на prod

«Доехать до prod» — половина дела. Сам выкат не должен ронять трафик:

  • Rolling update — дефолт в k8s: поды заменяются пачками, readinessProbe держит трафик от неготовых.
  • Blue-Green — две идентичные среды, переключение роутера; мгновенный откат сменой указателя.
  • Canary — 1% → 5% → 25% → 100% трафика с авто-rollback по SLO/ошибкам (см. Lesson 6.5 — error budget).

После переключения — smoke-тест (health, ключевой бизнес-сценарий) и наблюдение за метриками в окне стабилизации. Не прошло — автоматический откат на предыдущий digest.

4. Переменные окружения и конфигурация по средам

Артефакт неизменяем, а среды разные — значит, всё, что отличается между test, dev и prod, выносится в конфигурацию, а не в код и не в образ. Это III фактор 12-factor: strict separation of config from code. Проверка: репозиторий можно открыть в open-source хоть завтра — и ни один секрет не утечёт.

4.1. Два класса значений: variables vs secrets

Variables (не-секрет)Secrets
ПримерыLOG_LEVEL, API_BASE_URL, FEATURE_X=true, REGIONDB_PASSWORD, JWT_SIGNING_KEY, STRIPE_SK, токены
ХранилищеGitHub Environment variables, ConfigMap, .env (не секреты)Vault / AWS SM / Sealed Secrets / GH Encrypted Secrets
В логахможно печататьникогда (mask, ::add-mask::)
Ротацияредкорегулярно + при инциденте
Граница, которую нельзя стирать. Секрет в коде, в Dockerfile (ENV TOKEN=…), в git-истории или в логах CI — это инцидент, а не «потом почистим». Секреты приходят в рантайме из секрет-стора (детально — Lesson 5.1), переменные — из конфигурации среды.

4.2. Одно имя — разные значения по средам

Ключевая идея: имя переменной одинаковое во всех средах, значение — разное. Приложение читает DATABASE_URL и не знает, где запущено. «Куда» определяет среда, а не if env == 'prod' в коде. 

# GitHub: Settings → Environments → <среда> → Variables / Secrets
# одно имя, три значения:

test  →  API_BASE_URL = https://api.test.internal
dev   →  API_BASE_URL = https://api.staging.example.com
prod  →  API_BASE_URL = https://api.example.com

# в workflow значение подтягивается по environment job'а:
#   env:
#     API_BASE_URL: ${{ vars.API_BASE_URL }}
#     DB_PASSWORD:  ${{ secrets.DB_PASSWORD }}

В Kubernetes тот же принцип — overlay на среду:

# base/deployment.yaml — общее, без значений
envFrom:
  - configMapRef: { name: app-config }   # не-секреты
  - secretRef:    { name: app-secrets }  # из ESO/Sealed Secrets

# overlays/prod/config.yaml — значения именно для prod
apiVersion: v1
kind: ConfigMap
metadata: { name: app-config }
data:
  LOG_LEVEL: "warn"
  API_BASE_URL: "https://api.example.com"

4.3. Приоритет источников (precedence)

Когда переменная задана в нескольких местах, должен быть один предсказуемый порядок. Типовой приоритет — от низшего к высшему:

  1. дефолты в коде/образе (безопасные, dev-подобные);
  2. .env-файл (только локальная разработка, в .gitignore);
  3. ConfigMap / GitHub Environment variables (per-env не-секреты);
  4. Secret-store (Vault/SM) — секреты per-env;
  5. явный env: в шаге/манифесте (узкий override, осознанно).
Build-time vs run-time. Переменная, «вшитая» в образ на сборке (build-arg, бандл фронтенда), не поддаётся promotion — под каждую среду пришлось бы пересобирать. Конфигурация, влияющая на поведение между средами, должна читаться в рантайме. Build-time оставляем только для того, что одинаково везде.

4.4. Контракт переменных и фейл-фаст

Приложение должно падать на старте, если обязательная переменная не задана или невалидна, — а не отдавать 500 под нагрузкой. Документируйте контракт в .env.example (без значений) и валидируйте при инициализации. 

# .env.example — коммитится, описывает контракт, без секретов
APP_ENV=                 # test | dev | prod
LOG_LEVEL=info
API_BASE_URL=
DATABASE_URL=            # secret, приходит из стора, здесь пусто
FEATURE_NEW_CHECKOUT=false

Чек-лист урока

  • Артефакт собирается один раз и продвигается по digest, не пересобирается под prod.
  • В main нельзя пушить напрямую — только squash-merge через PR с зелёным CI.
  • Среды test → dev → prod, гейты заданы в Settings → Environments, не в YAML.
  • На prod — rolling/blue-green/canary + smoke-тест + авто-rollback по SLO.
  • Одно имя переменной — разные значения по средам; конфиг отделён от кода.
  • Secrets ≠ variables: секреты только из стора, не в коде/образе/логах.
  • Приложение фейлит старт при отсутствии обязательной переменной; есть .env.example.
