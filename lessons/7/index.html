Урок 7: QA Architect — мета-скилл qa-skill-tester

До сих пор мы создавали скиллы и запускали их. Этот урок переводит вас в роль Test Architect: вы строите систему, которая автоматически тестирует другие скиллы Antigravity. Качество вашего инструментария теперь — измеряемая величина.

Проблема, которую решаем

Скиллы — это код, который пишут люди для агента. У него есть:

  • API-поверхность (триггеры, аргументы, ожидаемый выход);
  • side-effects (создаёт файлы, дёргает API, тратит токены);
  • регрессии (новая версия описания убивает старые триггеры).

Ручное тестирование 17+ скиллов невозможно. Нужен мета-скилл, который превращает QA в воспроизводимый автоматический процесс.

Архитектура qa-skill-tester

┌──────────────────────────┐
│ 0. Persona Generation    │  Qwen → "QA Lead",  Gemini → "Test Architect"
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 1. Test Plan             │  читает SKILL.md, формирует план в .md
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 2. Checklist (.xlsx)     │  Frontend / API / Readability / Overlaps / Links
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 3. Execution             │  реальный запуск скилла + сбор артефактов
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 4. Validation (QA Lead)  │  Qwen валидирует каждый чек по чек-листу
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 5. Bug Report (.docx)    │  severity, repro, expected/actual
└────────────┬─────────────┘
             ▼
┌──────────────────────────┐
│ 6. Archival              │  artifacts/<skill>/test/<timestamp>/
└──────────────────────────┘

Слой 0. Персонажи (CO-STAR)

python skills/qa-skill-tester/scripts/optimize_qa_prompts.py

Генерируются два промпта:

  • qa_lead_prompt.txt — Qwen в роли «QA Lead»: критичен, проверяет читаемость, ищет противоречия.
  • test_architect_prompt.txt — Gemini в роли «Test Architect»: строит план и чек-лист по SKILL.md.

Important

Разделение ролей даёт независимое второе мнение: один и тот же скилл не может «защитить сам себя» — план составляет один агент, оценивает другой.

Слой 1. Test Plan

Test Architect читает SKILL.md и строит план:

# Test plan: skills/pptx

## Scope
- Создание .pptx
- Изменение существующего .pptx
- Совместимость с LibreOffice

## Inputs
- T1: «Создай питч-дек продукта на 5 слайдов»
- T2: «Добавь слайд с диаграммой в presentation.pptx»
- T3: невалидный запрос «открой .pptx» (out of scope → должен отказать)

## Expected
- T1: файл существует, 5 слайдов, заголовки заполнены
- T2: 6 слайдов, новый — последний, диаграмма читается
- T3: вежливый отказ + предложение альтернативы

Слой 2. Checklist (.xlsx)

Обязательные пять колонок проверок:

Категория Что проверяем
Frontend Читаемость текста, отсутствие наложений (overlap), кликабельность
API Корректность аргументов скрипта, exit code, формат вывода
Readability SKILL.md понятен новичку, нет жаргона без расшифровки
Overlaps Скилл не дублирует другой (например, два «PR review»)
Broken links Все @/path и URL в SKILL.md ведут к существующим ресурсам

Файл генерируется через skills/xlsx с формулами-счётчиками PASS/FAIL/SKIP.

Слой 3. Execution

.venv/bin/python skills/qa-skill-tester/scripts/run_qa.py \
    --target skills/pptx \
    --inputs artifacts/qa/pptx/test_plan.md

Что происходит:

  1. Для каждого Tn из плана агент реально дёргает скилл.
  2. Выход (файлы, stdout, скриншоты) сохраняется в artifacts/<skill>/test/<ts>/run-<n>/.
  3. UI-баги фиксируются через @/SCR (flameshot) — скрин прикладывается как доказательство.

Tip

Никогда не верьте «выходному» отчёту скилла. Доверяйте только артефактам, которые можно открыть в браузере / LibreOffice / pdftotext сторонним инструментом.

Слой 4. Validation (QA Lead persona)

Qwen с промптом qa_lead_prompt.txt получает:

  • план;
  • чек-лист;
  • артефакты;
  • сырой вывод скилла.

И выдаёт построчно по чек-листу: PASS / FAIL: <причина> / SKIP: <условие>.

Контракт: ответ обязан содержать секцию:

{
  "total": 27,
  "pass":  24,
  "fail":  2,
  "skip":  1,
  "verdict": "FAIL"
}

Этого достаточно, чтобы qa-suite в CI поставил статус сборки.

Слой 5. Bug Report (.docx)

Для каждого FAIL Test Architect генерирует карточку:

ID:        BUG-2026-05-14-003
Severity:  Major
Skill:     skills/pptx
Steps:     1) prompt "Создай питч 5 слайдов"
           2) открыть presentation.pptx в LibreOffice
Expected:  5 слайдов с заполненными заголовками
Actual:    4 слайда, 3-й — пустой
Evidence:  artifacts/pptx/test/2026-05-14T12-03/run-1/screenshot.png

Документ собирается через skills/docx и кладётся рядом с чек-листом.

Слой 6. Archival

Все артефакты группируются по принципу «одно тестирование — одна папка»:

artifacts/
└── pptx/
    └── test/
        └── 2026-05-14T12-03-22/
            ├── test_plan.md
            ├── checklist.xlsx
            ├── run-1/
            ├── run-2/
            ├── bug_report.docx
            └── summary.json

Архивация запускается воркфлоу artifact-archival (см. .agent/workflows/).

CI-интеграция

workflow qa-suite запускает полный цикл и возвращает exit code:

  • 0 — все скиллы зелёные.
  • 1 — есть FAIL (см. summary.json).
  • 2 — инфраструктурная ошибка (нет ключей, скилл не найден).

В GitHub Actions это превращается в обязательную проверку для PR, меняющих skills/.

Анти-паттерны

Анти-паттерн Симптом Лечение
QA-самосуд Скилл сам себя валидирует Разделение ролей: Test Architect ≠ QA Lead
Слепые тесты Только stdout, нет визуальных артефактов Скриншоты через @/SCR обязательны для UI
Зелёная пустота Все тесты PASS, потому что все SKIP В контракте verdict зависит от ratio pass / (total - skip)
Тест-данные в репо Гигабайты .pptx в git Хранить в artifacts/ (gitignore) + хэш в summary.json
Хрупкие триггеры Тест ломается от смены формулировки Использовать 3 синонимичных промпта на один кейс

Практические задания

Все результаты складывайте в artifacts/lesson-7/task-N/. Отдельный коммит на задание.

Задание 1 — Bootstrap окружения

Поднимите .venv под qa-skill-tester, установите зависимости из requirements.txt. Сгенерируйте обе персоны командой optimize_qa_prompts.py. Сравните два промпта, в personas.md опишите минимум три отличия в тоне и фокусе.

Задание 2 — Test plan руками

Для скилла skills/pptx напишите вручную test_plan.md (минимум 5 кейсов: 3 happy-path + 2 negative). Затем сгенерируйте план через Test Architect автоматически. Сравните покрытие. Что упустил человек? Что — машина?

Задание 3 — Checklist

Через skills/xlsx создайте checklist.xlsx с пятью обязательными категориями (Frontend / API / Readability / Overlaps / Broken links). Минимум 5 строк в каждой категории. Добавьте формулу-счётчик =COUNTIF(D:D,"PASS")/COUNTA(D:D) в шапку.

Задание 4 — Self-test

Прогоните qa-skill-tester сам на себе командой workflow qa-suite --target skills/qa-skill-tester. Зафиксируйте: сколько багов найдено, какие из них — реальные, какие — false positive. Открытие: мета-инструменты часто проваливают свои же чек-листы.

Задание 5 — Visual proof

Сделайте артефакт с заведомым UI-багом (например, через web-artifacts-builder — кнопка перекрывает текст). Прогоните webapp-testing + qa-skill-tester. Убедитесь, что в bug_report.docx приложен скриншот через @/SCR. Без скриншота — задание не зачтено.

Задание 6 — Report-веб-страница

Через skills/web-artifacts-builder соберите HTML-страницу отчёта: круговая диаграмма pass/fail/skip + таблица багов с фильтрами по severity. Прогоните webapp-testing-ом два сценария: «фильтр Critical показывает только critical-баги», «клик по строке открывает evidence-скрин».

Задание 7 — CI gate

Настройте GitHub Action, который на PR в skills/** запускает workflow qa-suite и блокирует merge при verdict == "FAIL". Pull request с намеренно сломанным скиллом должен получить красный чек. PR с фиксом — зелёный. Приложите ссылки на оба запуска в ci.md.

Definition of Done урока

Что вы получили

Вы — Test Architect. Ваш инструментарий теперь:

  1. Самодокументируется (план + чек-лист).
  2. Самовалидируется (две независимые персоны).
  3. Самоархивируется (timestamped папки).
  4. Самоинтегрируется в CI (qa-suite).

С этого момента любой новый скилл в skills/ обязан пройти qa-suite — иначе он не попадает в main. Качество перестало быть мнением и стало процессом.
