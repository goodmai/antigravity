Lesson 14: Prompt Engineering for Claude Code

Writing effective prompts for an agentic coding assistant is different from prompting a chat model. Tasks need to be decomposable, instructions need to be precise, and context needs to be focused.

The CADE Formula

CADE is a four-part structure for writing prompts that consistently produce accurate, contextually appropriate results. Each component eliminates a different class of ambiguity.

  • C — Context: What is the system, and what is its role? "We have a FastAPI backend monolith backed by MongoDB. This service handles payments only."
  • A — Action: What exactly should Claude do? "Refactor the Stripe integration into a separate async adapter class."
  • D — Details: What are the non-negotiable constraints? "Must follow OWASP security standards. No blocking I/O calls. Secrets via environment variables only."
  • E — Examples: What does the target pattern look like? "Structure it like the repository pattern in src/repositories/user_repo.py."

Assembling all four parts into a single prompt gives Claude everything it needs to start without asking clarifying questions:

> Context: FastAPI monolith + MongoDB, payments service only.
  Action: Refactor the Stripe integration into a separate async adapter class.
  Details: OWASP compliant, no blocking I/O, secrets from env vars only.
  Examples: Follow the pattern in src/repositories/user_repo.py
Anti-pattern — Vibe Coding: Short, vague prompts like "add auth" or "make it faster" force Claude to fill in missing variables with assumptions. Those assumptions are often wrong, frequently insecure, and always inconsistent with the rest of your codebase. CADE replaces assumptions with specifications.

The Three C Rule

Every effective Claude Code prompt satisfies three properties simultaneously:

  • Clear — grammatically unambiguous. One reading of the sentence, not two.
  • Complete — contains all variables Claude needs to start. No implicit knowledge required from the developer's head.
  • Contextual — accounts for the current state of the branch. Names the files that are relevant, references the last thing that changed, notes any constraints imposed by work already in progress.

A prompt that fails even one of these properties will either produce a wrong result on the first pass or require a follow-up to resolve the missing information — which is slower than writing the complete prompt upfront.

Task Decomposition

Don't ask Claude to do everything in one prompt. Break complex tasks into steps:

# Bad
> Refactor the entire authentication system to use OAuth 2.0

# Better
> 1. First, show me the current auth flow in src/auth/
> 2. Identify which components need to change for OAuth 2.0
> 3. Start with the login endpoint — refactor just that function

Chain-of-Thought in CLI

Ask Claude to think before acting:

> Before making any changes, explain your plan for refactoring this function.
  List the steps you'll take and any risks you see.

This "plan first" approach surfaces misunderstandings before code is changed.

Plan Mode (Shift+Tab)

Pressing Shift+Tab twice activates Plan Mode. In Plan Mode, Claude analyzes the codebase and generates a detailed, step-by-step plan for the requested task — but makes no file changes. The plan is presented for your review before any action is taken.

Plan Mode is the correct starting point for any task that touches system architecture, spans multiple modules, or has non-obvious downstream effects. It lets you catch logical errors, architectural mismatches, or overlooked dependencies before they become committed code — which is significantly cheaper to fix than rolling back changes after the fact.

Use Plan Mode as a default gate for:

  • Projects with real users where an incorrect change has operational consequences
  • Tasks involving complex external integrations (payment processors, identity providers, message queues)
  • Any surface with a significant attack area — auth, permissions, data access layers

After reviewing the plan, type proceed to execute it, or refine specific steps before Claude acts.

Precise Specifications

  • Name the exact file: src/components/LoginForm.tsx, not "the login form"
  • State the expected outcome: "the function should return null, not throw, on invalid input"
  • Specify constraints: "don't change the function signature" or "keep all existing tests passing"

Few-Shot Examples

Show Claude the pattern you want:

> I want all API errors handled like this example:
  try { ... } catch (e) { logger.error(e); return { error: e.message }; }
  Now apply this pattern to the three endpoints in src/api/users.ts

Iterative Refinement

Treat Claude Code like a pair programmer — review each step and redirect:

> That looks right but the error message should be user-facing, not technical.
  Revise just the error strings to be friendly and actionable.

Practical Exercises

Complete all three tasks to feel the impact of disciplined prompting:

  1. One-shot vs decomposed. Pick a real refactoring task (e.g., "convert callbacks to async/await across src/api/"). First, attempt it in a single prompt. Then redo it as a sequence of 3–4 narrower prompts that each name files, expected outcomes, and constraints. Compare the diffs.
  2. Plan-first gate. Prefix the same task with "Before touching any file, output a 5-bullet plan and pause for my approval." Verify Claude waits, refine the plan, then say "proceed". Notice how a 30-second plan review prevents 20 minutes of wrong-direction code.
  3. Few-shot pattern matching. Find three call sites that use an inconsistent error-handling pattern. Show Claude one corrected example, then ask it to apply the same pattern to the other two. Confirm style, error type, and logging match across all three.
  4. Iterative refinement. When the result is 80% right, don't restart — give a targeted follow-up: "Good, but rename the helper to parseUserId and move it above its first caller." Practice this until you stop instinctively re-prompting from scratch.
