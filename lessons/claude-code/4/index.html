Lesson 4: Memory with CLAUDE.md

CLAUDE.md is Claude Code's persistent memory system. Unlike conversation history, which resets with /clear, CLAUDE.md is loaded automatically at the start of every session, giving Claude standing context about your project and preferences.

How CLAUDE.md Works

When you start a Claude Code session in a directory, it automatically reads any CLAUDE.md files it finds. These files inject their content into Claude's context at the top of every conversation.

Scoping Rules

Claude Code respects a hierarchy of CLAUDE.md files:

  • ~/.claude/CLAUDE.md — global, loaded in every project
  • CLAUDE.md (project root) — loaded for this project
  • src/CLAUDE.md — loaded when working in src/

All applicable files are loaded and concatenated, with more specific files taking contextual precedence.

What to Put in CLAUDE.md

Effective CLAUDE.md files contain:

  • Project overview — what the codebase does, tech stack
  • Development conventions — naming, formatting, preferred patterns
  • Commands — how to run tests, build, deploy
  • Off-limits areas — files or patterns not to touch
  • Current focus — what you're working on right now

File Size Discipline

The optimal CLAUDE.md is around 60 lines. The hard limit is 300 lines. Beyond that, the agent starts selectively ignoring rules — especially those near the end of the document. The reason: Claude Code's own system prompt already consumes a significant portion of the instruction budget, so a bloated CLAUDE.md competes with the agent's core directives.

The governing principle is to include only what Claude cannot infer by reading the source code itself. Non-obvious things belong in CLAUDE.md; obvious things do not.

GOOD to includeBAD to include (Claude can infer this)
Specific test command: npm run test:unit -- --watch"We use TypeScript" (visible from any .ts file)
Git branch naming convention: feat/<ticket>-<slug>"Components are in src/components" (obvious from the tree)
Non-standard build path: ./scripts/compile.sh --env staging"Use async/await" (visible from the existing code style)
Implicit architectural decision: "all external HTTP calls go through src/gateway/""Don't use var" (ESLint config already enforces this)

For large projects with many subsystems, split rules into a .claude/rules/ directory. Each file in that directory covers one domain (e.g., payments.md, auth.md, infrastructure.md). The agent loads them on demand based on the context of the current task, keeping the active instruction set small and relevant.

Example CLAUDE.md

# Project: Antigravity Academy

## Stack
- Next.js 14, TypeScript, Tailwind CSS
- PostgreSQL via Prisma

## Commands
- `npm run dev` — start dev server
- `npm test` — run vitest suite

## Conventions
- Use kebab-case for filenames
- All components go in `src/components/`
- Never commit directly to main

## Do Not Touch
- `prisma/migrations/` — migration files are immutable

Practical Exercises

Complete all three tasks to build a CLAUDE.md that actually pays for itself:

  1. Write a project CLAUDE.md. In the root of a project you own, create CLAUDE.md containing four sections: Stack, Commands (test/build/dev), Conventions (at least one rule unique to your codebase), and Do Not Touch. Keep it under 60 lines — short and dense beats long and vague.
  2. Verify persistence. Start a fresh Claude Code session and ask "What testing framework does this project use and how do I run a single test?". Confirm Claude answers correctly without you mentioning CLAUDE.md. If it doesn't, your file is too vague — tighten it and retry.
  3. Layer a scoped memory file. Add src/CLAUDE.md (or any subdirectory) with one extra rule — for example, a naming convention or a deprecated module to avoid. Run Claude from that subdirectory and confirm the layered rules apply in addition to the root file.
  4. Add a global preference. Create or extend ~/.claude/CLAUDE.md with one personal default (e.g., "always show the diff before committing"). Open a different project and confirm the rule still applies, proving the global scope works.
