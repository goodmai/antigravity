Отладка и диагностика агентных задач

Агент может зависнуть, уйти не в ту сторону или вернуть непонятный результат. В этом уроке разбираем систематический подход к диагностике: как читать артефакты задач, распознавать паттерны ошибок и безопасно восстанавливаться.

Архитектура наблюдаемости в Antigravity

Antigravity оставляет три слоя информации о ходе задачи:

┌─────────────────────────────────────────┐
│  Task Group (видите в UI)               │
│  ├── Overarching Goal                   │
│  ├── Subtasks (зелёные / красные)       │
│  └── File Pills (изменённые файлы)      │
├─────────────────────────────────────────┤
│  Artifacts (артефакты)                  │
│  ├── implementation_plan.md             │
│  ├── walkthrough.md                     │
│  └── error_report.md                    │
├─────────────────────────────────────────┤
│  Terminal Output                        │
│  ├── stdout / stderr инструментов       │
│  ├── MCP server logs                    │
│  └── CLI exit codes                     │
└─────────────────────────────────────────┘

Паттерны ошибок и их диагноз

1. Агент «крутится на месте»

Симптом: подзадачи помечаются и снова сбрасываются, нет прогресса.

Причины и лечение:

Причина Диагноз Решение
Нечёткое задание В плане артефакта расплывчатые шаги Уточни задачу с примером ожидаемого результата
Противоречивые правила .agent/rules/ конфликтуют между собой Проверь trigger: always правила на пересечения
Зацикленный тест Тест всегда падает → агент чинит → снова падает Посмотри stdout теста вручную

2. MCP инструмент не отвечает

Симптом: в терминале MCP error: connection refused или timeout.

# Проверь статус MCP-серверов
# Settings → MCP Servers → список онлайн/офлайн

# Перезапусти конкретный сервер (пример для GitHub MCP)
pkill -f "mcp-server-github"
# Antigravity перезапустит его автоматически при следующем вызове

Частые причины:

  • Сервер требует GITHUB_TOKEN или другой секрет — проверь .env
  • Docker-сервер не запущен: docker ps | grep mcp
  • Порт занят другим процессом: lsof -i :3000

3. Агент редактирует не те файлы

Симптом: File Pills показывают изменения в не связанных с задачей файлах.

Действие: немедленно нажми «Stop» → проверь git diff → при необходимости откатись:

git diff --stat          # что изменилось
git stash                # сохрани изменения для анализа
git checkout -- .        # откат рабочего дерева

4. Тесты проходили, потом перестали

Симптом: агент сообщает «тесты зелёные», но при ручном запуске они падают.

# Запусти тесты самостоятельно, не через агента
npm test -- --verbose
pytest -xvs

# Проверь, не мокировал ли агент тест вместо фикса
git show HEAD:tests/test_feature.py | grep -E "mock|skip|xfail"

5. Неожиданное удаление или перезапись файлов

Симптом: агент выполнил rm или перезаписал важный файл.

# Проверь git history
git log --oneline -10
git show HEAD --stat

# Восстанови конкретный файл
git checkout HEAD~1 -- path/to/file.py

Стратегия «чистого дерева»

Золотое правило: всегда работай с чистым git tree перед запуском агента в Turbo-режиме.

git status                    # убедись, что нет незакоммиченных изменений
git stash                     # если есть — сохрани
# Запускай агента...
git diff                      # после — просмотри всё что изменилось
git add -p                    # стейджи только нужное

Использование Pending States для контроля

В опасных ситуациях агент переходит в Pending State и ждёт подтверждения. Используй это:

<!-- .agent/rules/confirm-destructive.md -->
---
trigger: always
---
Перед выполнением любой деструктивной операции (DROP TABLE, rm -rf, git reset --hard,
деплой в production) создай артефакт с описанием последствий и дождись явного апрува.

Диагностический чеклист

Когда что-то идёт не так — пройди по списку:

□ Прочитай последний артефакт — там описан текущий план
□ Проверь Terminal Output на exit codes != 0
□ Убедись, что все нужные MCP-серверы онлайн
□ Запусти тесты вручную — не полагайся только на отчёт агента
□ git diff — посмотри реальные изменения, не описание
□ Если агент явно не справляется — Stop → уточни задачу → рестарт

Техники превентивной отладки

Лучше предотвратить проблему, чем чинить:

// workflow: safe-execution

## Перед началом
- Сделай git commit "before: {task}" как точку отката
- Убедись, что тесты проходят ДО изменений

## Критерии остановки
Если за 3 итерации один и тот же тест всё ещё падает —
останови задачу и создай артефакт с диагнозом.

## После завершения
- Запусти полный тестовый прогон вручную
- Проверь git diff на нежелательные изменения

Практика

  1. Намеренно создай задачу с нечётким описанием — наблюдай, как агент интерпретирует её
  2. Отключи один MCP-сервер и запусти задачу, которая его использует — изучи сообщение об ошибке
  3. Настрой правило confirm-destructive из примера выше и проверь его срабатывание
