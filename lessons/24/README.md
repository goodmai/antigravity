# Работа с большими кодовыми базами

Antigravity работает с контекстным окном до 2 миллионов токенов. Но даже это имеет пределы — большой монорепозиторий, полный логов и автогенеренных файлов, засоряет контекст и снижает качество. В этом уроке — техники фокусировки, чанкинга и постепенной работы с крупными проектами.

## Проблема большого контекста

```
Проект: 50 000 файлов, 3M строк кода
Без управления: агент читает всё → медленно, дорого, качество падает

С управлением:
├── .antigravityignore → убрать лишнее из контекста
├── @ Mentions → явно указать нужные файлы
├── Chunking → разбить на независимые задачи
└── Incremental → работать итеративно, не всё сразу
```

## .antigravityignore

Файл `.antigravityignore` в корне проекта исключает файлы и директории из контекста агента. Синтаксис — как `.gitignore`:

```gitignore
# Зависимости
node_modules/
.venv/
__pycache__/
*.pyc

# Сборка и артефакты
dist/
build/
*.min.js
*.min.css
coverage/
.nyc_output/

# Базы данных и медиа
*.sqlite
*.db
*.png
*.jpg
*.mp4
*.zip

# Автогенерированное
migrations/versions/
*.pb.go
*_pb2.py
openapi_generated/

# Логи
logs/
*.log
*.log.*

# Секреты (на всякий случай)
.env
.env.*
secrets/
```

### Контекстно-зависимое игнорирование

Для разных задач используй разные игнор-файлы, переключая через промпт:

```
Работай только с src/api/ и tests/api/.
Игнорируй всё остальное для этой задачи.
```

## @ Mentions как точный скоупинг

Вместо «открой весь проект» — явно указывай только нужное:

```markdown
Задача: добавь валидацию email в форму регистрации.

Контекст:
@/src/components/RegisterForm.tsx  ← только этот компонент
@/src/api/auth.ts                  ← API эндпоинт
@/src/types/user.ts                ← типы

Не трогай остальные файлы.
```

## Стратегии чанкинга

### По модулям

Разбивай монолитный рефакторинг на независимые модули:

```markdown
// workflow: modular-refactor

## Итерация 1: src/api/
Рефакторинг только src/api/ — async/await, типы Pydantic V2.
Сделай коммит: "refactor(api): migrate to async/pydantic-v2"

## Итерация 2: src/services/
Рефакторинг только src/services/ — тот же стиль.
Запусти тесты для services: pytest tests/test_services.py
Сделай коммит.

## Итерация 3: src/models/
... и т.д.
```

### По слоям (вертикальный чанкинг)

Для фич, которые пронизывают несколько слоёв:

```
Фича: добавить поле phone_number в профиль пользователя

Шаг 1: миграция БД (только migrations/)
Шаг 2: модель данных (только src/models/user.py)
Шаг 3: API schema (только src/schemas/user.py)
Шаг 4: эндпоинты (только src/api/users.py)
Шаг 5: тесты (только tests/test_users.py)
```

Каждый шаг — отдельная задача с коммитом. Агент не теряет фокус.

## Управление 2M-токенным окном

### Что «тяжёлое» по токенам

| Тип контента | Приблизительный вес |
|-------------|-------------------|
| 1000 строк Python | ~2 000 токенов |
| `package-lock.json` (типичный) | ~50 000 токенов |
| `node_modules/` (полный) | >10M токенов |
| Картинка 1920×1080 | ~1 500 токенов |
| PDF на 100 страниц | ~80 000 токенов |

### Тактики экономии

```markdown
1. Исключай lock-файлы из контекста:
   package-lock.json, yarn.lock, poetry.lock → добавь в .antigravityignore

2. Для больших файлов — читай конкретные функции:
   «Прочитай только функцию calculate_discount в src/pricing.py»

3. Разделяй документацию и код:
   docs/ → в .antigravityignore (агент не читает если не спросишь)

4. Используй Git как навигатор:
   «Смотри только на файлы из git diff HEAD~5..HEAD»
```

## Инкрементальный рефакторинг

Подход «шаг за шагом» для legacy-кода:

```markdown
// workflow: incremental-legacy-refactor

## Принципы
- НЕ рефакторь весь проект за один раз
- Каждая итерация: один файл или один паттерн
- После каждой итерации: тесты зелёные + коммит

## Последовательность для Python legacy
1. Добавь type hints (без изменения логики)
   → pytest → commit "types: add type hints to module X"

2. Мигрируй на Pydantic V2 (только модели)
   → pytest → commit "refactor: pydantic v2 migration"

3. Добавь async/await (только IO-bound функции)
   → pytest → commit "perf: async io in db layer"

4. Обнови зависимости (по одной библиотеке)
   → pytest → commit "deps: upgrade sqlalchemy 1.4 → 2.0"
```

## Работа с монорепозиторием

Для больших monorepo с десятками сервисов:

```
monorepo/
├── services/
│   ├── auth/          ← работаем здесь
│   ├── payments/
│   └── notifications/
├── shared/
│   └── types/         ← и здесь (зависимость)
└── .antigravityignore
```

```gitignore
# .antigravityignore для работы с auth сервисом
services/payments/
services/notifications/
services/*/node_modules/
services/*/dist/
```

Затем явно указывай:

```
Работаю только с services/auth/ и shared/types/.
Остальные сервисы проигнорированы.
```

## Метрики эффективности

Как понять, что управление контекстом работает:

```
До:   агент читает 500 файлов → 30 сек на ответ, неточный фокус
После: агент читает 15 файлов → 3 сек на ответ, точные изменения

Индикаторы плохого контекста:
- Агент упоминает файлы, не связанные с задачей
- Медленные ответы без сложной логики
- «Я не нашёл файл» для существующего файла
```

## Практика

1. Создай `.antigravityignore` для своего проекта, исключи: `node_modules/`, `*.log`, `dist/`
2. Возьми задачу на рефакторинг и разбей её на 5 независимых чанков с коммитом после каждого
3. Сравни время ответа и точность агента до и после настройки `ignore`-файла
