## 2. Архитектурный обзор продукта (Product Review)

Архитектура системы **Daskibo Academy** представляет собой передовое гибридное DRM-решение (Digital Rights Management) для Web3, ориентированное на максимальную производительность, конфиденциальность контента и гибкость развертывания.

### А. Гибридная схема шифрования (Envelope Encryption)
Прямое использование асимметричного шифрования (например, Lit Protocol) для каждого медиа-файла курса неприменимо из-за огромных накладных расходов. Архитектура решает эту проблему через **конвертное шифрование (Envelope Encryption)**:
1. **На уровне контента (P1: AES-256-GCM)**: Каждый медиа-объект курса шифруется своим уникальным случайным симметричным 256-битным ключом — **DEK (Data Encryption Key)**. Это обеспечивает скорость уровня нативных алгоритмов (сотни мегабайт в секунду).
2. **На уровне бакета (P1 Key Wrap)**: Все DEK упаковываются (шифруются) под единым **Master Key (MK)** бакета. wrapped DEK сохраняются прямо в манифесте или метаданных зашифрованного файла.
3. **На уровне DRM (P3-Lit / P3-Ch)**: Сам 32-байтный Master Key (MK) зашифровывается с помощью Lit Protocol (под условия доступа ACC) или Chipotle (под REST-верификацию в TEE). 
4. **Crypto-Shredding за O(1)**: Для мгновенного отзыва доступа ко всему бакету (например, при компрометации или изменении условий лицензии) достаточно уничтожить или ротировать **один** Master Key (MK). Больше не нужно перешифровывать гигабайты контента.

### Б. Сплит-архитектура сред (Dual-DRM)
Продукт предлагает умное разделение сред, снижающее затраты на разработку и тестирование:
- **Devnet / Staging (Flows B–D)**: Используется облегченный REST DRM-бэкенд **Chipotle** (локальный мок или облачный сервис в TEE). Вместо сложных sessionSigs кошелька, клиент подписывает обычный nonce (`personal_sign` -> `signedProof`). Проверка ACC на devnet упрощена (прямое совпадение адресов).
- **Mainnet (Flow E)**: Включается полноценный **Lit Protocol MPC (Threshold KMS)**. Ключ MK распределен в виде BLS12-381 долей на независимых узлах. Клиент использует SIWE (EIP-4361) для генерации `sessionSigs`. Узлы Lit самостоятельно читают BSC on-chain состояние смарт-контрактов для проверки прав доступа.

### В. Модели лицензирования платформы (Deployer Models)
Продукт закладывает основу для B2B-дистрибуции платформы:
- **Модель А (White-label, Единоразовый выкуп)**: Оператор (Deployer) покупает вечную лицензию у владельца протокола (Alice) за фиксированную стоимость через `LicenseRegistry`. Дальнейшие комиссии с курсов идут напрямую Deployer'у.
- **Модель B (SaaS, Revenue-Share)**: Deployer интегрируется в существующий протокол и выплачивает процент от всех операций (публикация Bob'ом, чтение Charlie, покупка курсов). Логика `lit-pricing.js` расширена для поддержки трехстороннего сплита (Bob / Deployer / Alice).

## 3. Аудит безопасности и архитектуры (Security & Architecture Audit)

В ходе глубокого анализа кода смарт-контрактов (`smartcontracts/contracts/*`), клиентской логики (`buckets/*`) и структуры контейнеризации были выделены критические аспекты безопасности, потенциальные уязвимости и архитектурные допущения.

### А. Смарт-контракты (Solidity 0.8.28, EVM Shanghai)
Контракты написаны на высочайшем уровне безопасности. Разработчики применили лучшие практики:

```
                  [ CourseMarketplace.sol ]
                             │
       (purchase)            │  (collectFrom)
            ├──► Treasury ───┼───────────────► [ Treasury Balance ]
            │   (Pull-payment, 20% cut)
            │
            └──► AccessPass ─────────────────► [ Soulbound NFT registry ]
                (One-shot mint logic)
```

1. **Защита от Reentrancy и DoS на выплатах (Выполнено ✅)**:
   В ранних версиях распределение платы за курс происходило через немедленный `transfer`/`call` (push-модель) на кошелек автора и казны. В текущей версии `CourseMarketplace.sol` полностью перешел на **единую модель Pull-payments**:
   - При вызове `purchase()` все средства зачисляются на внутренние балансы участников в маппинге `pendingWithdrawals`.
   - Сами выплаты не производятся. Уязвимость DoS (когда один из получателей блокирует транзакцию покупки своим ревертящим `fallback()`) полностью устранена.
   - Участники забирают свои деньги самостоятельно через метод `withdraw()`, защищенный кастомным модификатором `nonReentrant` (сгенерированным с помощью `error Reentrancy()` для минимизации расхода газа).
2. **Soulbound Свойства `AccessPass.sol` (Выполнено ✅)**:
   Предикаты доступа Lit (ACC) опираются на владение правами. Если бы права доступа были передаваемыми ERC-721 токенами, злоумышленник мог бы применить **Flash-Loan атаку** (в рамках одной транзакции занять токен доступа, пройти проверку дешифрования Lit, вернуть токен в пул). 
   - `AccessPass` жестко блокирует любые переводы: `transferFrom`, `safeTransferFrom`, `approve` и `setApprovalForAll` безусловно ревертят транзакцию с ошибкой `Soulbound()`.
   - Это гарантирует, что право доступа жестко привязано к адресу пользователя (address equality is not flash-loanable).
3. **Безопасность времени действия (Expiry Hardening) (Выполнено ✅)**:
   Введен контроль максимальной длительности доступа `MAX_DURATION` (~100 лет). Это предотвращает overflow (переполнение) при сложении `block.timestamp + accessDuration` типа `uint64`. Нулевое значение или константа `DURATION_PERPETUAL` обрабатываются как бесконечный доступ (срок 0) без арифметических вычислений.

### Б. Криптографические и клиентские угрозы (Вне сети)

#### 1. Угроза компрометации Chipotle в тестовых средах (Single Point of Failure)
* **Проблема**: В средах `devnet` и `testnet-Ch` ключ шифрования `MK` защищается Chipotle REST API. При локальном тестировании Chipotle mock (`localhost:8000`) хранит AES-ключ в оперативной памяти и проверяет `signedProof` (`personal_sign` от кошелька). Это централизованная точка отказа. Более того, приватный ключ `CHIPOTLE_PKP_KEY` передается в переменных окружения.
* **Влияние**: Утечка `CHIPOTLE_PKP_KEY` в тестовой среде позволяет скомпрометировать все тестовые мастер-ключи.
* **Рекомендация / Митигация**: 
  - `CHIPOTLE_PKP_KEY` никогда не должен попадать в production. 
  - Для продакшена обязателен переход на Lit Protocol `datil` (Flow E), где ключ шифрования разделен с помощью схем пороговой подписи MPC, и централизованный сервер Chipotle полностью исключен из цепочки доверия.

#### 2. Риск утечки сессионных подписей (XSS / Session Theft)
* **Проблема**: Для дешифрования контента в Lit Protocol клиент генерирует сессионные подписи `sessionSigs` (или `signedProof` в Chipotle). В случае успешной XSS-атаки (внедрение вредоносного JS на страницу фронтенда), злоумышленник может перехватить `sessionSigs` или заставить кошелек жертвы подписать вредоносный запрос. 
* **Влияние**: Похищенные `sessionSigs` дают полный доступ к расшифровке `MK` бакета напрямую из браузера злоумышленника в обход интерфейса платформы.
* **Рекомендация / Митигация**:
  - Строгая настройка **Content Security Policy (CSP)**. Запретить inline-скрипты, ограничить `connect-src` исключительно эндпоинтами Greenfield SP, Lit Nodes и RPC.
  - Использовать минимальное время жизни сессии (TTL) для `sessionSigs`.
  - В Chipotle-схеме `signedProof` не имеет встроенного TTL, что делает его более уязвимым, чем Lit `sessionSigs` с поддержкой scoping. Chipotle должен использоваться строго в закрытых dev/testnet контурах.

#### 3. Публичность метаданных манифестов (Metadata Leakage)
* **Проблема**: Для индексации курсов краулер собирает файлы `_lit/manifest.json` из публично доступных бакетов (`public-read`). Имена файлов курса, их размер и `contentType` хранятся в открытом виде.
* **Влияние**: Злоумышленник может узнать структуру курса, названия лекций и типы файлов до покупки.
* **Рекомендация / Митигация**:
  - Не хранить конфиденциальную информацию в названиях ключей объектов (например, вместо `lecture-01-how-to-hack-bsc.mp4.enc` использовать хэши или UUID, например `a1c2e3...enc`).
  - Реальные названия и структуру лекций шифровать внутри самого манифеста, оставляя публичным только хэш контента и ID курса для индексатора.

#### 4. Проблема роста состояния (State Bloat) в `AccessPass.sol`
* **Проблема**: В контракте `AccessPass.sol` при продлении подписки (повторная покупка после истечения срока действия) для пользователя генерируется новый `tokenId`, который записывается в `ownerOf[tokenId] = to`. При этом старые ID токенов не сжигаются, а маппинг `_granted` просто перезаписывается новым временем истечения.
* **Влияние**: Накопление неиспользуемых "висячих" идентификаторов токенов в состоянии контракта, что со временем увеличивает стоимость хранения состояния для узлов BSC.
* **Рекомендация**: В следующей версии контракта реализовать функцию `burn()` или механизм повторного использования существующего `tokenId` при обновлении (продлении) подписки вместо генерации инкрементного `_nextId`.

## 4. Чеклист для вывода в Production (Mainnet)

При переходе из тестовой среды (`testnet-Ch`/Chipotle) в промышленную (`mainnet` / Lit Datil) необходимо выполнить следующие шаги:

- [ ] **Криптография и DRM**: Полностью заменить адаптер: импортировать `createLitClient({ litNetwork: 'datil' })` вместо Chipotle. Убедиться, что порт **7470** открыт на серверах для P2P-обмена с узлами Lit.
- [ ] **Контракты**: Задеплоить `CourseMarketplace.sol`, `AccessPass.sol` и `Treasury.sol` на BSC Mainnet.
- [ ] **Владение**: Выполнить передачу прав владения контрактами (`AcceptOwnership`) с EOA деплойера на мультисиг-кошелек (Gnosis Safe) или контракт таймлока.
- [ ] **Lit-кредиты**: Пополнить баланс Lit Capacity Credits (иначе узлы `datil` будут жестко ограничивать частоту запросов клиентов).
- [ ] **Хранилище**: Переключить Greenfield-клиент на промышленные SP (например, `gnfd-mainnet-sp1.bnbchain.org`).
- [ ] **Безопасность фронтенда**: Прописать строгие заголовки CSP на Nginx-сервере, убрав `localhost` и тестовые API из `connect-src` и добавив адреса нод Lit Mainnet.
